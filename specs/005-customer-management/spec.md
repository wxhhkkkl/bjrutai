# Feature Specification: 客户管理模块（组织客户视图 + 手工录入 + 医院绑定状态 + 推广员变更记录）

**Feature Branch**: `005-customer-management`
**Created**: 2026-08-03
**Status**: Draft
**Input**: User description: "客户管理模块， 左侧需要显示组织结构树，完后选中后显示对应组织下绑定的客户；默认选中根组织；去除以往的绑定管理菜单；后台管理员可以手工录入客户；客户绑定状态意味着和哈尔滨互联网医院进行绑定；客户详情内要有客户的医保账户、身份证填写的地方；管理员可以可以更改客户的推广员，但要有详细的更改记录；"

## Clarifications

### Session 2026-08-03

- Q: 手工录入客户后，绑定状态如何处理？ → A: 录入时即调用哈尔滨互联网医院接口尝试绑定匹配；匹配成功置为"已绑定"，匹配失败置为"待绑定"并记录失败原因，匹配结果不阻断客户建档
- Q: 身份证号、医保账户的存储方式如何处理？ → A: 仅脱敏展示，不加密（沿用现状明文存储，任何界面展示统一脱敏）
- Q: 后台是否保留对客户进行解绑的能力？ → A: 移除解绑（本迭代不提供解绑操作，仅保留推广员变更）
- Q: 手工录入匹配失败后（待绑定）的客户，如何后续完成与医院的绑定匹配？ → A: 靠分销员端（小程序绑定流程）完成，绑定流程需按身份证去重，复用已有档案而非新建重复档案

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 组织维度客户视图 (Priority: P1)

管理员进入"客户管理"模块，左侧展示组织结构树，右侧展示客户列表。默认选中根组织，选中任意组织后，右侧展示该组织及其全部下级组织范围内推广员（分销员）名下的客户。客户行展示姓名、手机号（脱敏）、绑定状态、推广员、所属组织、更新时间，并支持按绑定状态筛选与姓名/手机号搜索。

**Why this priority**: 客户管理从"全量平铺列表"改造为"按组织维度查看"，是本次客户管理模块重构的基础布局，其他客户操作（录入、详情、变更推广员）都挂载在此视图之上。该视图直接决定管理员定位客户的效率，属 P1。

**Independent Test**: 可通过管理员进入客户管理 → 默认选中根组织看到客户 → 切换组织节点 → 验证客户列表按组织范围变化（含下级组织）的流程独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员打开"客户管理", **When** 页面加载, **Then** 左侧展示组织结构树，默认选中根组织（若存在多个根组织则默认选中第一个），右侧展示根组织子树范围内的客户列表
2. **Given** 管理员选中某组织节点, **When** 切换组织, **Then** 右侧客户列表更新为该组织及其全部下级组织范围内推广员名下的客户
3. **Given** 客户列表已加载, **When** 查看每行, **Then** 展示姓名、手机号（脱敏）、绑定状态标签、推广员、所属组织、更新时间
4. **Given** 选中的组织范围内无客户, **When** 查看列表, **Then** 展示空状态提示
5. **Given** 管理员选择绑定状态筛选或输入关键词搜索, **When** 提交, **Then** 列表按条件过滤并展示对应结果
6. **Given** 客户所属推广员调整了所属组织, **When** 重新查看, **Then** 客户随之展示在新的组织范围内

---

### User Story 2 - 后台手工录入客户 (Priority: P1)

管理员在当前选中的组织下手工录入新客户：填写姓名、手机号、身份证号（必填），医保账户、家属电话、备注（选填），并指定该客户的推广员（默认当前组织下的分销员）。创建后客户展示在对应组织客户列表中，系统即时调用哈尔滨互联网医院接口尝试匹配，绑定状态视匹配结果置为"已绑定"或"待绑定"。

**Why this priority**: 手工录入是后台创建客户档案的主要入口，是"客户管理"模块的主动建档能力，也是后续绑定、推广员变更等操作的数据前提，属 P1。

**Independent Test**: 可通过管理员选中组织 → 打开新建客户 → 填写资料并指定推广员 → 提交 → 在客户列表及客户详情中看到新客户的过程独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员选中某组织并打开"新建客户", **When** 填写必填资料、指定推广员并提交, **Then** 系统创建客户，展示在对应组织客户列表中，详情可查看
2. **Given** 管理员录入时未填写姓名/手机号/身份证号任一必填项, **When** 提交, **Then** 系统提示必填项缺失并阻止提交
3. **Given** 管理员录入时未指定推广员, **When** 提交, **Then** 系统提示必须选择推广员并阻止提交
4. **Given** 管理员录入的身份证号已存在其他客户档案, **When** 提交, **Then** 系统拒绝并提示该身份证已建档
5. **Given** 新建客户提交成功且医院匹配成功, **When** 查看其绑定状态, **Then** 状态为"已绑定"，并展示医院绑定完成时间
6. **Given** 新建客户提交成功但医院匹配失败或接口异常, **When** 查看其绑定状态, **Then** 客户仍建档成功，状态为"待绑定"，并展示失败/待匹配原因
7. **Given** 选中的组织下没有任何分销员, **When** 打开新建客户, **Then** 推广员选择列表为空并给出提示，管理员需先在该组织下创建分销员

### User Story 3 - 客户详情：医保账户与身份证维护 (Priority: P1)

客户详情页的基本信息中必须提供身份证号与医保账户的查看与填写位置。敏感信息（身份证号、医保账户、手机号）一律脱敏展示；管理员编辑这些敏感字段时必须填写修改原因，系统记录变更审计。

**Why this priority**: 身份证与医保账户是客户与哈尔滨互联网医院绑定时用于匹配的核心身份信息，缺失或错误会导致绑定匹配失败。这是客户档案完整性的关键要求，属 P1。

**Independent Test**: 可通过打开客户详情 → 查看脱敏的身份证/医保账户 → 编辑并填写修改原因 → 保存后再次查看新脱敏值的流程独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员打开客户详情, **When** 查看基本信息, **Then** 展示身份证号与医保账户（存在时以脱敏形式展示，如 `110***********1234`）
2. **Given** 客户档案尚未填写身份证或医保账户, **When** 查看详情, **Then** 展示可填写位置，管理员可录入
3. **Given** 管理员编辑身份证号、医保账户或手机号任一敏感字段, **When** 未填写修改原因提交, **Then** 系统拒绝并提示填写修改原因
4. **Given** 管理员填写修改原因并保存敏感字段, **When** 保存成功, **Then** 新值生效并记录变更审计，可追溯
5. **Given** 管理员修改敏感字段后再次查看, **When** 刷新页面, **Then** 展示更新后的脱敏值，明文不直接展示

---

### User Story 4 - 推广员变更与详细变更记录 (Priority: P1)

管理员可以更改客户归属的推广员（分销员），更改时填写原因。每次变更系统生成完整的变更记录：操作人、变更时间、变更前推广员、变更后推广员、变更原因。管理员在客户详情的绑定记录中可完整追溯这些变更。

**Why this priority**: 客户与推广员的归属关系直接影响业绩贡献归属，变更必须留痕、可追溯、可审计，是客户管理模块的核心管理与合规要求，属 P1。

**Independent Test**: 可通过更改客户推广员 → 查看客户详情绑定记录 → 核对操作人/时间/变更前后推广员/原因的流程独立验证。

**Acceptance Scenarios**:

1. **Given** 客户档案已存在, **When** 管理员更改其推广员并填写原因, **Then** 客户归属新推广员，客户在对应组织视图中正确展示
2. **Given** 管理员发起推广员变更, **When** 目标推广员不存在或不可开展业务, **Then** 系统拒绝并给出明确提示
3. **Given** 推广员变更成功, **When** 查看客户详情的绑定记录, **Then** 展示该次变更的操作人、时间、变更前推广员、变更后推广员、原因
4. **Given** 客户历史上发生多次推广员变更, **When** 查看绑定记录, **Then** 每次变更均完整保留，按时间可追溯
5. **Given** 管理员查看变更记录, **When** 核对, **Then** 记录与实际操作一致，历史数据不丢失、不篡改

---

### User Story 5 - 移除"绑定管理"菜单并合并能力 (Priority: P2)

后台不再展示独立的"绑定管理"菜单及其页面。原绑定管理中的更改推广员（转移）能力并入客户管理模块；绑定请求的查看与绑定历史并入客户详情的绑定记录中展示。

**Why this priority**: 这是对导航与页面结构的清理，避免两套并行的客户相关入口。其核心能力（更改推广员）已由 US4 承接，剩余为菜单与页面的移除工作，故为 P2。

**Independent Test**: 可通过管理员登录后台 → 确认菜单中不再出现"绑定管理" → 在客户管理中仍能完成推广员变更的流程独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员打开后台导航, **When** 查看菜单, **Then** 不再出现"绑定管理"菜单入口
2. **Given** 管理员需要更改客户推广员, **When** 在客户管理模块内操作, **Then** 可正常完成，结果与变更记录一致
3. **Given** 管理员需要查看客户的绑定与变更历史, **When** 打开客户详情的绑定记录, **Then** 可查看完整记录
4. **Given** 原绑定管理页面被移除, **When** 直接访问旧地址, **Then** 跳转至客户管理或提示页面不存在，不出现空白页

### Edge Cases

- 组织结构为多根森林（存在多个根组织）：默认选中第一个根组织，切换根组织时客户列表随之切换
- 手工录入时当前组织下没有分销员：推广员选择为空，明确提示先创建分销员
- 身份证号重复建档：拒绝并提示，防止同一患者重复建档
- 客户所属推广员调整了组织：客户展示随推广员归属变化，出现在新的组织范围内
- 推广员被停用后其名下客户归属：客户保留在原推广员名下，直至管理员变更推广员
- 目标推广员所在组织资质不达标或被停用：参考既有业务规则，拒绝变更或明确警告（与现有转移校验一致）
- 手工录入时医院接口匹配失败、超时或不可用：客户仍建档成功，绑定状态为"待绑定"并展示失败原因，不因接口异常导致录入失败
- 手工录入的客户匹配失败后长期处于"待绑定"：状态真实反映医院侧绑定进度，不与推广员归属混淆；可由分销员小程序端提交绑定申请后续完成匹配
- 分销员端绑定匹配成功时已存在同身份证的客户档案：复用/更新该档案（绑定状态置为"已绑定"，涉及推广员变化按 FR-011/FR-012 记录变更），不新建重复档案
- 大组织下客户数量大：列表需支持分页加载，切换组织时数据正确替换
- 敏感信息（身份证/医保账户/手机号）：所有展示位置统一脱敏，明文不直接暴露
- 修改敏感信息时的审计：未填写修改原因的修改一律被拦截

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 客户管理模块左侧必须展示组织结构树（支持多根组织森林），管理员可选中任一组织节点
- **FR-002**: 客户管理模块默认选中根组织；存在多个根组织时默认选中第一个根组织
- **FR-003**: 选中组织后，系统必须展示该组织及其全部下级组织范围内推广员（分销员）名下的客户列表
- **FR-004**: 客户列表必须展示姓名、手机号（脱敏）、绑定状态、推广员、所属组织、更新时间，并支持按绑定状态筛选与按姓名/手机号搜索
- **FR-005**: 系统必须支持管理员在当前选中组织下手工录入客户，必填姓名、手机号、身份证号，选填医保账户、家属电话、备注
- **FR-006**: 手工录入客户时必须指定推广员（分销员），推广员可选范围为该组织及其下级组织下的分销员
- **FR-007**: 系统必须防止同一身份证号重复建档；分销员端绑定流程匹配成功时若已存在同身份证的客户档案，必须复用/更新该档案而非新建重复档案（涉及推广员变化时按 FR-011/FR-012 记录变更）
- **FR-008**: 手工录入客户时必须调用哈尔滨互联网医院接口进行绑定匹配；匹配成功则绑定状态置为"已绑定"，匹配失败则置为"待绑定"并记录失败原因。绑定状态反映客户与哈尔滨互联网医院的绑定关系——"已绑定"表示客户已在医院侧完成绑定匹配
- **FR-009**: 客户详情必须展示并支持维护身份证号与医保账户；身份证号、医保账户与手机号在任何展示位置一律脱敏，不得直接暴露明文
- **FR-010**: 身份证号、医保账户、手机号等敏感字段的修改必须填写修改原因，并记录变更审计
- **FR-011**: 系统必须支持管理员更改客户归属的推广员（分销员），目标推广员必须存在且可开展业务
- **FR-012**: 每次推广员变更必须生成完整审计记录：操作人、变更时间、变更前推广员、变更后推广员、变更原因；客户详情的绑定记录中可追溯查看
- **FR-013**: 系统必须移除"绑定管理"菜单及独立页面，原绑定请求查看与更改推广员能力并入客户管理模块
- **FR-014**: 客户管理模块的查看操作必须受 `customers.read` 权限控制，录入、编辑、更改推广员等写操作必须受 `customers.write` 权限控制；无权限操作必须被拒绝并明确提示

### Key Entities *(include if feature involves data)*

- **客户 (Customer)**: 患者/客户档案。含姓名、手机号、身份证号、医保账户、家属电话、备注，归属推广员（分销员），绑定状态（待绑定/已绑定/已解绑，与哈尔滨互联网医院绑定关系一致）。客户所属组织由推广员所属组织推导。
- **组织 (Organization)**: 组织结构树节点。客户管理视图的组织维度来源，客户按推广员所属组织归入对应组织视图。
- **分销员 (Distributor)**: 推广员。客户归属的业务主体，属于某一组织；客户列表按分销员所属组织聚合展示。
- **绑定/变更记录 (Binding & Change Record)**: 客户与推广员之间的绑定及推广员变更的审计记录，含操作人、时间、变更前后推广员、原因。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可在 3 分钟内完成"选中组织 → 手工录入客户 → 在客户列表看到新客户"的完整操作闭环
- **SC-002**: 切换组织节点后，客户列表在 2 秒内展示对应组织范围内的客户
- **SC-003**: 手工录入的客户 100% 能在其推广员所属组织及其上级组织的客户视图中看到
- **SC-004**: 客户详情中身份证、医保账户 100% 以脱敏形式展示，明文不直接暴露
- **SC-005**: 推广员每次变更 100% 生成完整审计记录，可追溯查看（操作人、时间、变更前后推广员、原因）
- **SC-006**: 敏感字段修改未填写原因时 100% 被拦截
- **SC-007**: 后台导航中 100% 不再出现"绑定管理"菜单
- **SC-008**: 无 `customers.write` 权限的账号对录入/编辑/更改推广员操作 100% 被拒绝并提示
- **SC-009**: 客户绑定状态标签与哈尔滨互联网医院绑定关系语义一致，"已绑定"即表示医院侧已绑定

## Assumptions

- 客户所属组织由推广员（分销员）所属组织推导，客户上不单独存储组织归属字段；组织视图默认包含该组织及其全部下级组织（子树）范围的客户
- 手工录入客户时即调用哈尔滨互联网医院接口尝试绑定匹配：匹配成功置为"已绑定"并记录绑定时间，匹配失败置为"待绑定"并记录失败原因；匹配结果不阻断客户建档（FR-008 已确认）
- 手工录入客户必须指定推广员（分销员），推广员可选范围为当前选中组织及其子树下的分销员，创建时默认选中该组织下的第一个可用分销员
- 身份证号作为客户唯一性标识，重复建档被拒绝
- 敏感信息（身份证、医保账户）沿用现状明文存储，不新增加密基础设施；任何界面展示统一脱敏（已确认）
- 客户推广员变更的对象为任意已建档客户，不限于已绑定客户
- 本迭代不提供解绑操作（已确认）；推广员变更不改变客户与医院的绑定状态，客户绑定状态仅由医院匹配结果决定
