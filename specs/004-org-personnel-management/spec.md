# Feature Specification: 组织人员管理（组织架构 + 分销员 + 组织管理员业绩视图）

**Feature Branch**: `004-org-personnel-management`
**Created**: 2026-08-02
**Status**: Draft
**Input**: User description: "层级管理改为组织人员管理，后台需要可以建立组织和管理组织结构，点开组织详情里面可以维护某一层组织的资质文件，每层的组织内都可以新建分销员账户，分销员，组织可以设置某几分销员为该组织的管理员，组织管理员可以在前端小程序看到该组织下的人员的业绩贡献情况。"

## Clarifications

### Session 2026-08-02

- Q: 分销员与组织的归属关系 → A: 单组织归属（每个分销员仅归属一个组织，业绩计入其所属组织）
- Q: 现有功能的迁移适配范围 → A: 全部适配（贡献值计算、个人贡献看板、客户绑定、推广码、分账规则、对账报表全部迁移到组织/分销员模型）
- Q: 后台角色权限分配方式 → A: 新增细分权限点（组织管理、分销员管理、组织管理员设置按角色独立配置；组织资质审核复用资质审核权限）
- Q: 组织管理员由谁授权 → A: 仅后台管理员（具备相应后台权限的账号设置/撤销组织管理员身份）
- Q: 分销员的小程序登录/认证方式 → A: 手机号+密码登录，首次登录强制绑定微信，此后可用微信授权快速登录
- Q: 组织业绩视图的数据深度 → A: 组织汇总 + 各分销员贡献值（本月/累计），不含客户级明细

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 组织结构建立与管理 (Priority: P1)

管理员在后台进入"组织人员管理"模块，建立组织树（如 L1 总部 → L2 区域 → L3 城市 → 等各级组织），对组织节点进行新增、编辑、删除、排序和整体迁移（含子树）。组织树取代现有"层级管理"中的层级树，成为组织与人员归属的结构骨架。

**Why this priority**: 组织树是全部组织人员管理功能的数据基础。没有组织结构，后续的资质维护、分销员创建、组织管理员设置和业绩查看都无法挂载。该模块同时直接替换现有"层级管理"入口，是最基础的一步。

**Independent Test**: 可通过管理员在后台创建多级组织 → 编辑 → 整体迁移 → 验证环路拦截的完整流程独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员在后台打开"组织人员管理", **When** 选择上级组织并创建新的下级组织节点, **Then** 系统建立父子关系，新节点立即展示在组织树对应位置
2. **Given** 管理员需要调整组织顺序或改名, **When** 编辑组织节点, **Then** 修改立即生效并展示在组织树中
3. **Given** 管理员需要将组织 X 及其全部下级整体迁移至另一分支, **When** 执行迁移操作, **Then** 系统保留调整历史，X 及其子树在新分支下展示
4. **Given** 管理员尝试将组织 A 设为 B 的下级（B 本身是 A 的下级）, **When** 提交操作, **Then** 系统检测到环形引用并拒绝操作，提示"组织关系不允许形成闭环"
5. **Given** 管理员删除某组织节点, **When** 该组织下仍有分销员或下级组织, **Then** 系统拒绝删除并提示先处理其下人员与下级组织，或明确二次确认的处置方式
6. **Given** 组织结构发生创建/迁移/删除, **When** 变更完成, **Then** 系统记录完整操作日志（操作人、时间、变更前后关系）

---

### User Story 2 - 组织资质文件维护 (Priority: P1)

管理员点开某一层组织的详情，维护该组织的资质文件（营业执照、法人证书等）。支持上传新资质文件、查看历史资质、替换即将到期或已驳回的资质、跟踪每个文件的审核与有效期状态。资质状态变化会反映到该组织的业务可用性。

**Why this priority**: 资质合规是业务开展的准入门槛。原系统资质挂在个人（拓展人）名下，本故事将其改为挂在组织层级上，是"层级管理改为组织人员管理"的核心语义变化之一。

**Independent Test**: 可通过管理员进入组织详情 → 上传资质文件 → 查看审核状态 → 替换/续期资质 → 查看组织业务状态变化的完整流程独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员点开某组织详情, **When** 切换到"资质文件"页签, **Then** 展示当前资质文件清单、每个文件的状态（审核中/已通过/已驳回/即将到期/已过期）与有效期
2. **Given** 管理员为组织上传新的资质文件, **When** 提交, **Then** 系统保存文件并置为"审核中"，通知有审核权限的后台账号
3. **Given** 资质文件已通过, **When** 该组织状态校验, **Then** 组织被视为具备有效资质，其下分销员无需单独资质即可按规则开展业务
4. **Given** 资质即将到期（30 天内）, **When** 系统检测有效期, **Then** 自动提醒管理员维护续期
5. **Given** 组织资质已过期, **When** 系统检测过期, **Then** 标记组织资质为"已过期"，暂停该组织下分销员的业务（保留登录与历史业绩查看，停止新推广码生成与贡献值累计）
6. **Given** 管理员查看组织资质历史, **When** 打开历史记录, **Then** 可追溯每次上传/审核/驳回/续期的记录与操作人

---

### User Story 3 - 分销员账户创建与管理 (Priority: P1)

管理员在每一层组织内新建分销员账户，为其设置登录凭证和基本资料（姓名、手机号等）。每个分销员仅归属一个组织；后台可调整分销员所属组织、启停用账户、重置凭证。分销员归属组织后，其产生的业绩贡献计入其所属组织。

**Why this priority**: 分销员是组织内的人员实体，也是业绩贡献的归属主体。没有分销员账户，组织只是一个空壳，也无法支撑组织管理员的业绩查看。

**Independent Test**: 可通过管理员在组织中创建分销员账户 → 调整所属组织 → 启停用 → 用新账户登录小程序的完整流程独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员打开某组织详情, **When** 新建分销员账户并填写资料, **Then** 系统创建账户、生成登录凭证，并将分销员归属到该组织
2. **Given** 分销员账户已创建且首次登录, **When** 使用手机号+密码登录, **Then** 登录成功并强制引导完成微信绑定，绑定后方可正常使用该组织范围内的功能与数据；此后可用微信授权快速登录
3. **Given** 管理员需要调整分销员的所属组织, **When** 执行调整, **Then** 分销员归属即时变更，此后的业绩计入新组织
4. **Given** 分销员离职或违规, **When** 管理员停用账户, **Then** 该账户无法再登录，其历史业绩保留在组织下
5. **Given** 分销员遗忘凭证, **When** 管理员重置凭证, **Then** 分销员可用新凭证登录，旧凭证立即失效
6. **Given** 一个手机号已被某组织使用, **When** 管理员用该手机号在其他组织创建账户, **Then** 系统拒绝并提示"该手机号已存在分销员账户"

---

### User Story 4 - 组织管理员设置 (Priority: P1)

组织可以设置若干名分销员为该组织的管理员。组织管理员身份仅由具备相应后台权限的管理员在后台授权，用于在小程序查看本组织的业绩情况；小程序端组织管理员不承担设置/撤销管理员等管理职能。设置与撤销即时生效。

**Why this priority**: 组织管理员是"组织人员管理"闭环的关键角色，连接组织结构与小程序端业绩查看。它是后续业绩视图（US5）的授权前提。

**Independent Test**: 可通过后台在某组织内设置分销员为组织管理员 → 该分销员登录小程序获得组织业绩查看权限 → 撤销后权限即时消失的流程独立验证。

**Acceptance Scenarios**:

1. **Given** 某组织下已存在分销员账户, **When** 管理员将该分销员设置为该组织管理员, **Then** 系统授予其该组织的管理身份，该分销员可在小程序看到组织业绩入口
2. **Given** 组织管理员身份已设置, **When** 分销员登录小程序, **Then** 展示其被授权的组织及其业绩查看功能
3. **Given** 管理员需要撤销某分销员的组织管理员身份, **When** 执行撤销, **Then** 其小程序端组织业绩入口即时消失，不影响其普通分销员身份
4. **Given** 管理员查看某分销员的身份, **When** 打开其详情, **Then** 展示其所属组织及在该组织内的身份（普通成员/组织管理员），身份随时间与授权变化
5. **Given** 被设为管理员的组织被迁移或调整, **When** 组织结构变化, **Then** 管理员的授权跟随组织迁移，权限范围随新结构更新

---

### User Story 5 - 组织管理员业绩贡献查看 (Priority: P2)

组织管理员登录前端小程序后，进入"组织业绩"页面，查看其被授权组织下人员的业绩贡献情况，包括组织整体汇总与组织内各分销员的本月/累计贡献值。查看范围受其授权组织约束，不展示客户级明细。

**Why this priority**: 这是组织管理员角色的最终价值体现——让组织负责人能掌握本组织的人员业绩。它依赖 US1-US4 的数据结构就绪，因此排在 P2。

**Independent Test**: 可通过设置组织管理员 → 登录小程序 → 查看组织业绩汇总与成员明细 → 验证越权组织数据不可见的流程独立验证。

**Acceptance Scenarios**:

1. **Given** 分销员已被设为某组织管理员, **When** 登录小程序进入"组织业绩"页面, **Then** 展示该组织及其全部下级组织的业绩汇总，以及树内各分销员的本月/累计贡献值，不含客户级明细
2. **Given** 组织业绩页面加载, **When** 数据更新, **Then** 业绩数据实时反映当前贡献值，只显示数值不显示金额
3. **Given** 组织管理员尝试查看其授权组织子树之外的任何组织数据, **When** 访问相关数据, **Then** 系统拒绝并只展示其授权子树范围内的数据
4. **Given** 组织管理员的授权被撤销, **When** 其再次登录小程序, **Then** 组织业绩入口不再展示
5. **Given** 组织下人员当月有新业绩产生, **When** 组织管理员刷新查看, **Then** 业绩贡献随之更新，与个人贡献值数据一致

---

### User Story 6 - 现有功能迁移到组织/分销员模型 (Priority: P1)

现有系统（001）中依赖"层级/拓展人"的功能在组织模型上线后必须整体迁移：拓展人数据迁移为分销员并归入组织，客户绑定关系与推广码迁移到分销员主体，贡献值计算主体改为分销员并按组织树逐级汇总，个人贡献看板、分账规则、对账报表随组织模型适配。迁移后历史数据完整保留、数值一致。

**Why this priority**: 组织树取代层级树后，现有功能若不迁移将失去数据支撑而失效。为保持系统整体可用，迁移必须与组织人员管理同步完成，属 P1。

**Independent Test**: 迁移完成后用历史数据验证：客户绑定、推广码、账单、贡献值 100% 保留且归属正确；个人贡献看板、推广码、分账、对账报表在新模型下正常运行。

**Acceptance Scenarios**:

1. **Given** 系统存在历史拓展人与层级数据, **When** 执行迁移, **Then** 拓展人迁移为分销员并归入对应组织，层级节点迁移为组织节点，上下级归属关系完整保留
2. **Given** 迁移前客户已绑定至某拓展人, **When** 迁移完成, **Then** 客户绑定关系迁移到对应分销员，绑定历史不丢失
3. **Given** 迁移前拓展人有推广码与历史账单/贡献值, **When** 迁移完成, **Then** 推广码与账单/贡献值归属到对应分销员，数值与迁移前一致
4. **Given** 迁移后新产生账单, **When** 系统计算贡献值, **Then** 贡献值计入分销员所属组织，并按组织树逐级向上汇总
5. **Given** 分账规则原按层级配置, **When** 适配到组织模型, **Then** 分账规则按组织层级/类型生效，新规则对新数据生效，历史数据不回溯
6. **Given** 对账报表原按拓展人层级汇总, **When** 适配到组织模型, **Then** 报表按组织维度汇总，与迁移前同口径数据一致

---

### Edge Cases

- 删除组织节点时该组织下仍有分销员或下级组织：拒绝删除并给出处理引导（见 US1-AC5）
- 组织迁移若超出后台配置的最大层级深度限制（未配置则不限制）：迁移前校验并拒绝
- 组织资质过期/被驳回时该组织下分销员已有进行中的业务：明确暂停/保留规则，历史业绩不受影响
- 组织管理员同时是分销员，其个人业绩同时出现在本组织明细与自己名下，两处数据一致
- 分销员账户停用后：无法登录，但其历史业绩继续保留在组织汇总中
- 迁移期间产生的新数据：迁移需保证原子性或明确的切换窗口，避免数据分叉或重复入账
- 迁移与已有数据的唯一性冲突（手机号、组织名称重复）：迁移前需定义冲突处理规则
- 迁移后组织结构调整时历史贡献值归属：历史贡献值保留在原组织，调整后新贡献值归入新组织
- 组织管理员查看"组织下人员"时的数据量边界：大组织（数百人）下页面应可正常加载
- 撤销组织管理员授权与小程序端数据缓存之间的同步：权限撤销后不应出现缓存残留可见
- 组织业绩视图不含客户级明细：成员贡献值不暴露客户姓名等个人信息，避免跨层可见的隐私问题

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持在后台建立组织树，包含组织节点的创建、编辑、删除、排序
- **FR-002**: 系统必须支持将组织节点连同其全部下级子树整体迁移至其他分支
- **FR-003**: 系统必须检测并拒绝形成环路的组织结构调整，给出明确错误提示
- **FR-004**: 系统必须保留组织结构每次创建、迁移、删除的操作历史（操作人、时间、变更前后）
- **FR-005**: 系统必须支持建立任意层级的通用组织树，不沿用固定"L1-L6 + 终端用户"的层级语义；组织层级深度与各层级组织类型由后台定义，组织树结构变化后贡献值逐级汇总自动适配可变深度
- **FR-006**: 系统必须支持在组织详情中维护该组织的资质文件，包括上传、替换、删除、查看历史
- **FR-007**: 系统必须跟踪组织资质的状态（审核中/已通过/已驳回/即将到期/已过期）并在有效期临近时自动提醒
- **FR-008**: 组织资质审核通过后即替代个人资质，成为该组织下分销员开展业务的准入门槛——组织资质有效期间其下分销员无需单独资质即可开展业务；组织资质被驳回或过期时，暂停该组织下分销员的业务（暂停边界：分销员可正常登录并查看历史业绩，但停止生成新推广码与参与新贡献值计算），历史业绩不受影响
- **FR-009**: 系统必须支持在每一层组织内创建分销员账户（设置登录凭证、姓名、手机号等资料）
- **FR-010**: 系统必须支持调整分销员的所属组织（调整后的业绩归属规则见 FR-019）
- **FR-011**: 系统必须支持启停用分销员账户、重置登录凭证，停用后账户无法登录
- **FR-012**: 系统必须防止同一手机号在多个组织重复创建分销员账户
- **FR-013**: 系统必须支持组织在组织内指定若干名分销员为组织管理员
- **FR-014**: 系统必须支持撤销分销员的组织管理员身份，撤销后其小程序端组织业绩权限即时失效
- **FR-015**: 系统必须让组织管理员在小程序查看其被授权组织下人员的业绩贡献情况，包括组织汇总与各分销员的贡献值（本月/累计），不展示客户级明细
- **FR-016**: 组织管理员在小程序可见其被授权组织及其全部下级组织的分销员业绩贡献（整个组织子树范围），可见数据范围严格限定在其授权组织树内
- **FR-017**: 系统必须保证组织业绩数据与个人贡献值数据来源一致，同一时段数值一致
- **FR-018**: 组织管理员身份与后台 RBAC 管理账号相互独立，后台管理权限不受组织管理员身份影响
- **FR-019**: 每个分销员同一时间仅归属一个组织，其业绩贡献计入当前所属组织；调整所属组织后新业绩计入新组织
- **FR-020**: 系统必须将现有"拓展人/层级"数据迁移到"组织/分销员"模型，迁移后历史数据完整保留且数值不变
- **FR-021**: 客户绑定关系与推广码必须迁移到分销员主体，绑定与推广的历史记录不丢失
- **FR-022**: 贡献值计算主体必须改为分销员，逐级汇总必须改为按组织树聚合，组织树结构调整后汇总自动适配
- **FR-023**: 分销员个人贡献看板、分账规则、对账报表必须适配组织/分销员模型
- **FR-024**: 系统必须提供组织管理、分销员管理、组织管理员设置等细分权限点，供后台角色独立配置与授权
- **FR-025**: 组织资质审核复用现有资质审核权限，拥有该权限的后台角色可审核组织资质；无权限角色的相关操作必须被拦截并提示
- **FR-026**: 组织管理员身份的设置与撤销仅能由具备相应后台权限的管理员执行，小程序端组织管理员不承担授权职能
- **FR-027**: 分销员账户必须支持手机号+密码登录；首次登录时必须完成微信绑定后方可正常使用功能，绑定后支持微信授权快速登录

### Key Entities *(include if feature involves data)*

- **组织 (Organization)**: 组织树的节点。含名称、父组织、层级、类型、排序、状态。取代现有"层级管理"中的层级节点，作为组织人员的归属结构骨架。
- **组织资质 (Organization Qualification)**: 挂在组织下的资质文件集合。含文件类型、文件地址、有效期、审核状态、操作历史。取代现有挂在个人（拓展人）名下的资质。
- **分销员 (Distributor)**: 组织内的人员账户。含登录凭证、姓名、手机号、所属组织、账户状态。由后台创建，取代现有"拓展人"作为业绩贡献的归属主体。
- **组织成员关系 (Org Membership)**: 分销员与组织之间唯一的归属关系（每个分销员仅归属一个组织），含其在组织内的身份（普通成员/组织管理员）。
- **组织业绩 (Org Performance)**: 按组织汇总的业绩贡献数据，由组织下分销员的贡献值聚合而成。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员在后台可在 5 分钟内完成"创建一层组织 + 新建该组织下分销员账户"的操作闭环
- **SC-002**: 组织结构创建、编辑、迁移后，5 秒内即可在组织树与组织业绩中反映
- **SC-003**: 被授权的组织管理员 100% 可在小程序看到其授权范围内组织及人员的业绩贡献
- **SC-004**: 环路调整、重复手机号、删除非空组织等非法操作 100% 被拦截并给出明确提示
- **SC-005**: 组织资质有效期临近（30 天内）的提醒 100% 发出，过期后按规则暂停对应业务
- **SC-006**: 组织业绩汇总与各分销员个人贡献值数据完全一致（同一时段核对偏差为 0）
- **SC-007**: 组织管理员无法访问其未被授权组织的任何业绩数据（越权访问全部被拒绝）
- **SC-008**: 撤销组织管理员授权后，其小程序端组织业绩入口立即消失，无缓存残留
- **SC-009**: 迁移完成后，历史数据（客户绑定、推广码、账单、贡献值）100% 保留，数值与迁移前一致
- **SC-010**: 迁移后现有功能（个人贡献看板、推广码、客户绑定、分账、对账报表）在组织/分销员模型下全部正常运行
- **SC-011**: 后台权限点按配置生效，无权限角色的组织/分销员/管理员设置操作 100% 被拦截并提示无权限

## Assumptions

- 组织树取代现有"层级管理"的层级树，作为组织人员归属与贡献值逐级汇总的结构骨架；现有层级/拓展人数据按对应关系迁移，层级结构转换为任意深度的通用组织树
- 现有功能（贡献值计算、个人贡献看板、客户绑定、推广码、分账规则、对账报表）全部迁移适配到组织/分销员模型（已确认）
- 后台权限采用细分权限点：组织管理、分销员管理、组织管理员设置按角色独立配置，原 `hierarchy:manage` 权限语义由组织管理权限取代；组织资质审核沿用资质审核权限（已确认）
- 每个分销员仅归属一个组织，业绩计入其所属组织；多组织归属不在本迭代范围（已确认）
- 组织树为任意层级通用结构，不沿用固定"L1-L6 + 终端用户"语义；层级深度与各层级组织类型由后台定义（FR-005 已确认）
- 分销员无需单独资质，组织资质审核通过即作为该组织及其下分销员开展业务的准入门槛；组织资质被驳回或过期时暂停对应业务（FR-008 已确认）
- 组织管理员在小程序可见其被授权组织及其全部下级组织（整个子树）的业绩贡献（FR-016 已确认）
- 分销员账户由后台创建，采用手机号 + 密码登录；首次登录必须绑定微信，此后可用微信授权快速登录（已确认）
- 组织资质文件沿用现有文件上传方式（云存储，仅存 URL）
- 组织资质审核沿用现有后台审核流程（上传 → 审核中 → 通过/驳回），由有审核权限的后台账号操作
- 业绩贡献沿用现有"贡献值"体系，贡献值只显示数值、不显示金额
- 组织管理员的小程序业绩视图为只读查看，不包含审批、调整等管理操作（本迭代范围）
- 组织管理员身份仅由后台管理员授权，小程序端组织管理员不承担设置/撤销管理员等管理职能（已确认）
- 小程序端通过组织管理员身份识别入口，复用现有登录与会话体系
