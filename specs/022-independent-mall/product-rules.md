# 产品规则：自营独立商城

**关联规格**：[spec.md](spec.md)  
**日期**：2026-11-04  
**用途**：为规划、交互和验收提供唯一业务口径，不定义技术实现。本文与主规格共同生效；明确用户决定优先，默认值如调整须同步修改验收。

## 1. 产品范围与责任

### B-01 决策来源

| 事项 | 来源/状态 | 本版执行边界 |
|---|---|---|
| 完整商城闭环、二八原则 | 用户明确要求 | 正常交易、异常、退款、票据和绩效均可结束或转有责任待办 |
| 排除六类功能 | 用户明确要求 | 营销/统计/客服中心、品牌/属性管理/评论不开发 |
| 商城消费计现有绩效 | 用户明确确认 | 合并基数使用现有阶梯及个人覆盖，不另设商城规则 |
| 发票 | 用户提出并已补充设计 | 首期申请、真实开具回传、查票、退款红冲与更正 |
| 小程序视觉 | 用户明确约定 | 2026-11-06已收到商品列表参考图；借鉴搜索/筛选/双列卡片层级，不显示“综合”，视觉采用暖米灰、松针绿和陶土红，详细边界见`ui-reference.md` |
| 单自营主体实物、单仓快递 | 设计默认 | 不多商户、不自提、不服务核销、不药品处方链路 |
| 运费不计绩效、30分钟支付、15天收货/售后窗口 | 设计默认 | 不称已逐项获批，可在规划复核或有权配置时调整 |
| 退款跨月差额 | 为冻结机制补齐的产品规则 | 保留原期，原规则算差额，后期审核调整，不声称当前已有实现 |

### B-02 角色与页面

| 页面 | 主要信息及动作 | 权限重点 |
|---|---|---|
| 商城工作台 | 待办数量、处理入口、今日已收/已退 | 仅本角色可处理范围，无销量排行或 BI |
| 商品列表 | 查询、草稿、编辑、复制、上下架、库存流水 | 商品编辑与库存调整可分配 |
| 商品分类 | 名称、层级、排序、启停 | 商品管理员 |
| 交易订单 | 查询、详情、发货、物流更正、内部备注、关联记录 | 查订单不代表可退款或导出 |
| 售后处理 | 审核、退货、验收、资金进度、异常 | 审核与执行资金分权，允许兼任 |
| 支付订单 | 原单、实付、退款汇总、状态、渠道核实、导出 | 财务读取/核实/导出分别授权 |
| 退款订单 | 关联支付售后、金额、进度、查证、安全重试 | 只执行有效已准售后，不修改支付事实 |
| 发票管理 | 申请、资料、领取、真实结果、红冲重开 | 财务办理，其他角色只得必要进度 |
| 配送与地址 | 发货/退货地址、快递、包邮或固定运费、禁配地区 | 有权配置，新规则只影响新交易 |
| 交易设置 | 支付、收货、售后窗口、原因、商家联系方式 | 有权管理员，变更留痕 |

商品详情内维护库存流水；订单详情内发货，不另建发货系统；原绩效页新增商城来源和调整明细，不复制现有核算页面。商家联系方式是订单基础服务，不引入客服会话系统。

### B-03 权限与资料边界

买家：本人地址、购物车、订单、售后和票据。运营：授权商品、订单和售后，不默认执行资金。发货：授权可发订单及退货验收，不默认全部消费或发票访问。财务：收退款核对、退款执行、开票、绩效调整按权限授权。组织管理员与人员：仅现有范围消费和绩效摘要。

账号管理员可给同一人多个权限；不因为人员少而跳过执行时授权。新增票据、履约权限不继承给所有运营或组织管理员。资金事实不允许人工改成成功。

## 2. 商品、地址与订单信息

### B-03A 用途告知与证据

| 目的 | 收集/处理范围 | 用户确认点 | 明确边界 |
|---|---|---|---|
| 收件 | 收件人、联系电话、地区、详细地址 | 新建商城收货地址前单独勾选 | 仅地址、订单配送及订单直接相关的履约/售后；配送必要字段提供给实际承运方 |
| 支付 | 订单金额、订单号、支付状态及必要渠道交易引用 | 结算提交前与履约用途一并展示并单独说明 | 仅支付请求、实收核对、退款及订单争议；不收集支付密码 |
| 履约 | 订单商品、收件资料、承运方、运单号、发货/送达状态 | 结算提交前与支付用途一并展示并单独说明 | 仅出库、物流查询、确认送达及售后；不用于营销画像 |
| 发票 | 发票抬头、企业税号（企业申请必填）、选填邮箱 | 申请开票及补资料前单独勾选 | 用于交易核验、真实出票、票据交付及更正/红冲；申请撤回不删除依法须留存的交易/财税记录 |

每次证据记录商城场景、告知配置版本、文案版本、有限用途scope、点击类型和服务端时间；不把姓名、地址、税号、邮箱原值复制到证据scope。收件、支付/履约、开票用途分别记录；不得将注册时同意复用为商城同意。文案目前是待业务/法务审阅的草案，版本确认不等同于接受用户协议或隐私政策。撤回开票申请只停止仍可撤回阶段的后续办理；已形成的订单快照、资金和财税事实仍按适用保留要求处理。商城用途告知与角色权限、资料访问和G-DATA原文交付门禁相互独立；任何确认均不会授权后台人员读取或领取原文。

| 对象 | 必需信息 | 校验/处理 |
|---|---|---|
| 商品草稿 | 名称可先存，其余可待补 | 草稿不前台售卖；发布时才检查完整性 |
| 发布商品 | 名称、主图、详情或说明、分类、售价、库存、配送/售后规则 | 名称1–64字；正售价精确到分；库存非负整数；主图及详情不依赖品牌 |
| 售卖规格 | 默认规格名或用户可辨选项、唯一内部编码、售价、库存 | 默认一个；多规格最多2个规格维度、20个组合，属于首期控制默认 |
| 分类 | 名称、排序、状态，可选父分类 | 最多两级、不循环；同一父级名称不重复；停用需处理在售关联 |
| 商品图片 | 主图1张，轮播最多8张 | 使用现有上传能力；用户可见替代文字，不把图片内信息作为唯一商品说明 |
| 库存调整 | 数量、原因、操作者 | 不能调减已被有效订单占用的数量造成负可售 |
| 收货地址 | 姓名、可配送地区、详细地址、可联系手机 | 首期大陆地址及手机号；完整性、格式、禁配校验，不推断业务客户身份 |
| 备注 | 买家备注、内部备注分别记录 | 默认各不超200字；内部备注不回显给用户，不含无关医疗等资料 |
| 售后申请 | 订单、明细/数量、方式、原因、补充、凭证 | 同明细一次仅一个有效处理申请；已成功数量不再重复申请；图片最多3张 |
| 企业普票 | 企业名称、税号，交付邮箱可选 | 名称不空、税号基本格式检查；格式通过不代表税务真实性认证 |
| 个人普票 | 个人抬头/姓名，交付邮箱可选 | 不强制身份证、开户行、银行卡；本期不做个人税务票夹归集 |

图片大小与具体输入上限沿用项目上传限制，规划须在契约中落实数值；本表数量上限是产品默认，不要求迁移既有内容模块。商品普通说明可以有生产信息与必要参数，但不建设公共属性字典。

### B-05 订单详情必含

订单号、买家身份、下单/支付/发货/收货时间、商品快照、数量单价小计、商品合计、运费、实付、已成功退款、退款中占用、资金净收、履约与售后状态；地址快照；快递记录；支付售后退款关联；发票进度；商城来源与归属；操作时间线。

订单详情额外明确展示应付总额、买家备注、关闭时间/原因及当前可用操作；买家详情与后台详情分契约。后台买家身份只给最小标识，内部备注及内部处理记录不进入买家详情；操作时间线按观看角色过滤，不能把敏感审计原文直接返回。缺失关联用明确null或空数组，不能省略字段令前端猜测。

不默认展示成本价、渠道技术报文、所有用户联系方式；财务原始证据仅在相应权限详情查看。对账不能依靠订单截图判断渠道收款。

### B-06 快照与归属时点

下单确定商品、价格、数量、运费与售后说明快照。支付确认确定成交时间、有效归属人员及成交组织证据。业务客户须已有有效授权绑定或经专门核实，不能用收件电话匹配。

订单创建后、支付前归属发生变化，以支付确认时有效人员为准，保留来源证据；支付后归属已定不随扫码改。无有效归属列待核实，授权补录才入人员基数，既有已归属单不提供任意调给另一人的按钮。

成交组织与核算组织分别说明：成交组织保留历史；未冻结核算继续采用当前现有引擎的人员所在组织及其管理范围。审核冻结同时记录实际核算人员、组织范围和规则，后期调整依据这些证据，而非当前组织树。

## 3. 金额、库存与状态

### B-07 金额口径

本期无商城优惠、积分或钱包抵扣。所有金额按人民币分计算，展示元，正数单价、整数数量，合计不接受客户端改写。

- 商品应付 = 各成交单价 × 对应数量之和。
- 订单应付 = 商品应付 + 一次整单运费。
- 实际收款 = 经渠道确认的成功收款。
- 成功退款 = 已成功的商品款退款 + 运费退款累计。
- 资金净收 = 实际收款 − 成功退款；处理中退款不算已退。
- 可承诺退款余额 = 实际收款 − 已成功退款 − 有效售后/退款处理中占用；同一申请从审核到执行只占一次。
- 可售后数量 = 实购 − 已成功取消购买/退货数量 − 处理中对应数量。
- 本版绩效候选金额 = 实付商品款，运费默认不计；部分退款保留全额，商品款全退归零。

资金净收不是利润，不等于渠道结算到账；可开票额与绩效基数不能互相代替。渠道支付优惠如实际发生，由财务核对用户实付、渠道补贴及票据口径，规划另明确映射，不在本期伪造商城营销功能。

### B-08 库存

| 事件 | 待付占用 | 可售/已售变化 | 唯一性要求 |
|---|---|---|---|
| 加购 | 不变 | 不变 | 购物车不是库存承诺 |
| 成功提交订单 | 增加对应量 | 可售减少 | 同次提交只占一次 |
| 确认收款 | 转出占用 | 对应量记已售，可售不再扣第二次 | 收款重复无二次变化 |
| 确认未付且渠道关单成功 | 释放 | 可售增加 | 不用本地超时直接释放 |
| 发货 | 不再占用 | 标记出库，不再次扣可售 | 一单一个有效包裹 |
| 未出库取消购买且退款成功 | 不适用 | 对取消数量恢复可售 | 审核通过不先回库 |
| 已出库商品验收可售 | 不适用 | 对实际验收数量恢复可售 | 记录验收，重复不回两次 |
| 已发货仅退款/退回破损 | 不适用 | 不恢复可售 | 退款成功不能代替验收 |

已退实物可先验收回库，资金仍处理中，两者分别留状态。有效发货前售后阻塞整单发货；部分退款终结后剩余未退商品统一一包发货。

### B-09 交易及支付状态

| 当前状态 | 事件与条件 | 结果 | 禁止行为 |
|---|---|---|---|
| 待付款 | 核实成功收款 | 待发货 | 不再未付关单 |
| 待付款 | 取消/过期，查证未付且关单成功 | 已关闭并释放占用 | 未知不能释放 |
| 待付款且渠道未知 | 查询中 | 保留业务、标记支付确认中 | 不能新建另一有效支付 |
| 待发货 | 无发货前售后，成功记录包裹 | 待收货 | 不能重复发货 |
| 待发货 | 全部商品退款且无剩余交付 | 已关闭，保留收款及退款 | 不假称未发生支付 |
| 待收货 | 用户确认或符合15天自动规则且无售后 | 已完成 | 售后中不自动完成 |
| 已发货/已完成 | 部分或全额退款 | 保留交付事实，加退款标签 | 不回退为未发货 |

支付记录保留待确认、成功、已关闭、明确失败及尝试历史。退款汇总独立为未退、处理中、部分成功退、全部成功退，不能用单个履约状态代替。先确认终态后到达的旧消息不能覆盖新事实。

### B-10 异常恢复

每次操作丢失响应，先查原业务记录；不能重做不可逆动作。渠道暂不可用保留处理中，自首次发现结果未知起持续超过10分钟进入责任待办；之后继续安全核实，不自动变失败。若已收款而业务不能履约，记录原因并由授权人员原路退款。

异常待办至少有类型、原记录、责任角色、首次发现、最后核实、当前证据和下一步；关闭须有确切结果。负责人交接有记录，不能仅靠通知已读关闭。

## 4. 售后、退货与资金退款

### R-01 受理与额度

普通用户可在未发货或有效售后窗口选择仅退款/退货退款、商品及数量，默认申请对应成交商品款；金额由原交易计算。商家原因支持发货后仅退款例外，需授权记录原因，不强制实物回库。

首期不做独立换货、价保或任意补偿转账。用户诉求超本期模式、超窗口或特殊品类条件，提供商家联系方式及后台人工受理通道，保留原记录；窗口不是权利终止声明。

运费为独立金额且只退实际收取上限：未发货整单取消与商家原因整单售后默认退原运费；用户原因部分退默认不退运费；例外由有权人员按约定调整并记录。退货寄回运费责任另向用户说明，不新增自动运费险或付款功能。

### R-02 售后状态及动作

| 阶段 | 可办动作 | 进入下一阶段的证据 |
|---|---|---|
| 待审核 | 运营通过/拒绝；用户可撤回 | 审核意见与实际人员 |
| 待用户退货 | 给退货地址，用户填写寄回运单；寄回前可联系撤回 | 运单及寄回事实 |
| 待商家收货 | 查寄回、验收；不可由用户直接撤掉资金处理 | 验收数量、结果及原因 |
| 待执行退款 | 财务确认原支付及额度 | 授权执行记录 |
| 退款处理中 | 查询原退款，不允许用户撤回 | 渠道终态证据 |
| 售后完成 | 查询历史 | 应退资金成功且实物/业务已按方式处理 |
| 已拒绝/已撤回 | 看理由、允许条件下重新申请 | 释放未实际执行的占用，有历史 |
| 争议/超时/收货异常 | 指派人工继续处理 | 证据及后续商定结果 |

仅退款通过后跳过寄回收货。已确定拒绝后可重新申请，但历史保留、数量额度再次核验。已成功数量不重复售后。售后完成不强制等红冲或绩效调整完成，但这些未决项必须分别显示。

### R-03 退款终态与占用

未提交财务执行的占用可在合法撤回/拒绝时释放。提交后结果未知仍占用，先查原退款。处理失败须区分明确未受理、已关闭、仍处理中与异常；安全重试不更换同一请求身份。原请求确定关闭且确需重开时，原记录留存并串联新请求，金额重新检查，不假设旧款一定没退。

成功退款一次性更新已退、相应业务商品数量、应否恢复库存、消费口径、票据待办。重复结果不重复修改。退款先于本地收款确认时，先核实原支付及关联关系，不把未知退款记到另一订单。

## 5. 现有绩效衔接

### P-01 合并与默认金额

按归属人员、支付所属北京时间月汇总原业务合格消费与商城候选基数，合并后使用现有阶梯；个人覆盖组织内默认，组织管理按当前引擎范围合并，不能商城分别套阶梯后相加。

原消费8,000、商城3,000，合并11,000；若示例规则为小于10,000按5%，达到10,000按8%，应为880元，而非400+150=550元。这只是验收示例规则，不改生产比例。金额四舍五入沿用现有引擎到分的算法，规划须固定临界值对照样本，不能另写一套舍入。

### P-02 部分退款与商品全退

现有口径：取消/全额退不计，部分退按原实付全额。本版商城默认不计运费，因此以商品金额判断候选基数是否完全退回，而非整单连运费都退回：

| 实付商品款 | 运费 | 累计成功商品退款 | 资金净收 | 商城绩效候选基数 |
|---|---|---|---|---|
| 200 | 10 | 0 | 210 | 200 |
| 200 | 10 | 100 | 110 | 200 |
| 200 | 10 | 200（运费未退） | 10 | 0 |
| 200 | 10 | 200且运费也退 | 0 | 0 |

以上单位元。仅退运费不改绩效。退款处理中暂不改成功退款事实，核算审核前必须提示未决资金及可能影响；本版不自动将未决退款冻结成已退款。如选择净额新规则，须另确认来源、生效期、展示和冻结影响，不能只改单一页。

### P-03 归属、时间及组织

支付前不计消费，确认收款即入支付月预估；原期按当前有效规则预估核算，审核冻结时固定规则和实际核算组织。成交人员已固定，之后客户绑定变化不挪走商城业绩。核算组织仍依现有核算时人员所属组织，成交组织快照只提供历史解释。

未归属订单继续正常买卖，授权核实人员并留依据；原月未审核则补入原月并重算，已审核走正向差额，不能直接塞到当前消费阶梯。人员无有效规则明确显示未配置且提示处理，不虚构比例。

原期因未达到首个阶梯等原因可能未生成绩效结果行。冻结时仍保存该原期计算单元的资格、规则、范围、原基数及原应得0作为证据锚点；补归属后按此锚点模拟并形成差额，不给已冻结月份补结果行。缺原期资格或规则证据转人工，不能拿后来规则直接补算；同一事件对同锚点只产生一次调整。

### P-04 冻结后差额算法

对原期间每个受影响的核算结果，固定原规则、原其他来源和原核算参与人员/组织。将本次及累计已确认的商城事实变化纳入原期模拟，只形成差额，不覆盖正式原结果。

- 原正式绩效记为 C0。
- 按原规则和最新有效商城事实模拟的应得记为 C*。
- 先前已审核调整合计记为 A（带正负号，含尚未抵扣的已确认债权）。
- 本次待审核差额 = C* − C0 − A。

一个退款影响个人阶梯和上级管理阶梯时分别形成相应结果差额，不能只扣个人。多次变化依累计公式不重复计。若缺原数据快照、原人员范围或规则证据，显示待人工核实，不能按当前比例猜算并自动确认。

### P-05 调整审核与抵扣

状态为待核实/待审核、已确认、已应用或剩余待抵扣、拒绝待重核。复用现有绩效审核权限，保留操作人、说明、原事件与原期间。未审核调整不进入已确认应发。

当期正常绩效按当期合并基数独立计算，再加已审核调整。若结果负值，应发显示0，未抵扣部分留结余，下期继续抵；同一债权已部分抵扣不得再生成另一笔全额扣回。正向补归属同样留原期关联。离职停用不删除债权，由财务记录后续人工处理，不启用钱包/自动扣银行款。

本期不改变既有积分等可能存在的权益口径；若绩效结果已转成既有权益，调整仅形成可追溯待处理，不擅自新增扣减权益能力，规划须查清原流程并给处理规则。

## 6. 发票管理

### I-01 边界与流程

标准链路：付款后申请 → 必要资料补充 → 财务领取并核对 → 在企业现有平台实际开具 → 回传真实结果 → 用户取票。用户可下单预填、付款后正式申请，不强制等收货或售后期结束；实际开具时点与税目由财务按真实经营确定。

首期普通数电票支持个人企业，专票真实诉求财务人工按能力办理；无资格不伪造开具承诺。销售方是实际自营主体，推广组织和抬头不是销售方。自动开票、合并拆分、个人票夹归集、税务申报或财税ERP不在本期。

企业普通发票须填写企业名称及税号，个人不强制无关资料，依据[上海税务发票问答](https://shanghai.chinatax.gov.cn/zcfw/rdwd/202402/t470676.html)。真实商品及金额按经营事实开具，不能用户随填内容。

### I-02 记录与状态

申请：申请号、原单、抬头类别和名称、税号、可选邮箱、交易版本、待开商品及含税金额、申请时间、领取人、补资料原因。回传：实际票据类型、销售主体、票号、开具日期、价税合计、真实文件和操作者。金额与真实申请不符进入核实，不直接交付伪称一致。

申请状态：待处理、待补充、开票中/结果待核实、已交付、合法撤回/关闭。票据状态：有效、待红冲、待对方确认、部分红冲、全部红冲。更正由原票、红票、新蓝票关联，不用一个状态丢失历史。

同单同一时点一份有效待开申请。用户重复申请返回原申请，财务重复回传同真实票据返回原记录；已领取的任务不被其他人重复领取，交接须留痕。首期一单一张标准蓝票，但全冲重开可以有多张历史票。

### I-03 金额和退款并发

未开票按剩余真实交易核对待开商品款和应由本主体开票的运费。已开有效覆盖 = 蓝字价税合计 − 对应成功红字价税合计；重开前先确认旧覆盖释放。不得将“实付减已退”直接当作还可再开一张的额度，而忽略已开有效票据。

开票执行前及结果回传均检查最新退款与资料变更。若财务已在平台出票，而用户此时退款，真实原票仍登记，随后转红冲待办；不因申请被关闭而丢掉实际出具事实。

| 退款/更正情形 | 处理 |
|---|---|
| 未开全部退款 | 关闭申请并留原因 |
| 未开部分退款 | 调整待开真实交易，提醒财务重新核对 |
| 领取后退款且是否出票未知 | 先核实原平台结果，不能直接再开 |
| 已开全部退款 | 原票关联待红冲，财务回传真实红票 |
| 已开部分退款 | 依平台规则部分冲或全冲后重开，保留金额和文件链 |
| 未开抬头错误 | 允许修正申请并记录版本，领取中先交接核实 |
| 已开抬头错误 | 更正申请、原票红冲、新蓝票关联，不能编辑原文件 |

按规定办理红字发票，具体确认环节取决于受票方用途/入账等状态，依据[税务总局红字说明](https://www.chinatax.gov.cn/chinatax/n810356/n3010387/c5236346/content.html)。商城记录待办与证据，不代替财务判断税率、资格或直接控制税务平台结果。

退款资金与票据独立：可显示退款成功但发票待红冲，持续分派财务；不把先退回电子文件或先红冲作为通用退款门槛。开票、红冲及重开不新生消费、不重复扣绩效。

### I-04 取票与交付

订单内可预览或按小程序支持方式下载本人票据；文件受权限控制，不用永久公开地址。失效允许重新交付同票文件，不重开新票。邮箱可选，首期不承诺自动邮件；人工交付记录与站内取票均保留结果，文件送达失败不修改税务开具事实。

## 7. 对账、待办与时间

### O-01 时间与查询

用户界面、统计周期及日账单统一北京时间。收款按成功时间、退款按成功时间，业务下单量按创建时间，三者不可混用。月末渠道延迟确认使用核实的实际成功时间落月；原月冻结则走调整，不能改时间塞当前月。

列表支持时间、状态及关键业务号，手机号查询需授权且输出仍脱敏。默认分页20条、时间倒序，相同时间稳定排序；翻页和返回保留筛选，不漏/重记录。首期查询范围默认最近30天，可主动扩展；长时间导出显示范围及办理状态，不能静默截断。

### O-02 人工核对闭环

财务选择自然日及成功收退款口径，拿真实渠道账单逐笔核对或录入汇总及证据；系统可记录金额与差异，但不得在未逐笔/完整对应时声称全日一致。

差异分渠道成功本地未知、本地成功缺渠道、金额不同、无关联、重复记录、费用/结算时差。状态待处理→处理中→待复核→已关闭，保留责任人与复核证据。权限兼任允许同人处理复核，但记录两动作，不新增强制多人审批。

核对关闭不修改原交易事实。费用、净收与结算到账分别展示，有据才填；发票核对与绩效差额可关联但不冒充资金退款。

### O-03 待办与处理时限默认

待发货、售后审核、商家待收退货、资金未知超过10分钟、渠道退款异常、未归属、未审核绩效调整、待开票/红冲及低库存分别计数。每个入口与实际筛选一致，已完成退出待办但保留历史。

商家服务目标默认：正常付款48小时内发货；售后申请1个工作日内受理；开票资料完整后3个工作日内处理；红冲1个工作日内领取，等待对方/外部平台时明确状态及跟进人。以上是运营默认承诺，需经营方上线前核定，不能承诺渠道到账时间。

通知只传必要业务号和状态，不含完整地址、证件或票据正文；用户从本人订单查询结果。未授权微信订阅不阻止交易，不新增营销消息。

### G-01 既有文档与新增履约需求

| 事项 | 当前证据 | 本规格处理 | 下一阶段责任 |
|---|---|---|---|

| 旧局部说明四Tab vs 当前五Tab | 小程序旧说明缺商城，当前配置已有商城 | 本轮保留当前五入口，不改历史样式 | 进入UI前统一活动文档 |
| 现有部分退款全额 vs 上版净额建议 | 当前消费规则、代码均按部分退款全额；用户要现有规则 | 采用现有全额口径，商品全退归零，资金净收另算 | 开发对比原流程，禁止暗改全系统历史 |

| 已审核绩效可能已换既有权益 | 当前核算展示存在权益记录 | 本期不直接扣已换权益或创建钱包；留人工待办和差额证据 | 规划查明已兑现范围，确定防重复抵扣契约 |

### G-02 上线输入与投产条件

上线前提供实际销售主体、开票主体及能力、准售商品清单、微信支付可用条件、发货退货地址、运费禁配规则、售后联系与处理人、资金核对账单、角色授权和可用通知方式。缺条件可保存草稿或进行隔离验收，不开放真实购买。

首发验收按500在售商品、10,000历史订单和20并发用户基线组织，另做100次末件争抢；这些是默认目标，不是当前生产实测。旧用户、客户绑定、外部账单、手工消费、文章与既有绩效作为回归边界，不借此迭代重构。
