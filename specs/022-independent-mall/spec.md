# Feature Specification: 自营独立商城完整闭环

**Feature Branch**: `022-independent-mall`  
**Created**: 2026-11-04  
**Status**: Implementation in progress — 产品规格已成稿；商品浏览与详情视觉已实现，其它商城页面继续按任务推进
**Input**: 根据本轮商城分析产出可执行、高标准产品文档。排除营销中心、统计中心、客服中心、商品品牌、公共商品属性管理、商品评论；商城消费计入现有绩效考核规则；纳入发票闭环；遵循二八原则；进入小程序 UI 设计前提醒用户提供风格参考图。

本规格定义用户和业务需要得到的结果，不包含技术选型、实现任务或视觉稿。商品、订单、资金、绩效及发票须可相互核对。配套文档：[业务规则](product-rules.md)、[验收场景与需求对应](acceptance.md)、[独立质量检查表](checklists/requirements.md)。

已确认：商城接入现有账号、权限及绩效，完成收款、交付、售后与发票链路，排除范围不以改名重新加入。单商户实物、单仓快递、人工开票回传及具体期限属于本版明确默认值，详见 Assumptions。P1/P2 表示交付优先级，九个故事均属于首期范围。

本规格定义小程序页面用途、必要信息、操作和状态，不定义具体视觉稿。2026-11-06用户已提供商品列表参考图并授权自行确定风格；商品列表/详情的设计边界见[参考图记录](ui-reference.md)，不以历史示意页替代真实商品数据。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 运营上架真实可售商品 (Priority: P1)

运营无需配置品牌、属性库或营销活动，即可发布有价格、库存和配送售后说明的商品。

**Why this priority**: 准确的货品与库存是交易前提。

**Independent Test**: 创建一个分类和两件商品，分别验证有货、售罄、补货及下架，不依赖真实支付。

**Acceptance Scenarios**:

1. **Given** 商品名称、主图、正售价、库存及配送规则有效，**When** 发布，**Then** 用户可检索和分类浏览，不要求品牌、公共属性或评论。
2. **Given** 缺少必填信息，**When** 发布，**Then** 指出缺失项并保留输入，不产生半发布状态。
3. **Given** 已有历史订单，**When** 商品改价或下架，**Then** 只改变新交易可售条件，历史快照及已付履约不变。
4. **Given** 在售商品库存为零，**When** 购买或补货，**Then** 售罄时不能下单，补货按原上架状态恢复；原本下架的不自动上架。

---

### User Story 2 - 普通用户选购、下单并完成支付 (Priority: P1)

用户通过购物车或立即购买核对商品、地址和金额，完成微信支付；无需医生、组织或推广身份。

**Why this priority**: 构成商城交易及消费业绩的来源。

**Independent Test**: 普通用户购买两种商品，核对一次运费、唯一订单及支付；另验证重复提交、末件争抢与支付结果未知。

**Acceptance Scenarios**:

1. **Given** 访客选购，**When** 提交订单，**Then** 引导登录并保留选购意图，不要求先建立业务客户归属。
2. **Given** 两种商品一起结算，**When** 确认，**Then** 展示明细、数量、商品金额、整单运费及总额；价格、库存或配送变化须重新确认。
3. **Given** 同次提交重试或多人争抢末件，**When** 处理，**Then** 原请求只产生一单，库存不超占，同一订单最多一个有效付款请求。
4. **Given** 用户退出或客户端返回付款结果，**When** 查询，**Then** 以渠道核实结果确认收款；未知显示确认中，重复通知不重复入账。
5. **Given** 付款与取消并发，**When** 核实，**Then** 已收款订单不按未付取消释放库存，不能履约的进入退款处理。
6. **Given** 商品设置了有效主图，**When** 买家查看购物车，**Then** 显示商品主图；主图缺失或加载失败时保留图片占位。

---

### User Story 3 - 商家发货、用户收货 (Priority: P1)

发货人员处理已付款且无发货前售后阻塞的订单，用户查包裹和确认收货。

**Why this priority**: 收款后必须完成交付。

**Independent Test**: 对已付款订单发货、改正运单、确认收货，另验证未付款及售后中的禁止发货。

**Acceptance Scenarios**:

1. **Given** 符合发货条件，**When** 提交公司及运单，**Then** 形成一个包裹并进入待收货，记录操作者和时间。
2. **Given** 未付款、已关闭或发货前售后处理中，**When** 发货，**Then** 拒绝操作且不改变库存。
3. **Given** 运单录错，**When** 授权更正，**Then** 保存原因及前后值，不触发第二次出库。
4. **Given** 待收货订单，**When** 用户确认或满足自动收货规则，**Then** 完成订单；未决售后阻止自动收货，完成后仍可按规则申请售后。

---

### User Story 4 - 售后、退货与原路退款 (Priority: P1)

用户按商品和数量申请仅退款或退货退款，运营审核、仓库验收、财务执行，各阶段可查询。

**Why this priority**: 金额、实物与售后承诺需同时闭环。

**Independent Test**: 完成发货前整单退款、部分商品退款、退货退款，再验证重复申请及退款未知。

**Acceptance Scenarios**:

1. **Given** 可售后订单，**When** 申请，**Then** 明确方式、商品数量、商品退款、运费、原因和凭证；处理中及成功数量金额不得重复申请。
2. **Given** 未发货有效申请，**When** 审核，**Then** 发货暂停；拒绝或合法撤回后恢复，通过不等于退款成功。
3. **Given** 退货退款通过，**When** 寄回并验收，**Then** 可售实物回库，损坏或缺件进入人工处理，退款不自动等于库存恢复。
4. **Given** 渠道受理、超时或异常，**When** 查询或重试，**Then** 未确认成功不显示已退款，同一请求不重复退钱。
5. **Given** 退款成功，**When** 查看各关联记录，**Then** 业务、资金、库存、绩效和发票分别按规则处理，未完成部分有待办。

---

### User Story 5 - 商城消费计入现有绩效 (Priority: P1)

商城消费与原消费按同一人员、同月合并，再使用现有阶梯、个人覆盖、组织管理和月度审核冻结机制。

**Why this priority**: 用户明确要求，不能另算一套商城提成。

**Independent Test**: 原消费8,000元与商城3,000元按11,000元合并命中阶梯，验证个人覆盖、部分退款、全额退款及跨月调整。

**Acceptance Scenarios**:

1. **Given** 同人同月两种消费，**When** 预估与核算，**Then** 先合并再套现有阶梯，个人覆盖优先级及组织管理方式不变，来源可追溯。
2. **Given** 商品款部分退款，**When** 核算，**Then** 沿用现有全额计入；累计商品款全部退回才归零，资金净收始终反映真实退款。
3. **Given** 原月未冻结且基数变化，**When** 重算，**Then** 对合并基数重算；原月冻结后以关联原规则的差额调整处理，不覆盖历史。
4. **Given** 无有效归属，**When** 支付，**Then** 正常履约并进入待归属，不随意计给人员；补归属按原支付期间及冻结状态处理。
5. **Given** 调整重复到达或当期不足扣回，**When** 审核，**Then** 不重复扣回，负差额分列并保留待抵扣结余，不执行账户扣款。

---

### User Story 6 - 申请发票并下载票据 (Priority: P1)

用户从已付款订单提交开票申请；后台工作人员在现有税务平台人工开具，只需将票据PDF上传到该申请并确认，金额由申请记录带入；商城记录经办人与文件并让用户查看、下载。普通开票不要求后台重复录入PDF内已有的票号、日期和销售主体。系统不调用税务平台查验真伪。退款后的红冲、更正与重开由财务作为异常事项处理，不成为普通申请的主要操作流程。

**Why this priority**: 已纳入本期的票据链路不能只收申请而无后续。

**Independent Test**: 用户提交申请，后台收到待办，工作人员上传PDF并确认，用户看到完成状态并安全下载；用合成票据验证文件访问和买家隔离。无需执行税务平台真伪查询；另验证必要资料补充和退款/更正例外留痕。

**Acceptance Scenarios**:

1. **Given** 已付款订单，**When** 个人或企业申请普票，**Then** 只收必要资料，企业有名称税号；不要求个人提供无关身份证或银行信息。
2. **Given** 后台收到用户申请，**When** 工作人员上传PDF并确认，**Then** 商城用申请金额登记PDF、留存操作者并标记可下载；普通流程不要求手填票号、日期和销售主体，系统不连接税务平台验证真伪，仍须校验订单/申请关联、退款版本、PDF完整性及买家访问权限。
3. **Given** 申请或回传重复，**When** 办理，**Then** 不重复占用金额或产生重复有效票；结果未知先核实。
4. **Given** 开票前退款、开票与退款并发，**When** 财务办理，**Then** 核对实际是否出票，再调整申请或转红冲。
5. **Given** 已开票退款或资料错误，**When** 红冲重开，**Then** 记录完整关联链，退款和票据状态分别显示，红冲不再次扣绩效。

---

### User Story 7 - 财务核对收退款与关闭差异 (Priority: P1)

财务关联订单与资金，按实际发生日核对渠道账单，指派、处理、复核差异。

**Why this priority**: 真实经营必须能对账并发现漏单。

**Independent Test**: 核对含收款、成功退款、渠道成功本地未知及费用的日账单，完成差异复核。

**Acceptance Scenarios**:

1. **Given** 原订单，**When** 查资金，**Then** 能互查支付、售后、退款和渠道身份，不靠人工拼接编号。
2. **Given** 账单不同，**When** 核对，**Then** 差异有类型、金额、责任、证据及进度，不手工改支付成功。
3. **Given** 差异解决，**When** 关闭，**Then** 有复核一致证据；净收、费用、到账、发票及绩效基数不混用。

---

### User Story 8 - 各角色在授权范围操作 (Priority: P1)

买家只访问本人业务，后台按岗位权限办理，组织管理权限不隐含全商城访问权。

**Why this priority**: 延续现有身份与隐私边界。

**Independent Test**: 两名买家、运营、发货、财务、组织管理员交叉访问及操作，核对拒绝与审计。

**Acceptance Scenarios**:

1. **Given** 他人订单或票据编号，**When** 买家读取、操作或下载，**Then** 拒绝且不泄露内容。
2. **Given** 无资金执行权的运营，**When** 执行退款，**Then** 拒绝；有授权财务按有效售后操作。
3. **Given** 组织管理员，**When** 查询或导出绩效，**Then** 只得现有授权范围摘要，不取得完整收件和票据资料。
4. **Given** 权限撤销或账号停用，**When** 再次操作，**Then** 执行时拒绝，历史仍可由授权后台处理。

---

### User Story 9 - 工作台推动未完成业务 (Priority: P2)

人员通过待办处理待发货、售后、资金、归属、绩效调整、开票红冲和低库存，不建设统计中心。

**Why this priority**: 用必要待办支持日常运营，不增加分析平台。

**Independent Test**: 构造每类待办，确认数量、跳转、处理后消失及历史可查。

**Acceptance Scenarios**:

1. **Given** 权限范围内有未完成记录，**When** 点击待办，**Then** 筛选记录与数量一致。
2. **Given** 无记录或读取失败，**When** 展示，**Then** 明确区分无待办与失败重试，不将错误显示为零。
3. **Given** 未授权微信订阅，**When** 业务变化，**Then** 站内进度仍可查，通知失败不回退交易。

### Edge Cases

- 末件争抢；重复提交；付款与关单并发；客户端失败而渠道成功；退款先于本地支付结果。
- 购物车商品变价、失效、缺货；地址跨不可配送地区；已付款后商品、用户或分类被停用。
- 发货与售后同时办理；部分商品退款；同一商品多次数量申请；退款处理中重复申请；运费独立保留。
- 退货超时、错误运单、缺件、拒收、损坏；无退货仅退款；未决售后遇自动收货。
- 月末付款、跨月退款、已冻结、人员转组织、个人规则变更、缺规则、原规则证据缺失、离职及不足扣回。
- 无归属后补归属；部分退后累计退完商品款但未退运费；同一事件在资金、绩效与票据链重复到达。
- 开票未知实际成功；退款先于票据回传；部分红冲、全冲重开、重开再次错误、受票方确认未完成。
- 文件链接失效、越权下载、导出时权限变化、数据空与读取失败、支付不可用、消息未送达。

## Requirements *(mandatory)*

### Functional Requirements

#### 范围、用户与入口

- **FR-001**: MUST 提供商品、购买、支付、履约、售后、退款、对账、发票及现有绩效闭环，复用现有身份权限。
- **FR-002**: MUST 排除营销、统计、客服中心及品牌、公共属性管理、商品评论，不以改名加入。
- **FR-003**: MUST 限单自营主体、人民币、微信支付、单仓；实物商品走快递一单一包裹，虚拟商品由后台人工交付；不做多商户、钱包、积分、活动、自提、拆包或独立分销。虚拟商品与实物商品必须分单。
- **FR-004**: MAY 开放访客浏览；下单、地址、订单、售后及发票 MUST 关联有效用户，不要求组织或推广身份。
- **FR-005**: MUST 区分买家、收货人、开票抬头和绩效归属，不以手机号、地址或抬头自动绑定客户。
- **FR-006**: MUST 保留现有五个主入口；购物车放商城内，订单及发票从我的和订单访问。
- **FR-007**: MUST 提供业务规则中的十个后台页面，账号、组织及绩效入口沿用现有系统。
- **FR-008**: MUST 区分医院同步、手工消费、商城来源，不以诊费或药费承载商城履约及票据。

#### 商品与库存

- **FR-009**: MUST 支持商品草稿、编辑、排序、上下架及保留交易关联的归档，发布校验见业务规则。
- **FR-010**: MUST 支持分类名称、排序、启停，仅支持一级分类，不能设置父分类；有在售商品的分类停用前迁移商品或下架。
- **FR-011**: MUST 有名称、图片、简介详情、真实说明、正售价、库存、预警及配送售后规则，不强制品牌、划线价或成本。
- **FR-012**: MUST 默认单规格；MAY 商品内维护少量购买规格，各自价格库存独立，不建设公共属性库。
- **FR-013**: MUST 区分可售、待付占用、已售；下单占用、收款转已售、确认关单释放、验收入库留痕，库存不为负。
- **FR-014**: MUST 记录补货盘点的前后值、数量、原因、操作者，不用覆盖库存掩盖交易占用。
- **FR-015**: MUST 区分售罄与下架；补货不自动上架已下架商品，下架不取消旧交易权利。
- **FR-016**: MUST 保存商品类型、配送方式、规格、单价、数量及规则成交快照；实物订单保存地址快照，虚拟订单不要求地址；后续修改不改历史。
- **FR-017**: MUST 真实检索分类，正确展示售罄、价格及配送，不以示意数据冒充结果。

#### 购物车与下单

- **FR-018**: MUST 支持加购、数量、移除、勾选及失效提示，并在购物车显示商品主图；购物车不占库存和入业绩，立即购买使用相同结算规则；订单创建成功后移除本次已购商品，未勾选商品保留。
- **FR-019**: MUST 支持收件人、联系电话、地区、详细地址及默认地址，订单取独立地址快照。
- **FR-020**: MUST 展示明细、商品合计、应付及备注；实物订单另展示地址和整单运费，虚拟订单免地址、免运费；人民币金额精确到分，不接受用户改应付金额。
- **FR-021**: MUST 提交时校验商品价格、数量、库存及配送；影响交易的变化需用户重新确认，失败保留选择。
- **FR-022**: MUST 同次提交重试返回原结果，不重复订单、库存或收款请求，明确新交易才另下单。
- **FR-023**: MUST 支持整单包邮或固定运费；每个运费模板独立配置不配送地区，按订单所选模板合并校验并保存规则快照，不做重量体积模板或满额营销。
- **FR-024**: MUST 核实未付并关闭有效付款请求后才关闭业务订单、释放库存，未知不可当未付；有效订单允许继续付款。
- **FR-025**: MUST 禁止未付发货、已付直接改商品数量金额；发货前改地址留痕且重验配送，不支持需补差价的地址变更。

#### 支付

- **FR-026**: MUST 订单关联支付及尝试历史，同一时点最多一个可支付请求，继续付优先使用原有效请求。
- **FR-027**: MUST 以核实渠道结果确认收款，匹配订单、主体、金额和币种，不凭客户端提示、截图或人工备注确认。
- **FR-028**: MUST 对未知显示确认中并持续核实，不诱导重建请求重复付款。
- **FR-029**: MUST 收款只推进一次待发货、已售和消费入账，重复乱序不重复处理或回退终态。
- **FR-030**: MUST 区分用户取消支付界面、支付失败和业务关单，仍有效的业务订单可继续付。
- **FR-031**: MUST 已收款无法履约进入异常及退款，不丢收款或无库存出库。
- **FR-032**: MUST 支付列表展示订单号、支付单、买家、金额、成功退款汇总、状态及时间，渠道身份置详情。
- **FR-033**: MUST 授权查询渠道、导出及核实记录，不提供人工改已支付。
- **FR-034**: MUST 收款状态与退款汇总分开，资金净收为成功收款减成功退款，不抹历史收款。
- **FR-035**: MUST 支付不可用显示真实提示及原交易查询入口，恢复后可安全续办。

#### 履约

- **FR-036**: MUST 按订单、状态、时间及授权条件查询，履约与售后分列，关联资金、物流、发票、绩效和操作记录；详情提供应付总额、关键时间、备注和角色可见时间线，买家响应不得包含内部备注。
- **FR-037**: MUST 已收款、有效待发货、无发货前售后阻塞才发货，记录快递、运单、唯一包裹及出库事实。
- **FR-038**: MUST 限履约最小范围使用收件资料，查看交付导出授权审计；规划处理与统一脱敏的适配，不开放既有客户原文资料。
- **FR-039**: MUST 接入用户已开通的快递100，由后端按订单权限、可信包裹和供应商频率提供真实轨迹/状态；缓存更新时间、无记录和异常分别提示。预计到达与地图轨迹按`resultv2=7`返回的预测路线呈现，预计信息标为参考；地图轨迹在小程序独立 web-view 页面展示，`src`只能是本项目自有已备案域名上的 HTTPS 页面（该页面以内嵌 iframe 方式加载快递100地图页；用户服务器无 nginx 权限，采用静态包装页方案），由后端仅向本人订单返回该地址；地址中的快递100令牌不得写入日志、审计或普通错误信息，未配置包装页源时生产环境不返回地图地址；不下发未代理的`trailUrl`或派件员资料。发货地和收货地只发送省/市/区县名称；承运商明确要求核验时，仅在本订单有效履约同意包含`recipient_contact`时发送收件人电话，且不记录、不回传、不写日志。轨迹签收不等于买家确认收货。
- **FR-040**: MUST 运单更正验证权限并记录原因及前后值，不重复出库。
- **FR-041**: MUST 支持用户与规则收货，未决售后阻止自动收货，完成后仍能按规则售后。
- **FR-042**: MUST 发货与售后互斥校验；先实际发货的后续申请按已发货处理，不误回库存。

#### 售后与退款

- **FR-043**: MUST 支持按商品数量的仅退款、退货退款和理由凭证；超窗口诉求可人工处理，下架不剥夺历史权利。
- **FR-044**: MUST 数量金额扣除成功及有效处理中占用，同一件同一分钱不并发承诺两次。
- **FR-045**: MUST 商品退款与运费分列，数量不超实购、金额不超实付；运费处理有场景依据。
- **FR-046**: MUST 申请审核执行沿用一次额度占用；拒绝、合法撤回、明确关闭才按阶段释放，未知不释放。
- **FR-047**: MUST 支持通过拒绝、允许阶段撤回、退货物流收货验收；拒绝或异常有理由与继续人工处理入口。
- **FR-048**: MUST 发货前有效申请暂停发货；退款成功后仅剩余内容履约，未出库成功退款商品回库一次。
- **FR-049**: MUST 已发货实物按验收决定入库，不因退钱自动回库存，仅退款无退货不回库。
- **FR-050**: MUST 审核通过与资金执行分离，有权财务按有效售后原路退款，不向任意指定账户转款。
- **FR-051**: MUST 退款记录含原单、售后、原支付、金额、状态、时间和异常，互相可查。
- **FR-052**: MUST 受理与成功分开；未知先查原请求，安全重试使用原退款身份，不因超时新退一笔。
- **FR-053**: MUST 核实退款且防重复，只有成功金额入已退汇总，异常失败关闭进入待处理，不覆盖成功事实。
- **FR-054**: MUST 退货超时、拒收、争议转人工留记录，不静默销毁申请或取消已受理退款。
- **FR-055**: MUST 售后完成满足业务与资金终态；票据、绩效未完成分列待办，不把到账等同全链完成。

#### 绩效

- **FR-056**: MUST 商城商品消费并入原业绩，按支付成功北京时间月份计入，不另建商城阶梯。
- **FR-057**: MUST 同人同月先合并来源再命中阶梯，保留个人覆盖优先级及组织管理方式，跨页面一致。
- **FR-058**: MUST 分清资金、运费与绩效基数，本版默认商品实付计入、运费不计，记录为设计默认值而非用户单独确认。
- **FR-059**: MUST 沿用部分退款全额计入；保留商品实付则基数不按部分退款减，累计商品款全退则归零，即使仍保留运费。
- **FR-060**: MUST 支付记录有效客户、人员归属及成交组织快照，后续扫码、收件电话或抬头不改变已定人员。
- **FR-061**: MUST 无归属进入待办，核实后按原支付期间处理；原月未冻结可重算，已冻结走调整，不记错月份。
- **FR-062**: MUST 核算组织沿用现有核算时人员组织及管理范围，成交组织快照是历史证据；不因商城改变人员迁移策略，冻结结果不改。
- **FR-063**: MUST 沿用预估、月核算、审核冻结与规则快照；无规则显示未配置，未确认不得显示已确认。
- **FR-064**: MUST 原月未冻结基数变化提示重算；冻结后以原期间证据和规则形成差额，独立审核，不覆盖原结果；原期未生成结果行仍须有原期计算证据身份，证据不足转人工，不补改冻结结果集合。
- **FR-065**: MUST 调整考虑个人及管理绩效的阶梯变化，不用退款乘本月比例；按原期应得与已处理差额防重复扣回。
- **FR-066**: MUST 调整与当期正常绩效分列，不把负消费混入当期阶梯；不足扣回留结余，不自动转账或扣账户款。
- **FR-067**: MUST 支付退款、来源和调整可追溯；开票红冲重开不新生业绩或重复扣回，存量及冻结历史不因商城上线重算。

#### 发票

- **FR-068**: MUST 已付订单可申请、补充、查进度及本人取票，预填不是已开，不强制等收货或售后期结束才允许提出申请。
- **FR-069**: MUST 支持个人企业普票，企业名税号必需；不强制个人身份证银行信息；真实专票诉求由财务依能力办理。
- **FR-070**: MUST 按真实交易确定内容数量及含税金额，不任填虚构；运费开票按实际业务财务确认，不按绩效运费规则决定。
- **FR-071**: MUST 同单同刻一个有效待开申请，已开有效额度不重复覆盖；不做合并拆分申请，保留合法红冲重开历史。
- **FR-072**: MUST 工作人员在现有税务渠道办理后，上传PDF并确认；普通流程不要求重复录入PDF已有的票号、日期和销售主体，价税合计按申请记录登记；商城不连接税务平台查验真伪或生成票据。
- **FR-073**: MUST 回传时检查最新交易及退款版本；如申请版本变化或退款并发则保留工作人员提交记录并转人工异常处理，防止重复开票或错误标记普通申请完成；不把税务平台真伪查询设为下载前置条件。
- **FR-074**: MUST 未开退款调整金额、全退关闭申请，已开退款关联原票创建红冲处理，不直接删除改写原票。
- **FR-075**: MUST 已开更正保留原因及红冲重开关联，部分冲或全冲重开按财务真实办理记录。
- **FR-076**: MUST 分开申请和票据状态，表达待补充、开具未知、待对方确认、部分全额红冲和重开，退钱成功不等于红冲完成。
- **FR-077**: MUST 订单与权限校验后预览下载导出，不永久公开；失效文件可补交而不重新开票。
- **FR-078**: MUST 有发票管理页及订单入口，工作台含待开红冲，金额差异与回传变更留审计。
- **FR-079**: MUST 销售主体与财务确定真实税目税率及开具时点，不硬编码全店税率；自动开票和票夹归集不在首期。

#### 对账、待办与权限

- **FR-080**: MUST 收款按成功时间、退款按退款成功时间，以北京时间自然日核对，待付及处理中不入成功金额。
- **FR-081**: MUST 可依真实渠道账单人工核对，记录范围、金额证据和差异，无证据不标一致。
- **FR-082**: MUST 差异分类、指派、处理、复核及关闭，未知收款、长时退款、无法履约及未关联资金有责任待办。
- **FR-083**: MUST 分清收退款、净收、费用、到账、开票及绩效，缺费用数据不伪造估算，不把净收当利润。
- **FR-084**: MUST 工作台各待办在权限范围计数，入口与筛选一致，含履约、售后、资金、归属、绩效调整、票据及低库存。
- **FR-085**: MUST 关键变化站内可查；订阅通知依授权及平台条件启用，通知失败不回退交易。
- **FR-086**: MUST 商品、库存、发货、售后审核、退款执行、资金导出、发票、归属及绩效调整分权限，可兼任，不默认多级审批。
- **FR-087**: MUST 用户仅访问本人业务，组织人员仅现有授权绩效摘要，不扩大为全部订单地址或票据。
- **FR-088**: MUST 执行时重验账号、权限及业务状态，停用不删除历史，授权后台仍可完成遗留业务。
- **FR-089**: MUST 敏感访问变更留操作者、时间、对象、原因及必要前后值；日志报错不含凭证或完整敏感资料。
- **FR-090**: MUST 定义加载、空、失败、无权限、登录失效、操作中及未知状态，失败保留安全可重试输入。
- **FR-091**: MUST 仅凭确认事实展示金额状态与成功提示；响应丢失查原结果，不重做不可逆动作。
- **FR-092**: MUST 开放购买前核验主体、真实品类、支付、配送退货地址、票据能力和权限，不满足只保留草稿。
- **FR-093**: MUST 进入小程序视觉设计或页面实现前提醒并等待本轮用户风格参考图与确认，产品文档不提前选风格出视觉稿。
- **FR-094**: MUST 保持原登录、绑定、医院同步、手工消费、内容、绩效及冻结历史可用，口径变化单独明确生效边界。

### Key Entities *(include if feature involves data)*

- **商品/售卖规格、分类**：真实说明、价格、上下架、有限分类及独立规格库存；不是公共属性体系。
- **购物车/地址簿**：选购意图、收件资料，不等于订单、付款或业务客户绑定。
- **订单/明细**：购买用户、商品及地址规则快照、商品款、运费、支付时间、履约状态及关联记录。
- **库存变动/包裹**：占用、已售、释放、补货、验收入库与唯一首期包裹及更正事实。
- **支付/退款记录**：原订单、渠道身份、金额、核实结果与时间、异常证据，不等于售后审核。
- **售后/明细**：原因凭证、商品数量及商品运费退款、审核、退货验收、真实退款关联。
- **绩效来源/核算/调整**：客户人员归属、成交组织证据、支付期间、规则快照、基数及差额和抵扣结余。
- **开票申请/票据**：抬头、主体、真实蓝票红票重开链、金额、开具及交付结果。
- **核对批次/差异**：自然日、账单证据、金额、处理人、复核与关闭。
- **操作记录/通知**：可追溯业务证据及进度，不替代交易事实。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 九故事、禁止动作及配套验收全部通过；超退、超卖、重复消费、重复有效票和越权成功数均为0。
- **SC-002**: 5名已登录且备好地址的验收用户至少4名，在稳定网络3分钟内完成选购至提交支付；外部支付等待另记。
- **SC-003**: 约定首期样本及稳定网络下，95%商品、订单和资金查询在2秒内呈现可用结果；外部等待明确显示，不伪报成功。
- **SC-004**: 100次并发末件争抢最多1次有效占用，关单释放、售出及退货入库数量差异为0。
- **SC-005**: 同一收款、退款、发货和入账各重复20次并乱序，金额库存各只变化一次，关联同一事实。
- **SC-006**: 可靠核实收退款结果后60秒内前后台及待办一致；超过10分钟仍未知的渠道结果生成责任异常。
- **SC-007**: 同人员组织月份的消费、预估、核算和导出误差0分，合并阶梯、个人覆盖及管理绩效符合验收手算。
- **SC-008**: 冻结月份因规则、组织或退款变化导致原结果改动为0；差额覆盖受影响结果，重复扣回0次。
- **SC-009**: 已交付票据真实号码、金额、文件及原单完整率100%；退款及更正样本票据链100%可查，不重复影响绩效。
- **SC-010**: 样本日收退款全可对应渠道；差异均有分类责任及复核，未关联记录不得标核对完成。
- **SC-011**: 交叉买家、角色越权、跨组织及私有文件访问拒绝率100%，敏感操作审计覆盖100%。
- **SC-012**: UI 视觉设计开始前有本轮用户参考图及确认；缺失时视觉稿及页面实现产出为0，不阻断非视觉规格与规划。

以上是后续验收目标，不代表本轮已跑通交易、性能或真机。

## Assumptions

### 已确认及设计默认的区别

- **C-01**：二八范围及排除项、商城消费计入现有规则、发票闭环、UI 前等参考图来自本轮用户要求。
- **A-01**：单自营主体实物、人民币微信支付、单仓快递、一单一包裹。真实商品与资质上线前核验，示意商品不等于准售清单。
- **A-02**：支付有效30分钟；发货后15天且无未决售后自动收货；确认收货后15天保留标准售后入口。均为可配置设计默认，不据此排除法定或已承诺权利；超窗口人工处理。
- **A-03**：启用前明确包邮或固定运费、不可配送地区；未配置不得发布。运费默认不计绩效，是新增金额边界默认，不称用户已单独确认。
- **A-04**：未发货及商家原因整单退款退对应商品款与原运费；用户原因部分退默认不退原运费，有权人员按实际约定调整留理由，不超原付。
- **A-05**：售后审核和退款执行分权限动作，允许兼任连续办理；不增加多层审批、阈值或自动打款。
- **A-06**：服务端确认支付计入支付月预估；沿用现有核算时组织策略。订单人员固定，原月冻结后调整分列，不以负消费冲当期阶梯。
- **A-07**：首期个人企业普票人工开具回传；专票依能力人工处理，不把交还电子票或红冲完成作为通用退款门槛。
- **A-08**：首期不做自动面单、自动轨迹承诺、自动开票、自动账单核对；但真实运单、票据及对账证据必须可记录。
- **A-09**：验收样本基线500在售商品、10,000历史订单、20名同时操作用户；是规划基线，不是生产负载或容量实测。
- **A-10**：首期不物理删除交易票据，审计沿用长期保留制度；实际开票税目税率及留存制度由经营财务确定。

以下是规划阶段核对源码后，为满足本规格所必须覆盖的衔接，不改变94条需求的编号或用户已确认规则：

- 员工在商城后台登记本地包裹及运单即完成发货登记，不存在另在微信小程序后台录入发货信息的步骤，也不对接微信发货API。快递100轨迹、本地出库、买家确认收货与资金结算分别记录。更正运单后旧轨迹快照失效；本地发货登记不代表买家确认收货或资金结算。
