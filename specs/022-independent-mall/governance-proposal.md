# 商城履约及开票必要资料交付：批准范围与运行门禁

**日期**：2026-11-09

**状态**：2026-11-09 用户批准内部单订单履约及单申请开票两类原文访问，宪章IV已升至4.0.0；T063/T102后端实现及契约回归已完成，订单/发票管理页已接入受权限控制的短时领取交互。前端构建通过；此次页面变更未运行前端交互回归。`VITE_MALL_DATA_RELEASE_UI_ENABLED`默认false。生产运行仍关闭，等待留存制度引用、经业务/法务审阅的告知版本和60秒页面清除行为验收。未传输真实资料；向微信、承运商或快递100传输仍未授权。

**关联**：[主规格FR-038、FR-086–089](spec.md)、[规划宪章检查](plan.md)。

## 原规则与冲突

现行[项目宪章IV](../../.specify/memory/constitution.md)要求：

> backend API responses and frontend UI displays MUST only expose masked values

该规则适用于手机号等敏感信息。商城实际发货需要购买人主动提供的姓名、联系电话与地址供履约使用，普通脱敏电话无法填有效快递单；财务实际开具企业发票也需要用户主动提供的完整抬头、税号，不能只拿脱敏税号办理。当前代码未发现已存在、可直接复用且获该规则允许的商城资料交付机制；已有医院对接不是商城例外。

## 已批准的窄范围

1. 仅涉及买家为该订单主动提交的收件资料，以及为该开票申请主动提交的抬头税号。不读取原业务客户身份证、医疗信息或其他客户原文。
2. 普通订单、地址簿、客户、组织、票据列表继续脱敏；无通用“查看原手机号”“导出全部地址”接口。
3. 履约权限仅对指定已付款、未出库且无退款阻塞订单，发起目的为填面单/交付承运商的领取；财务开票权限仅对指定本人领取的有效开票申请，领取开票必需的完整抬头税号。两类动作不同权限，不能互相替代。
4. 提交必须带用途、订单版本、幂等键；访问时实时校验账号、权限与状态，记录管理员身份、订单、目的、时间及结果，不把原文写审计。
5. 技术方案为独立短时订单级交付动作；若首期人工填单需原文显示，仅一次短时显示，不批量公开、不缓存普通响应、不写日志；打印或交给承运商须有业务告知与目的记录。
6. 如后续选定承运商直连，以服务器限定目标交付替代人工原文显示，但仍须按该目的记录，不自动认为免于规范。
7. 小程序隐私与同意记录新增商城收件、支付、履约与票据处理的准确说明及版本；不把一般隐私同意扩充为营销或医疗资料共享。
8. 始终保留拒绝、撤权、并发退款以及访问失败的审计；原文交付权限不授予所有运营或组织管理员。

## 逐项资料边界（批准范围）

| 目的 | 最少字段 | 可访问者及对象 | 允许条件 | 当前不包含 |
|---|---|---|---|---|
| 手工填写指定订单的物流面单 | 该订单快照中的收件人姓名、电话、地区和地址 | 当前具有`mall.fulfillment.release`的在职后台账号；一次只对应一个商城订单 | 订单已确认收款、尚未本地出库/关闭；无取消、退款或售后阻塞；订单上关联的商城履约用途告知仍为已确认、有效且scope匹配 | 批量地址、订单簿查询、未付款/已关闭/已出库订单、原业务客户资料、向承运商或快递100的自动传输 |
| 为指定申请办理真实发票 | 该申请的发票抬头、企业税号；税号仅企业抬头 | 当前具有`mall.billing.release`的在职财务账号；一次只对应一个买家本人开票申请 | 申请仍可办理且由当前财务人员领取；关联商城发票用途告知仍为已确认、有效且scope匹配 | 面向所有订单的抬头/税号查询、批量导出、营销或绩效用途、默认显示邮箱。若开票渠道确需邮箱，须另行确认必要性和对应告知范围 |
| 物流轨迹查询 | 承运商代码、运单号 | 服务端向快递100发起限定查询 | 现有查询目的和账户条件满足 | 买家电话不在本次授权内。只有取得当前官方字段要求、证明其为必要字段并另行获批后，才能考虑传输 |

以上条件以读取时的数据库状态和当前权限为准，不信任JWT里的旧权限快照；对订单/申请、用户、告知记录和用途scope必须逐项关联核验。读不到任一必要事实即拒绝。

## 已采用的实现控制

1. 履约与开票使用分离端点和权限；每次访问重新核验后台账号状态、当前角色权限、目标状态与版本、订单/申请关联、支付事实及有效用途告知。已确认告知不等于授予管理员权限。
2. 两个响应使用`Cache-Control: no-store, private, max-age=0`，并设置`Pragma: no-cache`及`Expires: 0`；商城后台幂等中间件不缓存/重放结果。响应只含允许字段、审计ID和60秒`expiresAt`；接入页面必须在60秒到期时清空，不持久化原文、不埋点、不写错误跟踪或应用日志。每次重新显示都重新鉴权并生成一条审计事件。
3. 只审计后台账号ID、目标订单/申请ID、目的码、预期/实际版本、事件键哈希、留存引用、告知版本、时间及允许/拒绝结果；不存字段值、自由文本原因、请求/响应正文。拒绝结果统一返回，不回显对象资料。
4. 已撤回/失效的用途告知、被撤销的角色、订单状态变化或申请已关闭都会阻止后续领取。已经交给承运商或已办理的票据无法由系统撤回；保留必要交易事实与访问元数据，按已批准的留存制度处理。
5. 这一提案只覆盖商城后台的单对象人工访问。本项目没有微信平台发货环节，员工在商城后台登记本地包裹及运单即完成发货，不由商城后端调用微信发货API，也不在微信小程序后台录入发货信息。该范围不授权本商城后端自动向微信或承运商传输收件原文；2026-11-11用户仅授权向快递100发送地图轨迹所需的省/市/区县名称，不发送姓名、电话或详细地址。未来若新增外部接收方或字段，须另核对官方字段、接收方、目的和必要字段，并满足G-LIVE及适用的数据治理要求。

## 启用运行开关前仍需落实

- 仓库没有记录订单收件快照、税号及敏感访问审计对应的现行留存制度编号。用户已批准沿用现有制度；运维仍需把真实制度引用配置到`MALL_DATA_RELEASE_RETENTION_POLICY_REF`。实现不猜留存年限、不另建原文副本、不延长已有保留。
- `mall_consent_service.py`中的商城用途告知目前标注为草案。业务/法务完成文案审阅后，运维再配置经审阅的版本到`MALL_DATA_RELEASE_NOTICE_APPROVED_VERSION`；在此之前，访问服务即使部署也因引用为空而拒绝。
- 宪章IV窄例外已按治理流程批准并升至4.0.0，Sync Impact Report记录于项目宪章。其批准不代表生产开关已开启。

## 用户批准记录

2026-11-09 用户批准以上两种商城内部单对象访问：履约人员查看一笔符合条件订单的收件资料；财务人员查看一笔由本人领取、仍可办理的开票申请抬头及企业税号。每次访问按当前权限、对象状态和有效用途告知重验，响应不缓存，审计不保存原文。外部承运商、微信、快递100的数据传输不在本次审批范围。

批准沿用现有留存制度，但具体制度引用和告知审阅版本尚未配置，所以生产运行开关继续关闭。T063/T102实现与合成数据专用验收已完成；配置正式引用前不能显示或访问真实原文。

## 生效规则摘要

保留宪章IV的默认全渠道脱敏原则，仅新增如下内部、单对象访问例外：

> 对买家为指定商城订单主动提供的收件资料，可在履约必要时，允许有当前履约权限的后台处理人员按订单单独访问；对买家为指定开票申请主动提供的发票抬头及企业税号，可在办理该申请必要时，允许有当前开票权限的财务人员按申请单独访问。每次访问须重新验证账号、权限、对象状态、版本和仍有效的对应商城用途告知，采用不缓存、不记录原文的响应，并以不含原文的审计元数据记录结果。其它接口和界面保持脱敏；不得提供通用查询、批量导出、原业务客户证件/医疗资料访问。向外部承运商、微信或快递100传输不由本例外自动授权，须按已核实的接收方字段另行审查和授权。

该规则已纳入宪章4.0.0，并已更新接口契约、权限校验和测试。运行时依旧要求已审阅告知版本及适用留存制度引用。

## 实施门禁

- 可继续实施不涉及原文交付的分类、商品、脱敏查询、订单、资金测试和私有文件基础。
- T063/T102仅允许已批准的两个内部端点；运行开关默认false，需同时配置现有留存制度引用和经审阅告知版本。
- 不得扩大到通用查询、批量导出、原业务客户信息，或因内部批准而向微信、承运商、快递100发送原文。外部传输仍需独立协议核验和授权。
- 当前真实个人数据访问、真实面单/开票流程及生产开关均未验收或启用。


### 快递100目的补充

查询尽量只提供公司、运单与必要行政区；可使用已验证寄件校验信息时不传买家电话。确有承运商校验要求时，仅在规范适配与目的告知落实后传其可接受的最小校验值，不能认为“已开通服务”授权发送所有客户原文。本次审批不改变该边界。
