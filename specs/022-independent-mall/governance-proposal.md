# 商城履约及开票必要资料交付：规范适配提案

**日期**：2026-11-04  
**状态**：供审阅的提案，尚未修改现行宪章、未开放权限、未传输真实资料。  
**关联**：[主规格FR-038、FR-086–089](spec.md)、[规划宪章检查](plan.md)。

## 原规则与冲突

现行[项目宪章IV](../../.specify/memory/constitution.md)要求：

> backend API responses and frontend UI displays MUST only expose masked values

该规则适用于手机号等敏感信息。商城实际发货需要购买人主动提供的姓名、联系电话与地址供履约使用，普通脱敏电话无法填有效快递单；财务实际开具企业发票也需要用户主动提供的完整抬头、税号，不能只拿脱敏税号办理。当前代码未发现已存在、可直接复用且获该规则允许的商城资料交付机制；已有医院对接不是商城例外。

## 拟采用的窄范围

1. 仅涉及买家为该订单主动提交的收件资料，以及为该开票申请主动提交的抬头税号。不读取原业务客户身份证、医疗信息或其他客户原文。
2. 普通订单、地址簿、客户、组织、票据列表继续脱敏；无通用“查看原手机号”“导出全部地址”接口。
3. 履约权限仅对指定已付款、未出库且无退款阻塞订单，发起目的为填面单/交付承运商的领取；财务开票权限仅对指定本人领取的有效开票申请，领取开票必需的完整抬头税号。两类动作不同权限，不能互相替代。
4. 提交必须带用途、订单版本、幂等键；访问时实时校验账号、权限与状态，记录管理员身份、订单、目的、时间及结果，不把原文写审计。
5. 技术方案为独立短时订单级交付动作；若首期人工填单需原文显示，仅一次短时显示，不批量公开、不缓存普通响应、不写日志；打印或交给承运商须有业务告知与目的记录。
6. 如后续选定承运商直连，以服务器限定目标交付替代人工原文显示，但仍须按该目的记录，不自动认为免于规范。
7. 小程序隐私与同意记录新增商城收件、支付、履约与票据处理的准确说明及版本；不把一般隐私同意扩充为营销或医疗资料共享。
8. 始终保留拒绝、撤权、并发退款以及访问失败的审计；原文交付权限不授予所有运营或组织管理员。

## 拟修订文本（未生效）

保留宪章IV的默认全渠道脱敏原则，仅新增：

> 对购买人为指定商城订单主动提供的收件信息及指定开票申请主动提供的抬头税号，可在对应履约或开票必要、明示用途、实时授权与完整访问审计的约束下，允许按订单/申请最小交付给经确认的履约处理人员、承运商、履约所需物流查询服务商（如快递100）或办理该申请的财务。该例外不适用于通用查询、批量导出、原客户证件或医疗资料。默认界面和所有其他响应仍须脱敏，不得持久公开或进入普通日志。

正式采纳时依宪章治理流程记录Sync Impact Report及版本，评估受影响契约、隐私文案、同意证据、测试和权限配置。当前不推定已获采纳，也不改写历史宪章。

## 实施门禁

- 可继续实施不涉及原文交付的分类、商品、脱敏查询、订单、资金测试和私有文件基础。
- 订单资料及开票必要信息领取契约作为条件性设计保留；正式规则适配与相应隐私告知/权限未落实前，该动作必须关闭，不能进入真实履约投产。
- 不能因测试环境、管理员身份或用户本次说“下一步”就认为已批准扩大生产资料可见范围。
- 本提案让待审事项具体可审阅，不要求现在为完成实施规划提前开通承运商或发送资料。


### 快递100目的补充

查询尽量只提供公司、运单与必要行政区；可使用已验证寄件校验信息时不传买家电话。确有承运商校验要求时，仅在规范适配与目的告知落实后传其可接受的最小校验值，不能认为“已开通服务”授权发送所有客户原文。该补充仍是提案，不改变现宪章或实际权限。
