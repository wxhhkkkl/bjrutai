# 商城发布、灰度与回退运行手册（T134）

更新：2026-11-09。状态：**T134文档任务已完成；T133及真实发布条件未完成；未执行任何部署或生产操作**。

本手册只描述具备正式条件后的操作顺序。当前 [T133发布准备](release-readiness.md) 未完成，销售主体、准售清单、经营承诺和真实平台能力仍缺证据；T131未通过G-LIVE。G-DATA内部范围已由宪章4.0.0采纳并完成T063/T102本地回归，但生产访问仍需留存制度引用及经审阅告知版本，第三方原文传输仍未获授权。G-PROTOCOL及官方协议已采纳/核验，T048本地回调实现与隔离回归已完成；T132已按用户确认完成真机验收，具体设备和逐人原始记录未归档。因此本手册不是开售许可、平台授权或生产变更批准。

## 1. 运行时闸门与安全基线

后端购买校验同时要求运行配置 `MALL_ENABLED=true`、`MALL_PURCHASE_ENABLED=true`，以及数据库单例 `mall_settings.enabled=true`、`mall_settings.purchase_enabled=true`。任一关闭时，结算配置应报告 `purchasingAvailable=false`，新建订单必须拒绝。只关闭购买不代表关闭本人订单、售后、退款和已受理工作项。

支付/退款出站、商城worker、快递100、商城文件存储是独立开关：`MALL_GATEWAY_MODE`、`MALL_GATEWAY_OUTBOUND_ENABLED`、`MALL_WORKER_ENABLED`、`MALL_KUAIDI100_MODE`、`MALL_KUAIDI100_OUTBOUND_ENABLED`、`MALL_STORAGE_OUTBOUND_ENABLED`。关闭购买不会自动取消已排队付款工作；关闭外部出站会暂停对应处理器，须先评估待处理/未知资金并安排人工核对。不得把“暂停worker”当作安全回退的默认动作，因为它也会暂停订单恢复、退款、通知和其它已接受任务。

仓库当前默认配置保持商城/新购关闭、支付test、支付出站关闭、worker关闭、快递100 fake且出站关闭、存储出站关闭。各环境必须独立核对；环境变量不得从开发机复制到生产，不得在本文件、工单或日志记录秘密。

## 2. 变更准入清单

任何生产迁移或开放新购前，由变更负责人确认并留存：

- [ ] T133完成，逐项经营、税务、平台及治理证据已核实；G-LIVE、G-DATA、G-PROTOCOL及适用G-UI条件均已解除或有经正式批准的适用结论。
- [ ] 真实销售/开票主体、逐项准售SKU和资质、仓/退地址、配送与禁配规则、服务承诺及责任人已由经营/财务确认。
- [ ] 微信商户/小程序关系、支付与退款能力、快递100权益、税务流程、私有对象存储策略，均有环境对应且脱敏的核验记录。本项目没有微信平台发货环节。
- [x] T132真机验收完成（用户2026-11-10确认）；详细设备/五人计时记录未归档。故事级未完成事项已明确负责人、影响和是否为发布阻塞。
- [ ] 变更单记录版本/镜像摘要、目标环境、窗口、执行人、复核人、回退负责人、观察时长、告警阈值和业务联系人。告警阈值没有依据时先确定并演练，不使用本手册临时臆定数值。
- [ ] 数据库备份与恢复演练证据有效，备份覆盖交易表、商城配置、持久任务、文件引用和审计；确认恢复方案不会覆盖备份后新增的真实资金/履约事实。
- [ ] 针对目标数据库核实当前Alembic版本、唯一head、DDL影响/锁表窗口、空间和连接余量；仅凭本地测试记录不推断生产当前版本。

上述任一项未完成，保持购买和真实出站关闭，只可做经批准的隔离环境验证。

## 3. 迁移与兼容部署

### 3.1 迁移前

1. 确认变更目标确为本次批准的商城环境和数据库；使用只读检查获取当前Alembic版本及仓库heads，并检查目标连接的环境标识。发现多head、版本未知、漂移、生产自动建表开启或目标不符即停止。
2. 当前仓库记录的迁移head为`036`，但每次发布须以该版本实际代码和目标库为准，不硬编码假设数据库已到`036`。已知商城迁移从既有版本逐步扩展；T129隔离MySQL证据不是生产迁移证据。
3. 验证最近备份可恢复到隔离环境，并记录恢复点；如果无法证明恢复路径，停止迁移。
4. 复核迁移脚本实际DDL及锁/回填影响。保持expand-first和兼容旧接口字段语义；生产只允许向前升级，不运行`create_all`，不采用模型自动建表。

### 3.2 向前迁移

在正式变更窗口，由获准的数据库执行人使用该环境已核验的连接运行Alembic向前升级（示意命令；本项目本轮未运行）：

```sh
cd backend
.venv/bin/alembic current
.venv/bin/alembic heads
# 仅在目标、备份、DDL评审和变更批准全部复核通过后执行：
.venv/bin/alembic upgrade head
```

升级后再次核对当前版本、预期表/列/索引、约束、错误日志和旧业务关键查询。保持新购关闭。迁移异常时停止后续步骤，保留数据库现状、完整日志和备份点，由数据库负责人制定前向修复；禁止线上`downgrade`、drop新表、删资金历史或用全量ORM建表覆盖迁移。

### 3.3 应用部署与隔离验收

1. 先部署已审阅的兼容版本，商城和新购两层开关均为关闭；支付/退款仍为test且出站关闭，快递100为fake且出站关闭，COS出站关闭。核对启动日志没有输出密钥、地址原文、税号或票据内容。
2. 使用健康检查时注意当前`/health`还会探测既有Rutai API（除非该环境显式mock）；未获准访问该外部服务时，不把此端点当成本地只读检查。使用已批准的部署平台就绪检查、数据库只读检查及本地日志核对。
3. 在隔离环境跑本版本定向验收：购买关闭校验、订单及支付未知恢复、退款/售后、绩效来源、发票状态、私有文件权限、工作台权限、任务租约恢复和旧系统回归。仅用合成账号、订单、票据及文件。
4. 验证购买双层闸门均关闭时，`GET /api/v1/mall/checkout/settings`的`purchasingAvailable`为false，订单创建被拒；本人读取既有订单、售后与授权内恢复路径仍按规则工作。真实环境验证须由相应环境负责人批准。

## 4. 灰度与新购开放

当前配置是全局开关，未据此证明已有按用户/组织的灰度名单或百分比分流能力。若发布要求分批买家放量，必须先实现并验收明确的分流机制；不得把全局开关称作“灰度”。

全部准入清单满足后，按此顺序操作并每步等待既定观察窗口：

1. 先启用仅浏览所需的商城展示配置，但保持`MALL_PURCHASE_ENABLED=false`及数据库`purchase_enabled=false`；核对目录、价格/库存、类目、搜索、配送/售后说明与真实准售清单一致。
2. 用批准的小范围机制验证访问权限、下单前置条件、运费/禁配、开票提示、隐私用途告知、工作台权限和告警。若没有受控分流机制，此步只做隔离环境，不在生产向公众开放购买。
3. 支付、退款、快递100、COS和worker分别按T131记录、账户能力和明确授权启用；每种外部操作单独复核，避免一次性打开全部出站开关。真实通知还须先满足G-PROTOCOL，个人资料交付还须先满足G-DATA。
4. 经营负责人确认准售、库存、客服与履约值守，财务确认收退款/开票/日账责任人，值班人员可访问工作台和应急联系人。
5. 最后才通过受审的商城设置动作，将运行配置和数据库的购买开关成对开放。数据库配置更新须使用预期版本号，避免并发覆盖；不直接绕过版本校验改表。
6. 验证一次经批准的端到端场景及其唯一支付/订单/消费/售后/票据关联，再按批准范围扩大。支付真实资金请求、退款、快递资料传输和税票办理各自仍须有清楚对象、环境和范围授权。

## 5. 发布观察与队列监控

每个观察周期对照发布前基线和获批阈值，至少检查以下三层；任何计数读取失败应标为“未知/不可观测”，不能报零。

| 层 | 检查项 | 处理原则 |
|---|---|---|
| API/数据库 | 应用就绪、错误率/延迟、数据库连通、连接池和迁移日志 | 不将含Rutai外部探测的综合`/health`误作本地独立检查；异常先暂停扩量 |
| 商业待办 | 工作台的待发货、待售后、待收退货、超10分钟支付未知、退款异常/未知、未归属绩效、待审核调整、待开票/红冲、低库存 | 按权限由对应责任人领取；支付/退款未知先查原渠道身份，不能新建另一请求；对账差异保持开放直到复核 |
| 持久worker | `mall_jobs`按`kind`和`status`的ready/retry/running/manual数量、最老创建时间、到期未运行任务、过期running租约、attempts及`last_error_code`分布 | `manual`和过期租约要进入人工核实；不能只靠worker进程存活或将失败计数清零 |

数据库队列监测只用获批只读账号和聚合字段；不要读取或导出`dedupe_key`、`notification_payload`、买家资料、票据内容或原始支付报文。手工重试必须通过对应的幂等业务动作，先核实原订单/支付/退款事实；禁止直接改`mall_jobs`状态或清除任务。

订单资金未知的工作台门槛当前为10分钟；worker失败在达到实现的尝试上限后转`manual`，其余任务会按退避延后。这些是系统行为，不替代业务负责人设定更严格的值班SLO。生产上线前须为队列年龄、manual数量、超期资金、退款异常、对账差异和业务响应时间明确责任人/告警渠道/升级时间。

至少每个观察周期记录：新增/成功/失败订单数、支付及退款未知/异常、待处理和最老任务年龄、过期租约、人工任务、库存异常、开票/红冲待办、对账差异、告警响应与处置人。只使用汇总值和内部实体号，不将个人资料放入通用监控平台。

## 6. 关停新购与回退

### 6.1 先停新交易

遇到重复下单/库存不一致、资金事实不明、越权/隐私泄露、重大积压超过批准SLO、错误商品/价格或关键数据迁移异常时，值班负责人应：

1. 通过已授权的版本化设置动作关闭数据库`purchase_enabled`；同时在配置管理中关闭运行时`MALL_PURCHASE_ENABLED`并按服务变更流程使API进程加载新配置。必要时同时关闭数据库`enabled`及运行时`MALL_ENABLED`以隐藏商城入口；仅关闭购买是更窄的默认动作。
2. 核对结算设置回报不可购买、下单请求拒绝，并从独立会话重复确认两个层级均关闭。已创建订单、原订单查询、售后申请/进度和既有资金恢复按权限保留。
3. 判断是否还需暂停新的渠道出站。如果发生正在重复扣款/错误第三方传输等风险，负责人可按专项应急流程关闭对应的支付/退款、快递100或COS出站开关；记录因此暂停的未知付款、退款、物流和文件任务，分派人工核对。不能删除或重新创建同一业务请求。
4. 只有明确故障来自worker且隔离单种处理器无法做到时，才暂停`MALL_WORKER_ENABLED`；必须安排对已受理的支付查询、关单、退款、售后、通知和私有文件任务的恢复负责人及恢复时点。恢复前逐笔核对未知资金状态。

### 6.2 修复方式与数据保留

- 首选前向修复或部署经验证的兼容修复版本；只有证明旧应用理解当前数据结构、状态和任务时，才考虑回退应用镜像。只增迁移并不自动证明所有旧版本兼容新数据。
- 不对已写入新商城交易的生产库执行Alembic降级，不drop商城表，不重置或删除任务/通知/审计/订单/支付/退款/消费/绩效/发票/文件事实。
- 备份恢复可能覆盖备份后产生的有效交易。若确需恢复，须另有事件处置审批、资金/库存/票据/绩效差异盘点及逐笔补偿计划；恢复结束前不得打开新购。
- 关闭新购不会撤回已授权支付或退款请求，也不表示渠道已关单。每笔未知结果按原商户单号/退款单号查证；不得换号重试、重复退款或伪造成功事实。
- 留存故障时间线、配置版本、迁移版本、部署摘要、聚合队列变化、决定人和复核人。日志中不记密钥、完整回调、收件电话/地址、税号或票据正文。

### 6.3 恢复开放

问题修复并回归后重新执行第2节准入与第3节隔离验收；业务责任人逐笔确认资金、库存、售后、绩效、发票和日账一致。尚有未查明交易、超期人工任务、迁移版本不明或治理门禁未解除时，保持新购关闭。恢复必须形成新的变更记录，不以自动重启或过期配置回滚代替批准。
