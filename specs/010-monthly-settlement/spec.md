# Feature Specification: 绩效计算模块月度核算（未核算月份选择 + 数据报表展示 + 审核冻结/打回）

**Feature Branch**: `010-monthly-settlement`  
**Created**: 2026-08-07  
**Status**: Draft  
**Input**: User description: "绩效计算模块要有月度核算功能，选定没有核算过的月份；如果核算成功后结果展示在数据报表菜单内，核算结果需要审核，审核后不能进行再次更改，审核不通过可以打回再次核算；"

## Clarifications

### Session 2026-08-07

- Q: 核算结果报表记录何时在「数据报表」可见？→ A: 核算成功即生成报表记录并可见（含「待审核」状态标记）；审核通过后成为最终数据
- Q: 用户可见文案的术语统一用「核算」还是「汇算」？→ A: 统一为「核算」；需求文档同步改为「核算」术语（本需求原称「汇算」）
- Q: 「数据报表」菜单中核算结果记录的查看权限？→ A: 查看核算报表记录需 `sharing_rules.read`（与 008 绩效页查看估算同权）；审核/打回/重算仍用 `performance.settle`

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 月度核算：选定未核算月份并发起核算 (Priority: P1)

管理员进入「绩效计算」页面，通过**月份选择器**选定**没有核算过的月份**（已冻结/已确认的月份不可选），发起**月度核算**。系统按当前生效的绩效规则对该月的业务数据计算提成结果。核算成功后，该月进入**待审核**状态。

**Why this priority**: 月度核算是本需求的核心动作——只有选定未核算月份并发起核算，后续的数据报表展示与审核才有数据基础，属 P1。

**Independent Test**: 进入绩效计算页 → 打开月份选择器 → 仅看到未核算（或已打回待重算）的月份 → 选定某月发起核算 → 提示核算成功、该月状态变为待审核 → 再次打开月份选择器，该月不再可选定。

**Acceptance Scenarios**:

1. **Given** 管理员进入绩效计算页, **When** 打开月份选择器, **Then** 仅展示未核算过的月份，已审核冻结/已确认的月份不可选
2. **Given** 选定某未核算月份, **When** 发起核算, **Then** 按当前绩效规则计算该月提成并提示核算成功
3. **Given** 某月核算成功（待审核）, **When** 再次打开月份选择器, **Then** 该月不再出现在可核算月份列表中
4. **Given** 某月审核被打回, **When** 打开月份选择器, **Then** 该月可再次被选定并发起重新核算
5. **Given** 未来月份, **When** 打开月份选择器, **Then** 未来月份不可选定（无业务数据）

---

### User Story 2 - 数据报表展示：核算成功的结果进入数据报表菜单 (Priority: P1)

**核算成功后，系统立即自动为该月生成一条核算报表记录，展示在「数据报表」菜单的历史报表列表内，并带「待审核」状态标记**。管理员在数据报表中可查看各已核算月份的绩效结果（汇总与人员明细），并可查看明细与导出表格文件，数据与核算结果一致。审核通过后，该记录成为最终数据（状态变更为已确认/冻结）；若打回，记录随之体现打回状态。

**Why this priority**: 核算结果的业务出口是数据报表——管理员在统一报表入口查看月度绩效汇总，是本需求「核算→展示」的结果落地，属 P1。

**Independent Test**: 某月核算成功后 → 打开数据报表菜单 → 能看到该月的核算结果 → 查看汇总与明细 → 导出表格 → 数据与核算结果一致。

**Acceptance Scenarios**:

1. **Given** 某月核算成功, **When** 打开数据报表菜单, **Then** 能看到该月的核算结果记录
2. **Given** 数据报表中的核算结果, **When** 查看, **Then** 展示该月绩效汇总与人员提成明细，数据与核算结果一致
3. **Given** 数据报表中的核算结果, **When** 导出, **Then** 得到包含该月核算明细的表格文件
4. **Given** 某月未核算, **When** 打开数据报表菜单, **Then** 不展示该月的核算结果
5. **Given** 管理员仅具备 `sharing_rules.read` 而无 `performance.settle`, **When** 查看核算结果记录, **Then** 可查看；尝试审核/打回/重算被拒绝

---

### User Story 3 - 审核与冻结：核算结果需审核，通过后不可更改，不通过可打回重算 (Priority: P1)

核算结果需要**审核**。审核**通过**后该月数据**冻结**——不能再进行任何更改（不能再次核算覆盖数值）。审核**不通过**可**打回**（记录原因），打回后该月回到**可重新核算**状态，重新核算后再进入待审核。

**Why this priority**: 审核—冻结—打回闭环是核算结果可信、稳定的保障，直接决定数据报表中的月度数据是否可作为最终口径，属 P1。

**Independent Test**: 某月核算成功（待审核）→ 管理员审核通过 → 该月冻结，再次核算被拒绝、数值不变 → 对另一月审核不通过（打回）→ 该月可重新核算 → 重新核算后再次进入待审核。

**Acceptance Scenarios**:

1. **Given** 某月处于待审核状态, **When** 管理员审核, **Then** 可选择审核通过或打回
2. **Given** 审核通过后, **When** 再次对冻结月份发起核算, **Then** 系统拒绝，该月数值保持不变
3. **Given** 审核通过后, **When** 尝试更改该月数据, **Then** 系统不允许（不能进行再次更改）
4. **Given** 审核不通过, **When** 管理员发起打回, **Then** 记录打回原因，该月回到可重新核算状态
5. **Given** 某月被打回, **When** 重新核算完成, **Then** 该月再次进入待审核状态，可再次审核

---

### Edge Cases

- 已冻结/已确认月份：不得出现在可核算月份列表中，任何更改均被拒绝
- 待审核月份：已在核算流程中，不再作为可核算月份重复选定（除非打回）
- 自动核算（月度任务）产生的待审核月份：不列入可核算月份选择器，通过「月度核算状态列表」进入审核
- 打回后的月份：可重新选定并发起重新核算，重新核算后再进入待审核
- 未来月份：无业务数据，不可选定
- 组织未配置绩效规则：相关人员无提成部分（沿用既有「未配置」提示）
- 当月无业务数据：核算结果为空态或为 0
- 核算中数据变化（如退款/新账单）：以核算当刻的数据快照为准；冻结后不受影响
- 重复审核/重复打回：同一月份幂等处理，不允许重复确认
- 多根组织森林：每个根组织独立参与核算与报表展示

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供月度核算功能，管理员能选定未核算过的月份并发起核算
- **FR-002**: 月份选择器必须仅列出可核算月份（无核算记录 / 已打回待重算的月份），待审核与已审核冻结/已确认的月份不可选
- **FR-003**: 核算必须按当前生效绩效规则对该月业务数据计算提成，结果包含人员级提成明细与月度汇总
- **FR-004**: 核算成功后该月必须进入「待审核」状态
- **FR-005**: 核算成功后，系统必须立即自动为该月生成一条核算报表记录，展示在「数据报表」菜单的历史报表列表中，并带「待审核」状态标记（可查看、可导出）；审核通过后状态变为已确认/冻结（最终数据），打回后体现打回状态
- **FR-006**: 数据报表中展示的核算结果必须包含月度汇总与人员明细，数据与核算结果一致（同源、偏差为 0）
- **FR-007**: 核算结果必须支持审核：审核通过 → 该月冻结（不可再更改）；审核不通过 → 打回并记录原因
- **FR-008**: 已审核冻结的月份，系统必须拒绝再次核算覆盖其数值
- **FR-009**: 打回后该月必须回到可重新核算状态，重新核算后再次进入待审核
- **FR-010**: 核算结果必须记录审核人、审核时间；打回必须记录原因
- **FR-011**: 审核/打回/重新核算操作必须受权限控制（沿用绩效计算审核权限点 `performance.settle`）；查看「数据报表」中的核算结果记录必须受 `sharing_rules.read` 控制（与 008 绩效页查看估算同权）
- **FR-012**: 数据报表中的核算结果必须支持导出表格文件

### Key Entities *(include if feature involves data)*

- **核算批次 (Settlement)**: 月度核算的整体单元。含周期（月份）、状态（待审核/已冻结/已打回）、审核人、审核时间、打回原因。
- **核算明细 (Commission Result)**: 每人在某月的提成明细。含人员、所属组织、提成类型、计算基数、命中比例、提成金额、规则快照、计算时间。
- **数据报表 (Report)**: 数据报表菜单中的核算结果记录，含月度汇总与人员明细，可查看与导出。
- **已核算月份集合 (Settled Periods)**: 已冻结/已确认的月份集合，用于限定可核算月份的选择范围。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 月份选择器仅列出未核算/可重算的月份，已冻结月份 100% 不可选
- **SC-002**: 核算结果与按当前绩效规则手算结果一致（核对偏差为 0）
- **SC-003**: 核算成功后 100% 可在数据报表菜单查看到该月结果
- **SC-004**: 审核通过后该月 100% 冻结，再次核算被拒绝、数值不变
- **SC-005**: 打回后 100% 可重新核算，重新核算后回到待审核状态
- **SC-006**: 数据报表展示的核算结果与核算数据 100% 一致（偏差为 0）
- **SC-007**: 核算成功到数据报表可见耗时在 2 秒以内
- **SC-008**: 核算/审核/打回操作 100% 留痕（操作人、时间、打回原因）

## Assumptions

- 核算**复用并增强**既有月度核算/审核机制（008 的 `performance_settlements` 状态机：待审核 → 已冻结 / 已打回 → 待审核）；本迭代聚焦「未核算月份选择」与「数据报表展示」两项增强（已确认：复用增强，非全新实现，非全面更名）
- 核算按当前生效绩效规则计算提成（与 008 同口径）；业绩/基数口径为消费金额（009）
- 审核/打回/重算权限沿用既有绩效计算审核权限点（`performance.settle`）；查看「数据报表」核算结果记录沿用 `sharing_rules.read`（已确认）
- 月份选择范围为既有数据所在月份（含当前月），未来月份不可选定
- 冻结机制：已审核确认的月份不得重算/更改，与 008 一致
- 数据报表展示形式：核算成功后**自动生成该月核算报表记录**，出现在数据报表历史列表，可查看明细与导出（已确认）
- 导出格式为表格文件（CSV/Excel），具体格式在计划阶段确定
- 本迭代不涉及小程序端（小程序绩效展示沿用 008 既有能力）
