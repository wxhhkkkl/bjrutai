# Feature Specification: 文章评论与评论管理

**Feature Branch**: `020-article-comments`  
**Created**: 2026-09-21  
**Status**: Ready for planning  
**Input**: 为小程序文章详情增加评论、点赞/取消点赞和内容审查；为管理后台增加评论删除、下架、置顶管理。

## Context

现有 `014-article-reading` 只覆盖已发布文章的列表、详情和转发，明确不包含评论、点赞。本功能在不改变现有文章发布与公开阅读规则的前提下，增加文章下方的互动区，并通过后台审核能力保证评论内容合规。

## Confirmed Product Decisions

- 评论区必须登录后才可查看；发表评论和点赞同样必须登录。
- 评论采用“先审后发”：通过本地审查规则后公开，命中风险进入待人工审核，不绕过审查直接展示。
- 不接入第三方内容审查服务；审查在后端本地执行，至少覆盖色情、暴力、政治规则。
- 普通用户、客户顾问、组织管理员均可参与评论；后台管理员是否能以小程序身份评论不单独开放。
- 评论只支持纯文本和文字表情，不支持链接、图片、语音或评论回复；单条最多 500 字，每分钟最多提交 3 条。
- 评论显示微信昵称和头像，不显示手机号、身份证号或内部用户编号。
- 下架可恢复，删除采用软删除并保留审计记录；每篇文章最多置顶 1 条评论。
- 新增后台权限 `comments.read` / `comments.write`；被删除评论正文、审查原始结果和业务处置记录保留 7 天，正常评论按文章业务生命周期保留，安全审计日志继续遵循系统既有合规保留规则。

## User Scenarios & Testing

### User Story 1 - 浏览并发表评论 (Priority: P1)

用户阅读已发布文章时，可以查看该文章下的可见评论；完成登录后可以提交评论，提交内容必须经过内容审查。

**Why this priority**: 评论是本功能的核心互动入口，且必须先建立安全的发表与展示边界。

**Independent Test**: 用一个已发布文章和两个登录用户，验证评论列表、成功提交、空状态、审核中状态、违规拦截和网络失败重试。

**Acceptance Scenarios**:

1. **Given** 文章已发布且用户已登录，且存在可见评论，**When** 用户打开文章详情，**Then** 评论区按约定顺序显示评论内容、显示名、发表时间、点赞数和当前用户点赞状态。
2. **Given** 用户已登录且输入有效评论，**When** 点击发表评论，**Then** 系统提交评论并显示明确的审核结果；评论只有在允许展示的状态下才出现在公开列表中。
3. **Given** 用户未登录，**When** 打开文章详情，**Then** 评论内容和评论输入区均不可见，并提示完成小程序登录后查看和参与互动。
4. **Given** 用户已登录但文章没有可见评论，**When** 评论列表请求成功，**Then** 显示空状态和发表评论入口，不显示错误占位。

### User Story 2 - 点赞和取消点赞 (Priority: P1)

用户可以对可见评论点赞，也可以再次点击取消点赞；同一用户对同一评论最多保持一个有效点赞。

**Why this priority**: 点赞是评论区最小成本的反馈方式，且必须避免重复计数。

**Independent Test**: 使用同一用户连续点击同一评论，并用第二个用户验证点赞数和各自的点赞状态相互独立。

**Acceptance Scenarios**:

1. **Given** 评论可见且用户未点赞，**When** 用户点击点赞，**Then** 点赞状态变为已点赞，服务端点赞数增加一次。
2. **Given** 评论已被当前用户点赞，**When** 用户再次点击，**Then** 点赞状态变为未点赞，服务端点赞数减少一次且不会低于零。
3. **Given** 点赞请求超时或失败，**When** 请求结束，**Then** 页面不会永久保留未经服务端确认的状态，并提供重试反馈。
4. **Given** 评论被下架、删除或文章不再发布，**When** 用户提交点赞，**Then** 服务端拒绝该操作，客户端刷新评论状态并不泄露隐藏内容。

### User Story 3 - 后台管理评论 (Priority: P1)

具有评论管理权限的后台管理员可以按文章、状态和关键词查看评论，并对评论执行删除、下架、恢复和置顶操作。

**Why this priority**: 评论安全和运营控制必须有可追溯的后台入口，不能只依赖前台自动审查。

**Independent Test**: 创建待审、已发布、已下架和已删除评论，验证后台筛选、操作确认、列表刷新、置顶排序和权限拒绝。

**Acceptance Scenarios**:

1. **Given** 管理员具有评论读取权限，**When** 打开评论管理，**Then** 可以按文章、状态、时间和关键词查询评论，并看到评论状态、作者显示名、审核信息、点赞数和操作记录摘要。
2. **Given** 管理员具有评论写入权限，**When** 对一条评论执行下架，**Then** 评论立即不再出现在小程序公开列表，后台保留其记录和下架原因。
3. **Given** 管理员确认删除一条评论，**When** 删除成功，**Then** 评论不能再被公开读取或点赞；删除动作留下审计记录，避免仅凭前端隐藏造成数据残留。
4. **Given** 管理员将评论置顶，**When** 小程序重新加载评论列表，**Then** 置顶评论按规则位于普通评论之前，并显示置顶标识。
5. **Given** 管理员没有评论管理权限，**When** 请求评论管理接口，**Then** 服务端拒绝请求，前端不通过隐藏按钮实现安全控制。

### User Story 4 - 审查与风险反馈 (Priority: P1)

系统在评论公开展示前检查色情、暴力、政治等违规内容；命中风险时不公开展示正文，并给用户可理解的处理提示。

**Independent Test**: 使用通过、疑似违规、明确违规、本地规则加载失败和规则执行异常的测试样本，验证评论状态、前台提示和后台可见性。

**Acceptance Scenarios**:

1. **Given** 评论通过审查，**When** 提交完成，**Then** 评论进入可展示状态并出现在文章评论列表。
2. **Given** 评论命中明确违规内容，**When** 审查完成，**Then** 评论不公开展示，用户收到“内容不符合社区规范”等受控提示，后台保留审查结果。
3. **Given** 评论被本地规则判定为疑似风险或规则暂时不可用，**When** 提交完成，**Then** 评论进入待人工审核或受控失败状态，不得绕过审查直接公开。
4. **Given** 评论正文命中敏感规则或本地审查执行异常，**When** 写入日志或返回错误，**Then** 不记录完整正文，不向用户暴露内部规则、原始异常或内部堆栈。

## Edge Cases

- 用户重复提交同一评论或快速连续点击提交时，不得产生重复评论。
- 同一用户在多个设备同时点赞/取消点赞时，最终计数以服务端幂等结果为准。
- 评论列表分页期间发生置顶、下架或删除，不能因迟到响应把已隐藏评论重新展示。
- 文章被下架后，文章详情和评论接口均不得继续公开其评论。
- 评论作者退出登录、账号停用或被删除后，历史评论的显示名和管理处置方式需保持一致。
- 评论正文为空、超长、包含仅空白字符或不支持的控制字符时，服务端拒绝保存。
- 本地审查规则无法确定或规则配置加载失败时，评论不能进入公开状态，并进入待人工审核或受控失败状态。
- 点赞数发生并发更新时，不能出现负数、重复计数或把点赞用户身份返回给其他用户。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 只对已发布文章提供评论读取和评论发表入口；草稿、已下架文章不得公开评论。
- **FR-002**: 小程序文章详情 MUST 展示评论列表、评论数量、空状态、加载更多、加载失败重试和发表评论入口。
- **FR-003**: 评论读取、发表、点赞和取消点赞 MUST 要求有效的小程序登录态；未登录用户不得读取评论正文或评论互动控件。
- **FR-004**: 评论正文 MUST 在写入可见状态前经过后端本地内容审查；审查规则至少覆盖色情、暴力、政治等违规内容，不调用第三方审查服务。
- **FR-005**: 本地规则命中违规或无法确定风险的评论 MUST 不得公开展示；命中结果进入待人工审核或受控拒绝，并向用户返回不泄露规则细节的提示。
- **FR-006**: 每条评论 MUST 记录所属文章、作者用户、正文、状态、审查结果、创建时间和更新时间；评论状态至少覆盖待审、可见、下架、删除。
- **FR-007**: 用户 MUST 能对可见评论点赞和取消点赞；服务端 MUST 对“用户 + 评论”施加唯一约束或等价幂等规则。
- **FR-008**: 评论列表响应 MUST 返回点赞总数和当前登录用户的 `liked` 状态；不得返回其他用户的点赞明细。
- **FR-009**: 评论列表 MUST 支持稳定分页；默认排序为置顶优先，其次按最新发表时间倒序，再按评论编号倒序稳定排序。
- **FR-010**: 后台 MUST 提供评论列表、按文章/状态/关键词筛选、查看审查结果及操作历史。
- **FR-011**: 具有 `comments.write` 权限的管理员 MUST 能对评论执行下架、恢复、置顶和软删除；下架可恢复，删除后的评论不再公开展示且不提供前台恢复入口。
- **FR-012**: 置顶 MUST 只影响所属文章的评论排序，并 MUST 在前台显示置顶标识；每篇文章最多同时置顶 1 条评论。
- **FR-013**: 评论管理接口 MUST 使用独立权限键 `comments.read` / `comments.write`，并按现有 RBAC 规则控制后台菜单和接口访问。
- **FR-014**: 删除、下架、恢复、置顶、审查结果变更和权限拒绝 MUST 写入审计日志，日志不得包含完整评论正文。
- **FR-015**: 所有接口 MUST 使用现有统一响应封装 `{code, message, data, requestId, serverTime}`，并遵循 `/api/v1` 版本路径。
- **FR-016**: 评论显示名、头像和用户标识 MUST 遵循现有隐私脱敏规则；不得返回手机号、身份证号或内部用户标识。
- **FR-017**: 评论正文 MUST 为 1–500 个字符（仅空白字符无效），允许文字表情，不允许链接、图片、语音、贴纸上传或回复其他评论；同一用户每分钟最多提交 3 条。
- **FR-018**: 本地审查规则 MUST 在后端维护并可版本化；规则命中或规则不可用时评论进入待审/受控失败状态，不得公开；被删除评论正文、审查原始结果和业务处置记录保留 7 天，正常评论按文章业务生命周期保留，安全审计日志继续遵循系统既有合规保留规则。

### Key Entities

- **ArticleComment**：一篇已发布文章下的一条用户评论，包含作者、正文、展示状态、审查状态、置顶状态、点赞计数和审计时间。
- **CommentLike**：用户与评论之间的唯一点赞关系，支持创建和取消，并用于返回当前用户点赞状态。
- **CommentModerationRecord**：评论自动审查或人工处置的结果，包含结果类型、原因分类、操作者/服务来源和时间；不保存不必要的完整敏感正文。
- **CommentAdminAction**：后台下架、恢复、删除、置顶等操作的审计记录。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 已登录用户从文章详情进入评论输入到提交成功不超过 3 个明确操作步骤；未登录用户得到可执行的登录提示。
- **SC-002**: 100% 进入公开评论列表的评论都具有通过审查或明确人工放行的状态。
- **SC-003**: 同一用户对同一评论重复点击点赞 10 次，服务端最终有效点赞关系最多 1 条，点赞计数不会重复累加。
- **SC-004**: 管理员下架或删除评论后，下一次公开评论请求不返回该评论；后台仍可按权限查询其处置记录。
- **SC-005**: 评论审查、列表、点赞接口失败时，文章正文仍可正常阅读，页面能显示局部错误和重试入口。
- **SC-006**: 所有评论管理操作均可通过审计记录追溯到操作者、目标评论、动作和时间，且不泄露完整正文。

## Assumptions

- 评论只挂在文章上，不扩展到首页、轮播图或其他内容类型。
- 本期只支持纯文本和文字表情；不做评论回复/楼中楼、图片、语音和贴纸上传，如需要应另立范围。
- 只有已发布文章可以产生新评论；文章下架后不再允许新增评论。
- 小程序继续使用现有登录、请求封装和统一错误状态；不新增前端框架或客户端直连数据库。
- 管理后台沿用现有 Vue 3 + Element Plus + Pinia，后端沿用 FastAPI + SQLAlchemy + Alembic。
- 本地审查规则不可用时默认“宁可延迟展示，也不绕过审查”；后台评论管理提供待审评论的人工放行、下架和删除入口。

## Remaining Implementation Notes

- 本地审查规则的具体词表和规则版本由后端配置维护，不写入小程序包，避免通过反编译暴露完整规则。
- “删除”采用软删除，删除后的正文、审查原始结果和业务处置记录保留 7 天后由清理任务清理；正常可见、待审和下架评论不因该规则自动过期；安全审计记录按系统既有审计保留策略处理。
- “普通用户、客户顾问、组织管理员均可评论”仅指小程序用户身份；后台管理员账号仍通过后台评论管理权限操作。
