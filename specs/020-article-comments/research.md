# Research: 文章评论与评论管理

**Feature**: 020-article-comments  
**Date**: 2026-09-21

## R1: 评论互动必须复用现有登录态

**Decision**: 评论读取、发表、点赞和取消点赞全部使用现有 `get_current_user` JWT 依赖；小程序请求复用 `request-service` 的 Bearer token 和登录过期处理。文章正文仍可按 014 的公开接口读取，但评论区单独要求登录。

**Rationale**:

- 产品已确认小程序登录是评论区前置条件。
- 后端已有统一 token 校验、用户状态和错误封装，不应为评论新增会话机制。
- 将文章正文与评论接口分离，登录失效时不会阻断用户阅读正文。

**Alternatives considered**:

1. 未登录可查看评论：与已确认的登录前置规则冲突。
2. 在小程序本地判断登录后才请求：不能替代后端鉴权，且会产生越权读取风险。
3. 为评论增加匿名访客 ID：增加隐私和滥用复杂度，当前范围不需要。

## R2: 使用本地规则进行内容审查

**Decision**: 后端新增轻量本地 moderation service，先做 Unicode NFKC 归一化、大小写/空白/常见标点规整，再按版本化的色情、暴力、政治关键词和短语规则匹配。通过则进入 `visible`；命中明确规则进入受控拒绝或待审；规则配置不可用或执行异常时进入 `pending`，不得公开。整个流程不调用微信或其他第三方审查服务。

**Rationale**:

- 用户明确要求不使用第三方，预算不足。
- 规则执行在后端，客户端无法绕过；规则不打入小程序包，避免暴露完整词表。
- 归一化能覆盖大小写、全角字符、空白和标点穿插等低成本规避方式。
- 将规则版本和命中分类保存，便于后台解释和后续更新，不保存完整规则命中片段到日志。

**Alternatives considered**:

1. 微信 `msgSecCheck`：成本和外部依赖不符合本次确认。
2. 只在小程序端关键词过滤：可被绕过，无法作为安全边界。
3. 引入 NLP/模型服务：增加依赖、部署成本和不可控误判，超出当前范围。
4. 命中后直接物理删除：丢失后台复核证据，不符合可管理要求。

## R3: 评论、点赞和管理动作使用独立业务表

**Decision**: 新增 `article_comments`、`comment_likes`、`comment_actions` 三类持久化数据；`AuditLog` 只记录安全审计摘要，不承担评论列表事实来源。

**Rationale**:

- 评论有独立状态、置顶、审查和保留周期，不能塞入文章 JSON 或审计日志。
- `comment_likes` 对 `(comment_id, user_id)` 建唯一约束，数据库层保证重复点击不会重复计数。
- `comment_actions` 保存人工审核、下架、恢复、置顶和删除的业务时间线；安全审计继续记录操作者、目标和动作摘要。
- 软删除保留一周时，主表仍能提供后台追踪和定时清理依据。

**Alternatives considered**:

1. 在 `articles` 中存评论 JSON：分页、点赞并发和后台筛选不可控。
2. 只存 `like_count` 不存点赞关系：无法可靠实现取消点赞和幂等。
3. 只依赖 `AuditLog`：审计日志不是评论查询模型，且正文会扩大敏感数据副本。

## R4: 使用显示快照保护历史一致性

**Decision**: 评论写入时保存作者显示名和头像快照；优先复用当前用户资料中的昵称映射（现有系统以 `User.name` 作为 `nickname` 返回）和 `avatar_url`，缺失时显示“儒泰用户”。评论接口只返回快照，不返回手机号、身份证号或用户 ID。

**Rationale**:

- 用户确认前台显示昵称和头像；当前数据模型没有独立的微信昵称字段，新增昵称体系会扩大迁移范围。
- 快照避免用户后续改名/换头像导致历史评论内容跳变。
- 只返回公开展示字段，保持现有敏感字段脱敏原则。

**Alternatives considered**:

1. 每次查询实时 join 用户资料：历史展示会随资料变更，不利于审核追溯。
2. 展示真实姓名和手机号尾号：不符合已确认的昵称头像展示与隐私边界。
3. 新增独立微信昵称同步链路：当前登录流程不提供稳定昵称来源，超出本期。

## R5: 评论列表采用置顶优先的稳定游标

**Decision**: 评论公开和后台列表均使用不透明 cursor；公开排序为 `is_pinned DESC, created_at DESC, id DESC`，后台可按状态/文章/关键词过滤并复用同一稳定排序。置顶操作限制为每篇文章一条，并在事务内先取消旧置顶再设置新置顶。

**Rationale**:

- 现有文章列表已经采用游标分页和服务端排序，评论保持同一请求模式。
- `created_at + id` 解决同一秒内评论的稳定顺序。
- 置顶数量约束防止多个管理员产生不可预测的首屏顺序。
- 游标仅由服务端编码，客户端不解码或自行拼接。

**Alternatives considered**:

1. offset 分页：评论新增/下架时容易重复或跳过。
2. 只按点赞数排序：点赞变化会导致分页漂移，且产品只要求置顶。
3. 允许多条置顶：需要额外置顶优先级和排序管理，超出本期。

## R6: 用数据库约束处理提交和点赞并发

**Decision**: 评论提交要求 `Idempotency-Key`，以 `(user_id, idempotency_key)` 唯一约束收敛超时重试；点赞用 `(comment_id, user_id)` 唯一约束，点赞/取消在事务中锁定评论计数并保证不低于零。后台状态更新携带 `expectedVersion`，过期返回 409。

**Rationale**:

- 现有小程序请求服务已经支持幂等键，反馈和绑定接口已有相同实践。
- 进程内幂等缓存不能覆盖多 worker 或重启，业务唯一约束更可靠。
- 点赞操作是高频并发路径，数据库唯一约束比前端按钮禁用更安全。
- 后台审核可能由多个管理员同时操作，版本号防止覆盖新的处置结果。

**Alternatives considered**:

1. 只禁用按钮：无法覆盖网络重试和多设备并发。
2. 只用全局内存幂等中间件：多实例不一致，且重启后丢失。
3. 后台最后写入覆盖：会丢失审核/下架原因和操作者信息。

## R7: 权限与后台页面沿用现有 RBAC

**Decision**: 新增 `comments.read` 与 `comments.write` 两个权限；系统管理员 seed 默认拥有全部权限，其他角色通过角色管理配置。后台新增 `/comments` 页面，列表与详情/动作在同一页面完成，后端每个接口使用 `require_permission`，前端菜单隐藏只作为体验优化。

**Rationale**:

- 命名与现有 `articles.read/write`、`feedbacks.read/write` 一致。
- 评论管理需要只读运营账号和可写审核账号的分离。
- 单页列表 + 详情抽屉可复用 Element Plus 表格、筛选、确认框和状态标签，不引入新 store。

**Alternatives considered**:

1. 复用 `articles.write`：文章编辑权限不应自动获得用户评论处置能力。
2. 只允许系统管理员：缺少运营只读/审核角色的最小授权能力。
3. 新建独立管理应用：与现有三层结构和后台部署方式冲突。

## R8: 7 天清理与永久安全审计分离

**Decision**: `pending/visible/hidden` 评论按业务生命周期保留；软删除评论的正文、审查原始结果、业务动作记录保留 7 天，由每日维护任务清理。安全 `AuditLog` 不复制正文，继续遵守系统既有审计保留策略。

**Rationale**:

- “保留一周”只针对删除后的业务数据，不能让正常评论自动过期。
- 删除延迟清理给后台复核和误操作排查留出窗口。
- 审计日志的合规留存不能因评论数据清理而被删除。

**Alternatives considered**:

1. 删除即物理清除：无法在一周窗口内复核或追责。
2. 所有评论 7 天过期：与文章长期内容展示冲突。
3. 在审计日志保存正文：扩大敏感信息副本和泄露面。

## R9: 不新增第三方依赖

**Decision**: 使用 Python 标准库文本归一化、SQLAlchemy、FastAPI、Alembic 和现有调度器；前端继续使用原生小程序组件、现有请求层、Vue 3/Element Plus，不引入评论 SDK 或富文本输入组件。

**Rationale**: 满足预算限制和项目 YAGNI 原则，减少审核链路、构建和上线风险。
