# Feature Specification: 绩效规则模块（组织内/组织管理绩效提成 + 单一组织管理员约束）

**Feature Branch**: `006-performance-rules`
**Created**: 2026-08-03
**Status**: Draft
**Input**: User description: "分成规则页名字改为绩效规则页； 绩效规则左侧有组织结构树，绩效规则分为组织内绩效提成方式（按阶梯 百分比提成），本组织内除管理员外人员按组织内绩效提成方式提成，和组织管理绩效提成（按管理组织内以及下属所有组织内人员的总额，以阶梯进行百分比提成），组织管理员按组织管理绩效提成计算；一个组织只能有一个组织管理员；"

## Clarifications

### Session 2026-08-03

- Q: 本次迭代是否包含按绩效规则实际计算提成金额？ → A: 配置 + 计算引擎（既配置规则，也按规则实际计算成员/管理员的提成）
- Q: 现有按层级的"分成规则"与"分成系数"如何处理？ → A: 新规则取代旧机制（旧配置入口移除、旧数据废弃不参与计算）
- Q: 提成百分比作用于什么基数？ → A: 消费金额（成员业务产生的账单金额），提成结果为金额（与业绩积分值体系相互独立）
- Q: 提成计算何时触发？结果存在哪里？ → A: 月度结算落库（提成结果表，按周期可查、可审计）+ 查看时按当前规则实时重算预览

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 绩效规则页与组织结构树 (Priority: P1)

后台"分成规则"菜单与页面改名为"绩效规则"。页面左侧展示组织结构树，选中组织后右侧展示该组织的绩效规则配置——两种绩效提成方式（组织内绩效提成、组织管理绩效提成）及其配置状态。默认选中根组织。

**Why this priority**: 页面改名与按组织维度浏览是本次功能重构的基础入口，决定管理员如何定位与配置每个组织的绩效规则，属 P1。

**Independent Test**: 管理员进入后台 → 导航显示"绩效规则"（无"分成规则"）→ 左侧组织树默认选中根组织 → 切换组织右侧展示对应组织的两种提成方式状态。

**Acceptance Scenarios**:

1. **Given** 管理员打开后台导航, **When** 查看菜单, **Then** 显示"绩效规则"，不再显示"分成规则"
2. **Given** 管理员打开绩效规则页, **When** 页面加载, **Then** 左侧展示组织结构树，默认选中根组织（多根时选第一个），右侧展示该组织的两种绩效提成方式配置状态
3. **Given** 管理员切换选中组织, **When** 切换, **Then** 右侧展示新选中组织的绩效规则配置
4. **Given** 组织尚未配置任何绩效提成方式, **When** 查看, **Then** 展示"未配置"状态

---

### User Story 2 - 组织内绩效提成配置 (Priority: P1)

管理员为选中组织配置"组织内绩效提成方式"：一组阶梯（消费金额区间 → 提成百分比）。该方式适用于本组织内**除组织管理员外**的所有成员，按成员自身业务对应的消费金额计算提成。

**Why this priority**: 这是绩效规则的核心构成之一——定义了组织内普通成员的提成计算方式，属 P1。

**Independent Test**: 为组织配置组织内绩效提成阶梯 → 保存生效 → 修改后变更记录可查。

**Acceptance Scenarios**:

1. **Given** 选中某组织, **When** 配置"组织内绩效提成方式"阶梯列表（多个金额区间与对应百分比）, **Then** 保存成功并生效
2. **Given** 配置的阶梯区间重叠或未覆盖, **When** 提交, **Then** 系统拒绝并提示阶梯区间非法
3. **Given** 组织内绩效提成已生效, **When** 计算某成员的提成, **Then** 该成员（非管理员）按其自身业务消费金额落入的阶梯百分比计算
4. **Given** 组织管理员在该组织内, **When** 计算其提成, **Then** 不按组织内绩效提成计算（按组织管理绩效提成）
5. **Given** 组织未配置组织内绩效提成, **When** 查看成员提成, **Then** 成员无该部分提成（或无提成，视配置）

---

### User Story 3 - 组织管理绩效提成配置 (Priority: P1)

管理员为选中组织配置"组织管理绩效提成方式"：阶梯百分比，计算基数为**该组织及全部下级组织人员业务产生的消费金额总额**。该方式适用于该组织的组织管理员。

**Why this priority**: 定义了组织管理员的提成来源——对管理范围内整体业绩的抽成，是组织管理角色的核心激励，属 P1。

**Independent Test**: 为组织配置组织管理绩效提成阶梯 → 保存生效 → 组织管理员按管理范围内总额计算。

**Acceptance Scenarios**:

1. **Given** 选中某组织, **When** 配置"组织管理绩效提成方式"阶梯列表, **Then** 保存成功并生效
2. **Given** 组织管理绩效提成已生效, **When** 计算该组织管理员的提成, **Then** 以该组织及全部下级组织人员业务产生的消费金额总额为基数，按落入的阶梯百分比计算
3. **Given** 组织树结构调整（下级组织迁入/迁出）, **When** 重新计算, **Then** 基数随之按新子树范围变化
4. **Given** 组织未配置组织管理绩效提成, **When** 查看管理员提成, **Then** 管理员无该部分提成

---

### User Story 4 - 一个组织仅一个组织管理员 (Priority: P1)

系统约束：**每个组织最多一名组织管理员**。在组织人员管理中，将某组织第二名成员设置为该组织管理员时被拒绝并提示（需先撤销现有管理员）。这是对现有行为（004 允许多个管理员）的收紧。

**Why this priority**: 组织管理员是"组织管理绩效提成"的唯一适用对象，若允许多个管理员则提成归属产生歧义；单一管理员约束是绩效规则正确计算的前提，属 P1。

**Independent Test**: 组织 A 已有管理员 X → 尝试将 Y 设为组织 A 管理员 → 被拒绝；撤销 X → 再设 Y → 成功。

**Acceptance Scenarios**:

1. **Given** 组织 A 已存在组织管理员, **When** 后台将另一名成员设为该组织管理员, **Then** 系统拒绝并提示"该组织已有管理员，请先撤销"
2. **Given** 撤销了组织 A 的现有管理员, **When** 再次设置新管理员, **Then** 设置成功
3. **Given** 现有数据中某组织存在多名管理员, **When** 本迭代上线/迁移, **Then** 有明确处理规则（保留一名，其余降为普通成员）
4. **Given** 组织管理员身份变更, **When** 提成计算, **Then** 按变更后的身份适用对应提成方式

---

### User Story 5 - 现有分成规则机制处理 (Priority: P2)

现有按**层级**配置的"分成规则"（固定比例/固定金额/阶梯 + 分成系数）由新的按**组织**绩效提成方式取代。后台不再提供旧的"分成规则"配置入口。

**Why this priority**: 这是对旧机制的重构清理。新绩效规则（US2/US3）上线后旧规则失去意义，但移除与数据处置属清理性质，故为 P2。

**Independent Test**: 后台导航与接口不再提供旧"分成规则"配置；旧数据不影响新绩效规则。

**Acceptance Scenarios**:

1. **Given** 管理员打开后台, **When** 查看, **Then** 不再存在旧"分成规则"配置入口
2. **Given** 新绩效规则生效, **When** 计算提成, **Then** 使用对应组织的绩效提成方式，不参考旧的按层级规则
3. **Given** 旧的规则与系数数据存在, **When** 系统运行, **Then** 旧数据被明确废弃（不再参与计算），处置方式清晰

---

### Edge Cases

- 阶梯区间边界：金额恰好落在阶梯边界（默认含下不含上）需明确归属
- 组织未配置任何提成方式：成员/管理员无提成
- 组织管理员撤销/重新设置：身份变化即时反映到适用的提成方式
- 组织树结构调整（子树迁入/迁出）：组织管理提成的基数（子树总额）随之变化
- 多根组织森林：每个根组织独立配置绩效规则
- 现有数据中组织存在多个管理员：上线时保留一名，其余降为成员（保留规则需明确）
- 组织管理员同时是成员：其业绩计入组织管理提成的基数，但不按组织内提成计算
- 大组织下阶梯配置的数据量：阶梯列表可正常增删改

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 后台导航与页面名称由"分成规则"改为"绩效规则"
- **FR-002**: 绩效规则页左侧必须展示组织结构树（支持多根森林），支持选中组织，默认选中根组织
- **FR-003**: 每个组织可独立配置两种绩效提成方式：组织内绩效提成、组织管理绩效提成
- **FR-004**: 组织内绩效提成以阶梯百分比配置（业绩金额区间 → 百分比），适用于本组织内除组织管理员外的所有成员
- **FR-005**: 组织管理绩效提成以阶梯百分比配置，计算基数为该组织及全部下级组织人员业务产生的消费金额总额，适用于该组织的组织管理员
- **FR-006**: 阶梯配置必须校验：区间不重叠、无歧义；非法配置被拒绝并提示
- **FR-007**: 绩效提成方式的每次修改必须记录变更历史（操作人、时间、变更前后配置）
- **FR-008**: 每个组织最多一名组织管理员；将第二名成员设为组织管理员必须被拒绝并提示
- **FR-009**: 撤销组织管理员后可重新设置新管理员
- **FR-010**: 现有按层级的固定比例/固定金额/阶梯分成规则及分成系数由新的按组织绩效提成方式取代，后台不再提供旧配置入口
- **FR-011**: 系统必须实现绩效提成计算引擎：非组织管理员成员按自身业务产生的消费金额、依所在组织的"组织内绩效提成"阶梯计算；组织管理员按"管理组织及全部下级组织人员业务产生的消费金额总额"、依"组织管理绩效提成"阶梯计算；提成结果为金额（已确认）
- **FR-012**: 现有按层级的固定比例/固定金额/阶梯分成规则及分成系数由新的按组织绩效提成方式取代，后台不再提供旧配置入口，旧数据废弃不再参与计算（已确认）
- **FR-013**: 系统必须支持月度结算任务按各组织绩效规则计算提成并落库（提成结果表，按周期可查、可审计），并支持查看时按当前规则实时重算预览（已确认）

### Key Entities *(include if feature involves data)*

- **绩效提成方式 (Performance Rule)**: 挂在组织下的提成配置。含类型（组织内 `intra_org` / 组织管理 `org_management`）、阶梯列表、生效状态、生效/失效时间、版本、变更历史。
- **阶梯 (Tier)**: 金额区间（下限、上限）与对应提成百分比。同一提成方式下多个阶梯组成阶梯表。
- **组织 (Organization)**: 绩效规则的挂载主体；组织管理提成的计算范围为组织及全部下级组织。
- **组织管理员约束**: 每组织至多一名管理员（适用于组织管理绩效提成）。
- **提成结果 (Commission Result)**: 月度结算按绩效规则计算产生的各成员/管理员提成记录（周期、人员、所属组织、消费金额基数、命中阶梯、提成金额），用于报表与审计。
- **（废弃）分成规则 / 分成系数 (SharingRule / ContributionCoefficient)**: 旧机制，由新绩效提成方式取代。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可在 3 分钟内完成某组织两种绩效提成方式的阶梯配置
- **SC-002**: 切换组织节点后，绩效规则配置在 2 秒内展示
- **SC-003**: 100% 组织满足"最多一名组织管理员"约束
- **SC-004**: 设置第二名组织管理员 100% 被拒绝并给出明确提示
- **SC-005**: 绩效提成方式每次修改 100% 生成变更历史，可追溯查看
- **SC-006**: 后台导航 100% 不再出现"分成规则"入口
- **SC-007**: 阶梯区间重叠等非法配置 100% 被拦截
- **SC-008**: 组织管理绩效提成基数与"该组织及全部下级组织人员消费金额总额"一致（核对偏差为 0）
- **SC-009**: 月度结算后，各成员/管理员的提成结果 100% 落库，按周期可查询、可审计追溯

## Assumptions

- 提成计算基数 = 消费金额（成员业务产生的账单金额），提成结果为金额；与业绩积分值体系相互独立（已确认）
- 阶梯为"金额区间 → 百分比"；区间默认"含下限、不含上限"（边界归属默认，可调整）
- 组织管理绩效提成基数包含管理组织及其全部下级组织所有人员业务产生的消费金额总额（含组织管理员本人）
- 现有按层级的旧"分成规则"与分成系数由新绩效提成方式取代，旧数据废弃不再参与计算（已确认）
- 每个组织最多一名管理员，为对既有行为（004 允许多个）的收紧（FR-008）
- 若现有数据存在组织多管理员，上线时保留一名（其余降为普通成员），具体保留规则在计划阶段明确
- 绩效规则配置由后台管理员操作；权限点沿用现有 `sharing_rules.read/write`（若页面改名，可评估是否迁移权限名为 `performance.*`，本迭代默认沿用现有权限点）
- 提成计算引擎在本迭代实现（已确认）：非管理员按自身业务消费金额 + 组织内提成阶梯，管理员按管理组织及全部下级组织业务消费金额总额 + 组织管理提成阶梯；计算周期沿用既有月度结算节奏，具体口径在计划阶段细化
- 提成结果按月落库（提成结果表），后台按周期可查、可审计；同时提供按当前规则实时重算预览（已确认）
