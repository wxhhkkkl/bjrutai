# Feature Specification: 后台消费录入

**Feature Branch**: `016-admin-consumption-entry`  
**Created**: 2026-09-02  
**Status**: Draft  
**Input**: User description: “在后台管理页面加入一个消费录入功能”

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 录入单笔客户消费 (Priority: P1)

具备消费录入权限的管理员在“消费业绩”页面发起单笔消费录入，选择一个已绑定客户，核对该客户当前归属人员和所属组织，填写消费时间、实付金额及可选备注，确认后完成录入。

**Why this priority**: 这是本功能的核心价值，解决线下消费或暂未同步消费无法进入后台统计的问题。

**Independent Test**: 使用一个已绑定客户填写合法的消费时间和金额并提交，可以独立验证消费记录成功创建，无需依赖其他新增能力。

**Acceptance Scenarios**:

1. **Given** 管理员拥有消费录入权限并进入“消费业绩”页面，**When** 点击“录入消费”，**Then** 系统展示单笔消费录入表单。
2. **Given** 管理员选择了一个已绑定客户，**When** 客户选择完成，**Then** 系统展示客户脱敏信息，并自动带出只读的当前归属人员和所属组织。
3. **Given** 客户、消费时间和实付金额均合法，**When** 管理员确认提交，**Then** 系统只创建一条状态为“已支付”的人工消费记录，为其生成唯一记录编号，并反馈录入成功。
4. **Given** 金额或消费时间不符合规则，**When** 管理员提交，**Then** 系统阻止录入，并在对应字段附近给出中文提示。
5. **Given** 客户在打开表单后被解绑、停用或变更归属，**When** 管理员提交，**Then** 系统按提交时的最新状态校验；不能录入时保留已填内容并说明原因。

---

### User Story 2 - 消费记录进入统一统计 (Priority: P1)

管理员录入成功后，可以在消费明细中看到该记录；该记录按照现有已支付账单规则进入消费总额、趋势及人员排行等统计，不因来源是人工录入而采用不同口径。

**Why this priority**: 只有录入数据能够进入现有统计链路，消费录入才具备完整业务价值。

**Independent Test**: 记录录入前后的消费明细、总额、趋势和归属人员排行变化，可以独立验证统计一致性。

**Acceptance Scenarios**:

1. **Given** 一笔人工消费录入成功，**When** 管理员查看最新消费明细，**Then** 可以看到该记录及其客户、归属人员、组织、消费时间、金额、状态和“人工录入”来源标识。
2. **Given** 一笔人工消费录入成功，**When** 管理员查看相应时间和组织范围内的统计，**Then** 消费总额、趋势和人员排行均按实付金额同步更新。
3. **Given** 管理员使用日期、组织或人员条件筛选，**When** 人工消费符合或不符合筛选条件，**Then** 该记录与现有同步消费使用相同的筛选规则。

---

### User Story 3 - 权限控制与操作追溯 (Priority: P2)

系统只允许被授权的管理员录入消费，并保留可追溯的操作信息，便于核查人工数据来源。

**Why this priority**: 人工录入会直接影响业绩数据，必须限制操作范围并明确责任人。

**Independent Test**: 分别使用有权限和无权限的账号操作，并检查成功记录的审计信息，即可独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员只有消费查看权限，**When** 进入“消费业绩”页面，**Then** 可以查看数据但看不到可用的消费录入入口。
2. **Given** 无消费录入权限的账号尝试提交，**When** 系统处理请求，**Then** 拒绝操作且不产生消费记录。
3. **Given** 一笔人工消费录入成功，**When** 有权限的管理人员核查记录，**Then** 可以追溯操作人、操作时间、客户、金额、来源和备注。

### Edge Cases

- 搜索不到已绑定客户时，展示明确空状态，不允许凭空创建客户后直接录入。
- 客户姓名、手机号或身份证号用于搜索和确认时，敏感信息必须脱敏展示。
- 实付金额为零、负数、包含超过两位小数或不是有效数字时，阻止提交。
- 消费时间晚于当前时间时，阻止提交。
- 客户在提交瞬间已解绑、停用或变更归属时，以提交时的有效关系决定是否允许录入及归属对象。
- 管理员连续点击提交、页面重复请求或网络重试时，同一次录入不得产生多条记录。
- 网络中断导致提交结果不确定时，应提示管理员先查询记录状态再重试，避免重复录入。
- 暂无消费数据时，明细与统计区域保持正常空状态，不显示错误或无意义数值。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在后台“消费业绩”页面向具备消费录入权限的管理员提供单笔“录入消费”入口。
- **FR-002**: 系统必须允许管理员按客户姓名、手机号或身份证号搜索并选择已绑定客户，展示结果时必须隐藏敏感信息的非必要部分。
- **FR-003**: 系统必须自动展示所选客户当前有效的归属人员和所属组织，并将两者设为不可手工更改。
- **FR-004**: 每次录入必须包含客户、消费时间和实付金额；备注为选填项。
- **FR-005**: 实付金额必须使用人民币、数值大于零且最多保留两位小数；消费时间默认当前时间且不得晚于当前时间。
- **FR-006**: 系统必须在最终创建记录前向管理员展示关键信息供确认。
- **FR-007**: 每次成功录入必须生成唯一记录编号，记录来源必须标记为“人工录入”，初始状态必须为“已支付”。
- **FR-008**: 人工录入的已支付消费必须与现有已支付账单采用相同口径，进入消费总额、趋势、组织统计和人员排行。
- **FR-009**: 消费明细必须展示人工记录的客户、归属人员、组织、消费时间、实付金额、状态及来源。
- **FR-010**: 系统必须防止重复点击、重复请求或网络重试为同一次操作创建多条消费记录。
- **FR-011**: 系统必须在最终提交时重新校验客户的绑定状态、启用状态及当前归属关系，并以此确定记录归属。
- **FR-012**: 系统必须记录每次人工录入的操作人、操作时间、客户、金额、来源和备注，以供追溯。
- **FR-013**: 系统必须区分消费查看权限和消费录入权限；无录入权限的账号不得创建人工消费记录。
- **FR-014**: 系统必须为加载、空数据、校验失败、权限不足和提交失败提供清晰的中文反馈；可恢复错误发生后应保留管理员已填写的内容。
- **FR-015**: 首版消费录入不得提供批量导入、已录记录修改、删除、退款处理或向儒泰外部系统回传能力。

### Key Entities *(include if feature involves data)*

- **人工消费记录**: 代表一次由后台管理员补录的已支付客户消费，包含唯一编号、客户、归属人员、组织、消费时间、实付金额、来源、状态和备注。
- **客户**: 消费对应的业务对象；只有存在有效绑定关系且处于可用状态的客户才能被选择。
- **客户归属关系**: 描述客户在提交时所属的拓展人员和组织，是消费统计归属的依据，录入人员不可手工覆盖。
- **操作审计记录**: 描述谁在何时为哪个客户录入了多少金额，以及该操作的来源和备注。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 具备权限的管理员能够在 2 分钟内完成一笔合法消费的录入。
- **SC-002**: 100% 成功录入的消费都能在对应消费明细和统计范围中查到，统计金额与录入实付金额的差异为零。
- **SC-003**: 对同一次提交进行连续点击或自动重试时，最终只产生一条消费记录。
- **SC-004**: 100% 无消费录入权限的账号无法创建人工消费记录。
- **SC-005**: 零金额、负数、超过两位小数、无效金额及未来消费时间均在创建记录前被拦截并显示中文原因。
- **SC-006**: 在正常网络条件下，95% 的录入提交在 3 秒内得到明确的成功或失败结果。
- **SC-007**: 客户搜索结果和录入确认区域中的手机号、身份证号等敏感信息均按现有后台规则脱敏展示。

## Assumptions

- 首版仅支持人民币单笔消费录入。
- 管理员只能为已经与拓展人员建立有效绑定关系的客户录入消费；客户创建和绑定继续使用现有功能。
- 人工录入只创建“已支付”消费，退款、撤销和状态变更不在本次范围内。
- 消费记录编号由系统生成，管理员无需填写外部交易号。
- 消费归属以提交时客户的有效归属关系为准，历史录入不会因为客户后续转移而自动改写。
- 人工录入用于补充后台内部消费与业绩数据，不向儒泰外部系统回传。
- 现有消费统计口径继续作为唯一计算标准，人工来源不改变金额权重或筛选规则。
