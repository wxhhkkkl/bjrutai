# Research: 小程序文章资讯与阅读

**Feature**: 014-article-reading  
**Date**: 2026-08-10

## R1: 直接复用现有公开文章接口

**Decision**: 小程序使用现有公开文章列表和详情能力；本功能不增加首页聚合接口、文章数据库字段或新的管理接口。

**Rationale**:
- 现有服务已经只返回 published，按 `published_at DESC, id DESC` 排序，提供游标分页和详情浏览量递增。
- 后端合同测试已覆盖发布/草稿/下架可见性、分页、空列表、404 和浏览量。
- 首页只需要 3 条，复用列表的 `limit=3` 足够，不值得扩展 workbench 响应。

**Alternatives considered**:
1. 把最新文章加入 workbench：会耦合业务工作台与内容模块，文章故障可能拖垮首页核心数据。
2. 新增推荐接口：当前没有推荐规则，等价于重复列表能力。
3. 小程序调用管理端列表：会暴露草稿/下架内容并破坏权限边界。

## R2: 首页文章采用独立请求与独立状态

**Decision**: 首页原工作台三请求保持现状；文章列表由独立方法加载，维护自己的请求版本、状态与条目。首页主状态不等待文章结果。

**Rationale**:
- 规格明确文章失败不能把首页整体置为失败。
- 现有首页使用 `Promise.all`，若把文章加入其中，任一文章异常会触发全页错误。
- 独立的小状态只增加少量字段，不需要全局 store 或复杂并发抽象。

**Alternatives considered**:
1. 加入现有 `Promise.all`：不满足故障隔离。
2. 使用 `Promise.allSettled` 重写全部首页加载：触碰更多既有逻辑，超出本功能。
3. 把首页文章做成静态入口：可靠但无法让用户发现最新发布内容，不满足首页发现故事。

## R3: 文章 service 复用统一请求层并显式公共访问

**Decision**: 新建最小 `article-service.js`，列表和详情都通过现有 `request-service`，设置 `auth:false`；service 不做展示转换。

**Rationale**:
- 后端公开接口不要求 token，避免过期 token 为公开阅读触发无意义刷新或退出。
- `request-service` 已负责 API base、超时、统一响应验证与错误归一化。
- service/model/page 三层职责与小程序现有代码一致。

**Alternatives considered**:
1. 直接在页面调用 `wx.request`：绕过统一错误和环境配置。
2. 默认携带 token：可以工作，但把公共内容错误地耦合到登录刷新生命周期。
3. 新增文章 Pinia/store：小程序未使用此模式，且没有跨页面写状态。

## R4: 使用原生富文本容器展示受控 HTML

**Decision**: 详情使用小程序原生富文本能力展示后台 HTML，只允许平台支持的安全节点；不使用 WebView、不执行脚本/事件/内嵌程序，也不引入第三方 HTML 解析器。

**Rationale**:
- 后台编辑器产出 HTML，公开详情已直接返回该内容。
- 原生富文本不会提供浏览器脚本执行环境，适合只读图文。
- 后端内容最长 100,000 字符，引入完整浏览器或富编辑器运行时没有必要。
- 图片宽度通过正文容器规则收敛，失败只影响单图。

**Alternatives considered**:
1. WebView：需要 H5 承载页和业务域名，导航与认证更复杂。
2. 第三方 HTML parser：新增依赖和体积，当前标签范围没有明确必要性。
3. 去除全部 HTML 后纯文本：会丢失后台文章的图文结构。

## R5: 游标分页由客户端原样传递并按 articleId 去重

**Decision**: 列表首屏 `limit=20`；加载更多只回传 `nextCursor`。追加前按 `articleId` 去重，并用请求版本避免刷新与旧分页响应竞争。

**Rationale**:
- 服务端游标包含排序位置，客户端不应解析或自行计算页码。
- 发布/下架可能发生在翻页期间，客户端去重能防止边界重复，但最终可见性仍由刷新后的服务端结果决定。
- 页面栈会保留列表实例，返回详情时无需持久化正文或额外缓存。

**Alternatives considered**:
1. 页码分页：与现有接口不匹配。
2. 本地长期缓存列表：会延迟下架内容收敛，且本功能没有离线要求。
3. 每次从详情返回都重载：会丢失阅读位置并增加请求。

## R6: 两个入口共享同一个导航 action

**Decision**: 导航模型新增 `article-list`，首页“查看全部”和“我的”服务项都使用该 action；首页文章卡片携带合法 `articleId` 直接进入统一详情页。

**Rationale**:
- 集中路径定义可被导航合同测试覆盖，避免两个入口出现路径漂移。
- 文章是面向全部已激活业务用户的公开内容，不增加角色 capability。
- “我的”服务项排在消费明细之后，普通用户正好填满截图中的 2×2 宫格。

**Alternatives considered**:
1. 两处直接写死 URL：更容易产生不一致。
2. 新增 article capability：后端没有对应用户权限，属于无依据的前端限制。
3. 将入口放到账户与服务：用户已明确指定“我的服务”空位。

## R7: 列表与详情使用独立页面，不做弹窗或内嵌首页阅读

**Decision**: 新增文章列表和文章详情两个标准二级页面，均复用 `flow-navigation`、`page-state` 和现有安全区规则。

**Rationale**:
- 富文本正文可能较长，独立页面最适合滚动阅读和返回。
- 文章列表需要分页、刷新和位置保留，不适合首页内嵌全部内容。
- 页面栈天然保留列表数据与滚动位置，满足返回体验。

**Alternatives considered**:
1. 首页弹窗阅读：长文体验差且无法从“我的”一致复用。
2. 单页列表内展开正文：会扩大列表节点数量并破坏滚动位置。
3. 使用功能占位页：不满足真实阅读需求。

## R8: 不新增客户端阅读历史或详情缓存

**Decision**: 列表数据只存在页面实例；详情每次新进入调用一次现有详情接口，从而由服务端记录本次查看。`onShow` 不重复加载，用户主动重试时才再次请求。

**Rationale**:
- 规格排除个人阅读历史和长期正文缓存。
- 详情接口读取即增加浏览量，页面生命周期必须避免无意义重复请求。
- 重新进入文章代表新的查看，沿用服务端现有统计语义。

**Alternatives considered**:
1. 全局缓存详情：可能继续展示已下架正文。
2. 本地记录已读：新增用户—文章状态，超出范围。
3. 前端直接 `viewCount + 1`：会伪造服务端事实。

## R9: 文章图标使用独立本地资源

**Decision**: 新增一张与现有服务宫格同尺寸、同圆角和柔和底色的文章图标，缺封面占位则使用页面 CSS 与现有图标能力，不新增另一套插画体系。

**Rationale**:
- 当前服务宫格统一使用本地图片资源，专用图标可保持结构不变。
- 复用推广码、通知或账号图标会造成语义混淆。
- 单个小资源比改造全部服务项支持多种 icon 类型更小。

**Alternatives considered**:
1. 复用现有无关图标：用户识别成本高。
2. 修改服务宫格为动态图标组件：影响所有既有项，范围过大。
3. 加入新图标库：违反无新增依赖约束。
