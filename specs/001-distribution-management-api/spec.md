## Clarifications

### Session 2026-07-30

- Q: 管理后台使用什么认证方式？ → A: 账号密码登录 + JWT令牌（管理员由超级管理员在后台创建账号）
- Q: 贡献值从"待结算"变为"已结算"由什么触发？ → A: 按月自动结算（每月1日凌晨系统自动将上月所有待结算贡献值批量结算）
- Q: 系统告警和通知通过什么渠道发送？ → A: 站内通知 + 管理后台消息中心（管理员登录后台可看到所有通知，支持已读/未读状态）
- Q: 后台账号的角色权限如何管理？ → A: RBAC角色权限模型（超级管理员创建后台账号时分配角色，每个角色有预设权限范围，支持后续新增自定义角色）
- Q: 审计日志和业务操作记录需要保留多长时间？ → A: 永久保留（所有审计日志不删除不归档，数据库随业务增长持续扩容）

> **Note**: Stories are listed in spec order (US1-US10). Implementation order in tasks.md follows logical dependencies: US1 → US4 → US2 → US10 → US3 → US5 → US7 → US6 → US8 → US9.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 登录与身份认证 (Priority: P1)

**小程序端**：用户（市场拓展人或儒泰医生）打开北京儒泰小程序，通过微信授权登录完成身份认证。系统识别用户角色，根据角色和资质状态返回对应的功能权限和首页入口。

**管理后台端**：管理员、财务人员、运营人员通过账号密码登录Vue管理后台，获取JWT令牌。超级管理员在后台创建和管理后台账号。

**Why this priority**: 所有业务功能的入口，没有登录和身份认证，后续所有功能都无法使用。这是系统的基础设施。

**Independent Test**: 可通过微信开发者工具模拟登录流程，验证不同角色的会话创建、令牌刷新、权限返回和页面路由是否正确。

**Acceptance Scenarios**:

1. **Given** 用户首次打开小程序, **When** 点击微信授权登录并输入有效微信code, **Then** 系统创建账号、返回访问令牌和刷新令牌，标记 `isNewUser=true`，引导用户完成资料补全
2. **Given** 已有账号用户打开小程序, **When** 点击微信授权登录, **Then** 系统识别已有账号，返回最新会话信息、角色权限和推荐首页入口
3. **Given** 用户的访问令牌已过期, **When** 前端使用刷新令牌调用刷新接口, **Then** 系统返回新的访问令牌和刷新令牌，旧令牌立即失效
4. **Given** 用户已登录, **When** 调用退出登录接口, **Then** 系统使当前所有令牌失效，清除服务端会话
5. **Given** 用户已登录但资质审核未通过, **When** 获取会话信息, **Then** 系统返回 `qualificationStatus=reviewing`，功能权限受限于当前状态
6. **Given** 管理员在Web后台登录页, **When** 输入正确的账号密码并提交, **Then** 系统返回JWT令牌，跳转至管理后台首页
7. **Given** 管理后台账号连续5次输入错误密码, **When** 再次尝试登录, **Then** 系统锁定该账号15分钟，记录安全日志

### User Story 2 - 资质上传与审核管理 (Priority: P1)

L2-L5层级市场拓展人在注册后需上传法人公司资质文件（营业执照等）。管理员在后台审核资质，审核通过后拓展人方可开展业务（生成推广码、参与贡献值计算）。资质即将过期时系统自动提醒。

**Why this priority**: 资质审核是合规运营的核心环节。未通过审核的拓展人无法正常使用推广和贡献功能，直接影响业务流转。

**Independent Test**: 可通过拓展人端上传资质→管理员后台审核→查询资质状态的完整流程独立验证。

**Acceptance Scenarios**:

1. **Given** 新注册的 L3 拓展人, **When** 提交营业执照、法人证书等资质文件并确认信息真实, **Then** 系统将资质状态设为"审核中"，通知管理员有待审核资质
2. **Given** 管理员在后台看到待审核资质, **When** 审核通过并确认, **Then** 系统将资质状态更新为"已通过"，拓展人账号激活，可生成推广码
3. **Given** 管理员审核资质, **When** 发现资料不符合要求选择驳回并填写原因, **Then** 系统通知拓展人资质被驳回及具体原因，拓展人可重新提交
4. **Given** 拓展人资质已通过但即将到期（30天内）, **When** 系统检测到期时间, **Then** 自动向拓展人发送续期提醒，标记资质状态为"即将到期"
5. **Given** 拓展人资质已过期, **When** 系统检测过期, **Then** 自动停用推广码，暂停该拓展人的贡献值计算

### User Story 3 - 客户绑定管理 (Priority: P1)

儒泰医生在北京小程序中录入患者信息（支持手工录入和拍照AI识别），系统调用哈尔滨儒泰接口进行匹配验证，将客户与指定拓展人建立绑定关系。管理员可在后台对已绑定的客户进行解绑或转移操作。

**Why this priority**: 客户绑定是连接"北京拓展→儒泰服务→贡献计算"整个业务闭环的核心纽带。没有绑定，后续的贡献值计算和分账都无法进行。

**Independent Test**: 可通过医生登录→选择拓展人→录入患者信息→提交绑定→查看绑定状态全流程验证，包括成功匹配、未匹配、重复绑定等场景。

**Acceptance Scenarios**:

1. **Given** 医生登录北京小程序, **When** 选择拓展人并录入患者姓名、手机号、身份证号等完整信息后提交, **Then** 系统调用儒泰 `bindBjUser` 接口匹配，匹配成功返回 `hrb_user_id` 并建立绑定关系
2. **Given** 儒泰尚未匹配到该患者（`hrb_user_id: null`）, **When** 医生提交绑定, **Then** 系统记录绑定申请为"待匹配"状态，等待儒泰后续匹配成功后自动更新
3. **Given** 客户已绑定至某拓展人, **When** 医生再次为该客户提交绑定, **Then** 系统拒绝操作并提示"该客户已存在有效绑定关系"
4. **Given** 管理员在后台对已绑定客户发起解绑, **When** 填写解绑原因并二次确认, **Then** 系统保留历史绑定记录，客户状态变更为"已解绑"，原拓展人保留已结算贡献值
5. **Given** 调用儒泰 `bindBjUser` 接口失败, **When** 系统检测失败, **Then** 自动每10分钟重试一次，最多重试3次，超过后标记为"待人工处理"并通知管理员
6. **Given** 管理员在后台将客户从拓展人A转移到拓展人B, **When** 确认转移操作, **Then** 客户归属变更为拓展人B，历史贡献值归属拓展人A不变，新消费产生的贡献值归属拓展人B

### User Story 4 - 拓展人层级体系管理 (Priority: P1)

管理员在后台建立和管理5-6级层级结构（L1北京总部 → L2 → L3 → L4 → L5 → L6终端用户），支持增删改查、层级迁移、环路检测。每级拓展人可发展多个下级，形成树形结构。

**Why this priority**: 层级体系是整个分账和贡献值计算的基础数据结构。没有层级体系，贡献值的逐级汇总和分账规则无法运作。

**Independent Test**: 可通过管理员在后台创建层级节点→关联上下级→查看层级树→迁移分支→验证环路检测独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员在后台打开层级管理, **When** 选择上级节点并创建新的下级拓展人节点, **Then** 系统自动建立父子关系，展示在层级树中
2. **Given** 邀请人A通过推广码邀请B注册, **When** B完成注册和资质审核, **Then** 系统自动将B归入A的直属下级
3. **Given** 管理员需要将拓展人X及其所有下级从分支A迁移至分支B, **When** 执行迁移操作, **Then** 系统保留历史层级快照，X及其子树在新分支下展示
4. **Given** 管理员尝试将节点A设为B的下级（B本身是A的下级）, **When** 提交操作, **Then** 系统检测到环形引用并拒绝操作，提示"层级关系不允许形成闭环"
5. **Given** 拓展人离职退出, **When** 管理员将其名下所有下级批量迁移至新的上级节点, **Then** 历史贡献值保留在原拓展人名下，新贡献值归入新上级

### User Story 5 - 数据同步与贡献值计算 (Priority: P1)

系统每分钟自动轮询哈尔滨儒泰 `getBindUser` 接口获取新标记的北京来源用户，按用户查询 `getUserBill` 账单数据。根据账单实付金额和配置的换算系数自动计算贡献值，并将贡献值逐级向上汇总至整个层级树。

**Why this priority**: 数据同步和贡献值计算是系统的核心业务引擎。拓展人的收益计算、团队业绩查看、报表对账全部依赖于此。

**Independent Test**: 可通过模拟儒泰接口返回数据→验证北京侧同步入库→检查贡献值计算和汇总结果的端到端流程验证。

**Acceptance Scenarios**:

1. **Given** 儒泰侧有新的北京来源用户标记, **When** 北京侧每分钟轮询 `getBindUser`, **Then** 系统获取新标记用户列表，与本地记录比对后自动入库
2. **Given** 新绑定用户入库, **When** 系统自动调用 `getUserBill` 查询账单, **Then** 以 `transaction_id` 为幂等键写入账单数据，避免重复入账
3. **Given** 账单数据写入成功, **When** 系统触发贡献值计算, **Then** 贡献值 = 实付金额 × 换算系数，结果保留2位小数，并在1分钟内完成更新
4. **Given** 贡献值计算完成, **When** 系统逐级向上汇总, **Then** 每级拓展人的团队贡献值等于其个人贡献值 + 所有直属下级团队贡献值之和
5. **Given** `getBindUser` 连续5次轮询失败, **When** 系统检测失败次数, **Then** 向管理员发送告警通知，记录失败日志
6. **Given** `getUserBill` 对同一用户连续5次查询失败, **When** 系统检测失败次数, **Then** 标记该用户为"查询异常"，通知管理员，支持手动触发重试
7. **Given** 用户账单查询返回空（暂无消费）, **When** 系统处理返回结果, **Then** 标记用户为"已绑定无消费"，等待下次轮询周期重新查询

### User Story 6 - 个人与团队贡献值查看 (Priority: P2)

市场拓展人在小程序查看个人贡献值（本月、累计、趋势图、明细）和直属下级的团队贡献汇总（支持下钻查看子团队）。贡献值只显示数值，不显示金额。

**Why this priority**: 贡献值看板是拓展人使用小程序的核心动力，但需要P1的数据同步和计算先运行起来。可以独立于后台管理功能上线。

**Independent Test**: 可通过切换不同拓展人身份登录→查看个人贡献看板→查看团队贡献→下钻子团队独立验证。

**Acceptance Scenarios**:

1. **Given** 拓展人登录进入"我的贡献"页面, **When** 页面加载, **Then** 展示本月贡献值、累计贡献值、近6个月趋势图、贡献构成分类
2. **Given** 拓展人点击某月贡献值, **When** 展开明细, **Then** 展示该月的贡献明细列表（客户姓名、贡献值、贡献来源、时间）
3. **Given** 拓展人进入"团队贡献"页面, **When** 页面加载, **Then** 展示直属下级的贡献值汇总（每人本月+累计），不显示金额
4. **Given** 拓展人点击某个直属下级, **When** 下钻查看, **Then** 展示该下级的子团队贡献汇总，验证目标拓展人属于当前用户的下级分支
5. **Given** 贡献值处于"待结算"状态, **When** 管理员进行人工调整, **Then** 系统记录调整原因，调整后贡献值更新
6. **Given** 贡献值处于"已结算"状态, **When** 尝试修改, **Then** 系统禁止修改
7. **Given** 月末最后一天, **When** 系统到达次月1日凌晨, **Then** 自动将上月所有待结算贡献值批量结算为"已结算"状态，生成结算日志

### User Story 7 - 分账规则配置 (Priority: P2)

管理员在后台按层级灵活配置分账比例和计算规则（支持固定比例、固定金额、阶梯分账），配置生效时间，规则变更后新数据按新规则计算，历史数据不回溯。

**Why this priority**: 分账规则是贡献值计算和收益分配的依据。P2因为可以先用默认规则运行，待业务方确认具体比例后再灵活调整。

**Independent Test**: 可通过管理员配置不同分账规则→验证规则生效时间切换→检查新旧数据分别按对应规则计算独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员在后台打开分账配置, **When** 新增一条分账规则（选择层级、分账类型、分账基数、分账值、生效时间）, **Then** 系统保存规则并在生效时间到达后自动启用
2. **Given** 某层级已存在生效中的分账规则, **When** 管理员尝试新增同层级规则, **Then** 系统拒绝保存并提示"该层级已存在生效规则，请先停用旧规则"
3. **Given** 管理员修改了换算系数, **When** 新系数生效, **Then** 新系数仅对新产生的账单数据生效，历史数据不回溯计算
4. **Given** 分账规则变更, **When** 变更保存, **Then** 系统记录完整变更日志（变更人、时间、变更前后内容）
5. **Given** 存在未结算数据时修改分账规则, **When** 规则变更生效, **Then** 未结算数据按旧规则结算，新数据按新规则计算

---

### User Story 8 - 多维对账报表 (Priority: P2)

管理员和财务人员在后台选择时间范围和报表维度，生成多维对账报表（客户数据、收款数据、折扣数据、分配金额明细）。支持导出Excel文件。

**Why this priority**: 对账报表是财务和运营管理的刚需，但可以在核心业务流程跑通后再完善。P2优先级合理。

**Independent Test**: 可通过管理员选择时间范围→生成报表→查看各维度数据→导出Excel独立验证。

**Acceptance Scenarios**:

1. **Given** 管理员在后台选择时间范围和报表维度, **When** 点击"生成报表", **Then** 系统在60秒内生成对账报表，包含客户绑定数据汇总、收款数据汇总、折扣数据汇总、按拓展人层级汇总的分配金额明细
2. **Given** 报表生成完成, **When** 用户点击"导出报表", **Then** 系统生成Excel文件并提供下载链接
3. **Given** 财务人员进行月度对账, **When** 对比系统报表与儒泰侧原始数据, **Then** 双方数据偏差不超过0.01%

### User Story 9 - 科普内容管理 (Priority: P3)

运营人员在后台通过CMS系统管理科普文章（创建、编辑、发布、下架、分类）。小程序"科普"板块实时展示已发布的文章列表和详情，支持分类筛选和搜索。

**Why this priority**: 科普内容是提升小程序用户留存和粘性的辅助功能，不涉及核心业务流程。P3优先级可以最后实现。

**Independent Test**: 可通过运营人员发布文章→小程序端查看列表和详情→搜索筛选功能独立验证。

**Acceptance Scenarios**:

1. **Given** 运营人员在CMS创建科普文章, **When** 使用富文本编辑器撰写内容并发布, **Then** 小程序"科普"板块即时展示该文章
2. **Given** 小程序用户浏览科普板块, **When** 选择分类或搜索关键词, **Then** 系统返回符合条件的文章列表
3. **Given** 运营人员需要下架某篇文章, **When** 在CMS点击下架, **Then** 小程序端不再展示该文章

### User Story 10 - 推广码生成与管理 (Priority: P1)

市场拓展人在资质审核通过后，可生成个人专属推广码（二维码）。客户扫码直接进入哈尔滨儒泰小程序，儒泰标记客户来源为"北京（BJTR）"。推广码支持刷新（过期/泄露/手动）和统计分析。

**Why this priority**: 推广码是客户扫码绑定流程的起点，是连接北京拓展人与儒泰客户的桥梁。没有推广码，扫码绑定流程无法启动。

**Independent Test**: 可通过拓展人生成推广码→客户扫码验证→查看推广统计独立验证。

**Acceptance Scenarios**:

1. **Given** 拓展人资质已通过审核, **When** 进入推广码页面, **Then** 系统生成包含 `refToken` 的专属二维码，二维码参数含 `src=BJTR`
2. **Given** 客户用微信扫描推广码, **When** 微信识别URL, **Then** 直接打开哈尔滨儒泰小程序，儒泰解析 `src=BJTR` 标记客户来源为"北京"
3. **Given** 推广码已过期或被怀疑泄露, **When** 拓展人点击刷新推广码, **Then** 系统废止旧令牌，生成新令牌，旧推广码立即失效
4. **Given** 拓展人资质未通过或已过期, **When** 尝试获取推广码, **Then** 系统拒绝并提示资质状态不允许
5. **Given** 拓展人查看推广统计, **When** 选择统计周期, **Then** 系统展示扫码次数、来源线索数、成功绑定数和转化率

---

### Edge Cases

- 客户扫码时网络异常：二维码保持有效性，儒泰侧应提示"网络异常，请稍后重试"
- 同一客户被两个拓展人同时手动录入：以首次录入时间为准，后者提示"该客户已绑定"
- 拓展人离职/退出：管理员将其下级批量迁移至新上级节点，历史贡献值保留
- 儒泰接口超时：北京侧自动重试并做幂等处理，避免重复数据
- 分账规则变更时存在未结算数据：未结算数据按旧规则结算，新数据按新规则
- 资质审核期间拓展人已有客户绑定：客户可扫码绑定但贡献值暂不计算，审核通过后补算
- 医生更换归属拓展人：需管理员操作，医生名下已有客户归属不变
- 退款场景：儒泰返回退款/部分退款状态，北京侧自动冲正对应贡献值
- 轮询漏数：使用游标机制确保增量同步不遗漏，支持手动补拉指定时间段数据
- 高并发绑定提交：使用幂等键 (`Idempotency-Key`) 防止重复提交
- 审计日志增长：日志表需按年度分区，历史分区可迁移至低成本存储以维持查询性能，但逻辑上永久保留不可删除

## Requirements *(mandatory)*

### Functional Requirements

**认证与授权**
- **FR-001**: 系统必须支持微信小程序登录，通过 `wx.login` 返回的临时code在服务端换取微信身份
- **FR-002**: 系统必须支持微信手机号授权绑定，用户首次登录后可绑定手机号
- **FR-003**: 系统必须支持访问令牌和刷新令牌的双令牌机制，访问令牌过期后可通过刷新令牌获取新令牌
- **FR-004**: 系统必须根据用户角色（管理员/拓展人/医生/财务/运营）和资质状态返回对应的功能权限
- **FR-005**: 系统必须支持退出登录，使当前所有令牌失效
- **FR-005a**: 管理后台必须支持账号密码登录，返回JWT令牌，超级管理员可在后台创建和管理后台账号
- **FR-005b**: 管理后台必须在连续登录失败5次后锁定账号15分钟，并记录安全审计日志
- **FR-005c**: 管理后台必须采用RBAC角色权限模型：超级管理员创建后台账号时分配角色（管理员/财务/运营），每个角色预设权限范围（见权限矩阵），一个账号可拥有多个角色，支持后续新增自定义角色

**资质管理**
- **FR-006**: 系统必须支持 L2-L5 拓展人上传法人公司资质文件（营业执照、法人证书、医疗机构许可证），支持 JPG/PNG/PDF 格式，单文件不超过 10MB
- **FR-007**: 后台必须支持管理员审核资质（通过/驳回），驳回时填写原因，审核结果通知拓展人
- **FR-008**: 系统必须在资质即将到期（提前30天）时自动生成站内续期提醒通知
- **FR-008a**: 系统必须在管理后台提供消息中心，汇总所有系统通知（资质审核结果、资质到期提醒、数据同步异常、绑定异常），支持按分类筛选、已读/未读状态管理和查看详情
- **FR-009**: 资质未通过审核的拓展人禁止生成推广码和参与贡献值计算

**客户绑定**
- **FR-010**: 系统必须支持医生在北京小程序中录入患者信息（姓名必填，手机号、身份证号、医保账户、家属手机号为选填）
- **FR-011**: [P2 - deferred] 系统必须支持拍照AI识别录入方式，自动提取患者档案关键信息填入表单。一期仅支持手工录入，AI识别功能延后至二期实现
- **FR-012**: 系统必须调用哈尔滨儒泰 `bindBjUser` 接口进行患者匹配验证，匹配成功返回 `hrb_user_id`
- **FR-013**: 系统必须在儒泰暂未匹配到患者时（`hrb_user_id: null`）记录为"待匹配"状态，等待后续匹配成功后自动更新
- **FR-014**: 系统必须对重复绑定进行检测和拒绝，同一客户不能同时绑定多个拓展人
- **FR-015**: 系统必须支持管理员在后台对已绑定客户进行解绑（需填写原因并二次确认）和转移操作
- **FR-016**: 系统必须记录完整的绑定关系日志（操作时间、操作人、客户标识、原/新拓展人、操作类型、原因）
- **FR-017**: `bindBjUser` 接口调用失败时，系统必须每 10 分钟自动重试一次，最多重试 3 次

**层级管理**
- **FR-018**: 系统必须支持最多 6 级层级结构（L1 总部 → L2 → L3 → L4 → L5 → L6 终端用户）
- **FR-019**: 系统必须支持树形层级结构的增删改查和展示
- **FR-020**: 系统必须检测并拒绝环形引用（如 A 的下级是 B，B 的下级又设为 A）
- **FR-021**: 系统必须支持批量迁移拓展人及其所有下级至另一分支，保留历史层级快照
- **FR-022**: 系统必须在邀请关系建立时自动将新拓展人归入邀请人名下

**推广码**
- **FR-023**: 系统必须为资质审核通过的拓展人生成包含唯一 `refToken` 的专属二维码
- **FR-024**: 二维码内容必须包含 `src=BJTR` 参数，客户扫码后直接打开哈尔滨儒泰小程序
- **FR-025**: 系统必须支持推广码刷新（过期/泄露/手动），刷新后旧令牌立即失效
- **FR-026**: 系统必须提供推广码统计分析（扫码次数、线索数、绑定数、转化率）

**数据同步**
- **FR-027**: 系统必须每分钟定时调用哈尔滨儒泰 `getBindUser` 接口，获取新标记的北京来源用户
- **FR-028**: `getBindUser` 接口必须支持游标分页和时间窗口补拉，确保不遗漏数据
- **FR-029**: 系统必须对照本地绑定记录自动入库新增用户
- **FR-030**: 系统必须在新增绑定用户入库后自动调用 `getUserBill` 查询该用户账单
- **FR-031**: 系统必须以 `transaction_id` 作为幂等键处理账单数据，避免重复入账
- **FR-032**: 系统必须支持 `getAllUsersBill` 日终补偿对账查询
- **FR-033**: `getBindUser` 连续 5 次失败必须在消息中心生成管理员告警通知
- **FR-034**: `getUserBill` 对同一用户连续 5 次失败必须标记为"查询异常"并在消息中心通知管理员
- **FR-035**: 系统必须记录所有接口调用的完整日志（调用时间、接口名、请求参数、响应状态、耗时）

**贡献值计算**
- **FR-036**: 系统必须按照公式"贡献值 = 实付金额 × 换算系数"自动计算，结果保留2位小数
- **FR-037**: 系统必须在账单数据入库后 1 分钟内完成贡献值更新
- **FR-038**: 系统必须支持贡献值逐级向上汇总至整个层级树
- **FR-039**: 贡献值必须支持"待结算"和"已结算"状态流转，每月1日凌晨系统自动将上月所有待结算贡献值批量结算，已结算后禁止修改；同时支持管理员对单个待结算贡献值进行人工调整
- **FR-040**: 管理员修改换算系数后，新系数仅对新数据生效，历史数据不回溯
- **FR-041**: 系统必须在儒泰返回退款/部分退款时自动冲正对应贡献值

**贡献值展示**
- **FR-042**: 小程序必须展示拓展人本月贡献值、累计贡献值、近6个月趋势图
- **FR-043**: 小程序必须展示贡献值明细列表（客户、贡献值、来源、时间）
- **FR-044**: 小程序必须展示直属下级贡献值汇总（每人本月+累计），不显示金额
- **FR-045**: 小程序必须支持团队贡献下钻查看，验证查询者具有对应分支权限
- **FR-046**: 小程序必须展示贡献值构成分类（绑定/服务/跟进/账单/调整）

**分账配置**
- **FR-047**: 后台必须支持按层级配置分账规则（分账类型：固定比例/固定金额/阶梯；分账基数：实付金额/合计金额；分账值）
- **FR-048**: 分账规则必须支持设置生效时间，到达生效时间后自动启用
- **FR-049**: 同一层级同一时间只能有一条生效中的分账规则
- **FR-050**: 分账规则变更必须记录完整变更日志

**报表与对账**
- **FR-051**: 后台必须支持选择时间范围和维度生成对账报表，60 秒内完成
- **FR-052**: 对账报表必须包含：客户绑定数据汇总、收款数据汇总、折扣数据汇总、按层级汇总的分配金额明细
- **FR-053**: 系统必须支持报表导出为 Excel 文件
- **FR-054**: 报表数据与儒泰侧原始数据偏差不超过 0.01%

**内容管理**
- **FR-055**: 后台必须提供科普文章 CMS（创建、编辑、发布、下架、分类管理）
- **FR-056**: CMS 必须支持富文本编辑，可插入图片和视频
- **FR-057**: 小程序"科普"板块必须支持文章列表（分类筛选）、文章详情、搜索功能
- **FR-058**: 已下架文章不得在小程序前端展示

**合规**
- **FR-059**: 系统必须在客户首次进入绑定流程时展示隐私协议弹窗，获得用户明确同意后方可进行绑定
- **FR-060**: 隐私协议必须明确告知用户数据将与哈尔滨儒泰互联网医院共享
- **FR-061**: 列表和详情接口默认返回脱敏数据（手机号、身份证号）
- **FR-062**: 小程序不得保存身份证、医保账户和完整手机号明文到本地缓存
- **FR-063**: 所有敏感数据修改、客户归属变更和贡献调整必须留存审计记录
- **FR-063a**: 所有审计日志（绑定操作日志、接口调用日志、分账规则变更日志、敏感数据修改记录、登录安全日志）必须永久保留，不可物理删除；数据库需按年度分区以维持查询性能

**公共API规范**
- **FR-064**: 所有API必须遵循统一的请求/响应格式（code/message/data/requestId/serverTime）
- **FR-065**: 列表接口必须支持游标分页（cursor/pageSize/nextCursor/hasMore）
- **FR-066**: 关键写接口（绑定、资质提交、反馈提交）必须支持幂等键 (`Idempotency-Key`)
- **FR-067**: 所有接口必须返回标准化的业务错误码，调用方可根据错误码判断是否可以重试
- **FR-068**: 金额字段服务端内部使用"分"为单位，贡献值使用字符串格式避免浮点精度问题
- **FR-069**: 时间字段统一使用 ISO 8601 格式，日期使用 `YYYY-MM-DD` 格式

### Key Entities

- **用户 (User)**: 系统的使用者，包含身份类型（拓展人/医生/管理员/财务/运营）、激活状态、资质状态、个人资料（姓名、手机号、所属机构、头像）
- **拓展人 (Promoter)**: 层级体系中的节点，属于某一层级（L2-L5），拥有推广码，可发展下级拓展人，有资质信息，参与贡献值计算
- **层级节点 (HierarchyNode)**: 树形结构中的节点，有上级节点引用，包含层级标识（L1-L6）、子节点列表、创建时间
- **资质 (Qualification)**: 拓展人上传的法人公司资质文件，包含法人主体名称、资质类型、统一社会信用代码、有效期、审核状态、审核记录
- **客户 (Customer)**: 被拓展人发展的终端用户，通过绑定关系归属于某拓展人，有姓名、手机号、身份证号、医保账户等个人信息
- **绑定申请 (BindingRequest)**: 医生提交的客户绑定记录，包含客户信息、归属拓展人、绑定来源（手动/扫码/儒泰标记）、绑定状态（待匹配/匹配中/已绑定/已解绑/已转移/异常）、儒泰用户ID
- **推广码 (PromotionCode)**: 拓展人的专属推广标识，包含唯一短令牌、二维码图片、状态（可用/停用/过期）、有效期
- **账单 (Bill)**: 从哈尔滨儒泰同步的客户消费记录，包含交易流水号、交易时间、诊费、医药费、合计、折扣、实付金额、退款金额、交易状态
- **贡献值记录 (ContributionRecord)**: 基于账单计算产生的贡献值，包含贡献值数量、状态（待结算/已结算/已冲正/已取消）、来源类型、来源记录、计算规则版本、归属拓展人
- **分账规则 (SharingRule)**: 管理员配置的分账规则，包含适用层级、分账类型、分账基数、分账值、生效时间、状态
- **对账报表 (ReconciliationReport)**: 按时间范围和维度聚合生成的报表，包含客户数据汇总、收款数据汇总、折扣数据汇总、分配金额明细
- **文章 (Article)**: CMS管理的科普内容，包含标题、富文本正文、封面图、分类、发布状态、发布时间
- **跟进记录 (FollowupRecord)**: 医生对客户的跟进记录，包含跟进方式、跟进结果、跟进内容、下次提醒时间
- **授权记录 (ConsentRecord)**: 用户或客户的隐私协议授权记录，包含授权场景、同意版本、授权范围、授权时间

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从扫码到完成微信登录全流程在 5 秒内完成
- **SC-002**: 客户绑定成功率（提交申请到成功绑定）达到 99% 以上
- **SC-003**: 绑定数据同步延迟不超过 1 分钟（儒泰标记 → 北京轮询获取）
- **SC-004**: 账单数据同步延迟不超过 10 分钟（儒泰产生 → 北京获取入库）
- **SC-005**: 数据同步成功率（getBindUser/getUserBill 调用成功次数/总调用次数）达到 99.5% 以上
- **SC-006**: 账单数据入库后 1 分钟内贡献值完成更新和逐级汇总
- **SC-007**: 对账报表在 60 秒内生成完成
- **SC-008**: 系统报表与儒泰侧原始数据偏差不超过 0.01%
- **SC-009**: 资质审核时效 P95 不超过 24 小时（提交 → 审核完成）
- **SC-010**: 对账耗时相比人工对账降低 80% 以上
- **SC-011**: 系统支持同时 500 名拓展人的贡献值并发计算和查询
- **SC-012**: 前端页面主要接口（工作台、客户列表、贡献看板）响应时间在正常网络下不超过 2 秒

## Assumptions

- 哈尔滨儒泰互联网医院已提供 `bindBjUser`、`getBindUser`、`getUserBill`、`getAllUsersBill` 四个接口，接口规范以双方联调确认结果为准
- 双方用户身份通过手机号作为主要关联字段，儒泰侧已支持手机号匹配
- 微信小程序已通过微信公众平台审核，具备「扫普通链接二维码打开小程序」能力
- 推广二维码采用微信「普通链接二维码」方案，客户扫码直接进入儒泰小程序
- 小程序前端代码已完成，本规格聚焦于管理后台和API接口层的功能范围
- 贡献值换算系数初始值为"1元 = 1贡献值"，后续可由管理员在后台调整
- 各层级分账比例由业务方后续提供具体参数，系统支持灵活配置
- 医生身为拓展人之一，可在北京主体小程序中完成客户与拓展人的关联操作
- 小程序的云存储（文件上传）已就绪，使用短期上传凭证方案
- 服务端部署环境支持 HTTPS，域名已完成微信后台配置和ICP备案
- 系统遵循"常规版本"定位，不涉及敏感医疗诊断、处方开具等需医疗资质的功能
