# Feature Specification: 绩效计算模块（月度核算 + 审核确认 + 小程序展示 + 导出）

**Feature Branch**: `008-performance-calculation`
**Created**: 2026-08-05
**Status**: Draft
**Input**: User description: "增加一个绩效计算模块； 绩效计算要按绩效规则进行计算；每个月计算完成后需要审核才能展示到小程序页面；小程序可以看到当月绩效情况的预估值；当月审核确认后的数字不能进行再次核算，要保留当时计算的规则；管理员可以导出每个月的核算详情数据；页面进入时展示组织结构树，以及每个人的当月绩效的估算；"

## Clarifications

### Session 2026-08-05

- Q: 审核与导出的权限控制 → A: 新增独立权限点（performance.settle），与规则编辑权限（sharing_rules.*）分离
- Q: 小程序预估/已确认展示的内容 → A: 仅提成金额明细（计算基数、命中比例、提成金额），不含业绩贡献值
- Q: 小程序端预估/已确认的展示对象 → A: 推广员查看本人，组织管理员查看所管理组织（两种视角都支持）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 绩效计算页：组织结构树 + 当月绩效估算 (Priority: P1)

管理员进入"绩效计算"页面，左侧展示**组织结构树**，右侧展示选中组织（默认根组织）下**每个人的当月绩效估算**。页面支持切换月份（默认当前月）与切换组织节点。

**Why this priority**: 这是绩效计算模块的入口页，让管理员一眼看到全组织每个人的当月绩效估算，是审核、导出的前提与数据入口，属 P1。

**Independent Test**: 进入页面 → 看到组织树 + 选中组织下每个人的当月绩效估算 → 切换组织/月份 → 估算随之更新且与规则一致。

**Acceptance Scenarios**:

1. **Given** 管理员进入绩效计算页, **When** 页面加载, **Then** 左侧展示组织结构树，默认选中根组织，右侧展示该组织下每个人的当月绩效估算
2. **Given** 页面展示估算, **When** 切换选中组织, **Then** 展示新选中组织及其下属组织范围人员的估算
3. **Given** 页面展示估算, **When** 切换月份, **Then** 展示对应月份的估算（默认当前月）
4. **Given** 估算数据, **When** 核对, **Then** 估算按当前生效绩效规则（组织内/组织管理提成阶梯）计算，结果与规则一致

---

### User Story 2 - 月度核算与审核确认（冻结 + 规则快照） (Priority: P1)

系统按绩效规则对某月进行核算。核算完成后结果处于**待审核**状态。管理员对某月核算进行**审核确认**；确认后该月数据**冻结**——不能再重新核算覆盖数值，且保留核算时使用的绩效规则（规则快照）。只有确认后的数据才作为"已确认"结果展示到小程序页面。

**Why this priority**: 审核—冻结机制是本模块的核心价值——保证小程序展示的数字是经过确认、稳定、可追溯的，属 P1。

**Independent Test**: 完成某月核算 → 小程序不展示该月已确认数据 → 管理员审核确认 → 小程序展示确认后的数字 → 修改规则后再触发核算 → 已确认月份数字不变（保留当时规则）。

**Acceptance Scenarios**:

1. **Given** 某月核算完成, **When** 管理员查看, **Then** 结果显示为"待审核"，小程序不展示该月已确认数据
2. **Given** 待审核结果, **When** 管理员审核确认, **Then** 状态变为"已确认"，记录确认人与确认时间
3. **Given** 某月已审核确认, **When** 系统再次核算, **Then** 该月数字不再重算（冻结），保持确认时的数值
4. **Given** 某月已审核确认, **When** 绩效规则随后被修改, **Then** 已确认月份的核算结果仍按核算当时的规则展示（规则快照，可追溯）
5. **Given** 待审核结果, **When** 管理员发现数据需要调整, **Then** 可在确认前重新核算
6. **Given** 某月处于待审核状态, **When** 管理员审核并"打回", **Then** 记录打回原因，该月回到可重新核算状态
7. **Given** 某月被打回, **When** 重新核算完成, **Then** 该月再次进入待审核状态，管理员可再次审核确认

---

### User Story 3 - 小程序绩效展示：当月预估 + 已确认结果 (Priority: P1)

小程序用户（**推广员查看本人**、**组织管理员查看所管理组织**）可以查看：**当月绩效的预估**（实时按当前规则估算）与**历史已确认月份**的绩效结果（审核确认后冻结的数字）。展示内容为**提成金额明细**（计算基数、命中比例、提成金额），不含业绩贡献值。未确认月份的结果不作为已确认数据展示。

**Why this priority**: 小程序是最终用户查看绩效的出口，预估与已确认双态并存是本需求的核心交付，属 P1。

**Independent Test**: 小程序进入绩效页 → 看到当月预估值 → 看到已确认月份的历史结果 → 未确认月份不显示已确认数据。

**Acceptance Scenarios**:

1. **Given** 小程序用户进入绩效页, **When** 查看当月, **Then** 展示当月绩效预估值（按当前规则实时估算）
2. **Given** 某月已审核确认, **When** 小程序用户查看该月, **Then** 展示确认后冻结的绩效结果
3. **Given** 某月未审核确认, **When** 小程序用户查看该月, **Then** 不展示已确认数据（仅当月展示预估）
4. **Given** 当月数据, **When** 核对, **Then** 小程序预估与管理员页面看到的当月估算一致

---

### User Story 4 - 管理员导出月度核算详情 (Priority: P2)

管理员可以导出某个月的核算详情数据（各人员绩效核算明细），用于对账与存档，导出为表格文件。

**Why this priority**: 导出是核算结果对外交付与存档的辅助能力，在审核确认主流程之后，故为 P2。

**Independent Test**: 选择某月 → 点击导出 → 得到包含各人员核算明细的表格文件 → 与页面数据核对一致。

**Acceptance Scenarios**:

1. **Given** 管理员选择某月, **When** 点击导出, **Then** 下载包含该月各人员核算明细的表格文件
2. **Given** 导出文件, **When** 核对, **Then** 文件内数据与页面展示的核算结果一致
3. **Given** 某月无核算数据, **When** 导出, **Then** 明确提示无数据或导出空表

---

### Edge Cases

- 组织未配置绩效规则：该组织人员无估算/核算结果（展示"未配置"）
- 当月无业务数据：估算为 0 或空态
- 多根组织森林：每个根组织独立展示与核算
- 审核确认后规则变更：已确认月份保留规则快照，新月份按新规则计算
- 待审核期间数据变化：待审核状态可重新核算；确认后冻结不受影响
- 打回后必须重新核算、再审核确认：打回 → 重算 → 待审核 → 确认 的闭环；确认后不得再次打回
- 人员调整组织：按当月调整后的归属计算
- 组织管理员身份变化：按适用提成方式（组织内/组织管理）计算
- 重复审核确认：同一月份不得重复确认（幂等，只允许一次）
- 人员停用/离职：当月是否有核算结果需有明确规则（按当月归属与业务数据）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供绩效计算页面，进入时展示组织结构树与选中组织内每个人的当月绩效估算（默认当前月份、默认选中根组织）
- **FR-002**: 绩效计算必须按各组织当前的绩效规则计算（组织内/组织管理提成，沿用绩效规则模块的阶梯定义）
- **FR-003**: 每个月的绩效核算结果必须具备状态流转：待审核 → 已确认
- **FR-004**: 未审核确认的月度核算结果不得作为"已确认"数据展示到小程序
- **FR-005**: 管理员必须能对某月核算结果进行审核确认，并记录确认人（管理员）与确认时间
- **FR-006**: 已审核确认的月份必须冻结：系统不得再对该月重新核算覆盖其数值
- **FR-007**: 已审核确认的月份必须保留核算时使用的绩效规则（规则快照），后续规则变更不影响已确认月份的历史数据
- **FR-008**: 待审核状态的月份允许重新核算（数据或规则调整后可重算）
- **FR-009**: 小程序必须向推广员展示本人、向组织管理员展示所管理组织的当月绩效预估（按当前规则实时估算）与历史已确认月份的绩效结果；展示内容为提成金额明细（计算基数、命中比例、提成金额），不含业绩贡献值
- **FR-010**: 管理员必须能导出某个月的核算详情数据（表格文件），导出内容与页面数据一致
- **FR-011**: 核算结果必须按组织与人员可查询，支持按组织树范围筛选
- **FR-012**: 系统必须以"月"为整体单元进行核算审核：管理员一次确认即覆盖该月所有组织的核算结果（按月整体确认）
- **FR-013**: 审核操作必须包含"确认"与"打回"两种操作；打回必须记录原因；打回后该月核算回到可重新计算状态，重新核算后再进入待审核
- **FR-014**: 绩效核算的审核确认/打回与导出操作必须受独立权限点（performance.settle）控制，与绩效规则编辑权限（sharing_rules.*）分离

### Key Entities *(include if feature involves data)*

- **绩效核算 (Performance Settlement)**: 某月（周期）的核算批次。含核算周期、状态（待审核/已确认）、确认人、确认时间。是冻结与小程序展示的单元。
- **核算结果 (Commission Result)**: 每个人员在某月的核算明细。含人员、所属组织、提成类型、计算基数、命中比例、核算金额、规则快照、计算时间、状态。
- **规则快照 (Rule Snapshot)**: 核算时使用的绩效规则配置（阶梯列表、比例等）的副本，随核算结果保留，用于历史追溯与冻结。
- **组织 (Organization)**: 组织结构树节点；核算与预估按组织及子树范围聚合/筛选。
- **人员 (Distributor)**: 绩效核算与预估的归属主体。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员进入绩效计算页 2 秒内展示组织树与当月估算
- **SC-002**: 当月估算与按当前绩效规则手算结果一致（核对偏差为 0）
- **SC-003**: 未审核确认的月份 100% 不作为已确认数据展示到小程序
- **SC-004**: 已确认月份 100% 冻结，重复核算不改变其数值
- **SC-005**: 规则修改后，已确认月份的历史数字 100% 保持不变，且可追溯核算当时使用的规则
- **SC-006**: 审核确认操作 100% 记录确认人与确认时间
- **SC-007**: 导出的月度核算文件与页面数据 100% 一致
- **SC-008**: 小程序当月预估与管理员页面当月估算一致（核对偏差为 0）

## Assumptions

- 审核由后台管理员操作，需具备独立审核权限点（performance.settle）；审核/导出与绩效规则编辑权限（sharing_rules.*）分离（已确认）
- 审核以"月"为整体单元，管理员一次确认覆盖该月所有组织的核算结果（已确认）
- 审核支持"确认"与"打回"两种操作：打回记录原因、打回后重算再审核；确认后冻结不可变（已确认）
- 小程序端：推广员查看本人绩效，组织管理员可查看所管理组织绩效（沿用现有小程序绩效页面能力）（已确认：两种视角都支持）
- 预估 = 按当前生效绩效规则对当月数据实时计算（与现有预览计算一致），不落冻结库；已确认 = 审核确认后冻结的核算结果
- 小程序预估与已确认展示内容为提成金额明细（基数、比例、金额），不含业绩贡献值（已确认）
- 结算与核算沿用既有月度节奏；核算结果以"月"为单位冻结，跨月数据相互独立
- 导出格式为表格文件（CSV/Excel），具体格式在计划阶段确定
- 规则快照在核算落库时生成并随核算结果保存（基于现有绩效规则版本）
- 本迭代包含管理后台"绩效计算"页、后端核算/审核/导出能力、小程序预估与已确认展示；小程序 UI 具体改动范围在计划阶段细化
- 依赖已实施的绩效规则模块（006）与业绩贡献/结算体系（贡献结算、消费金额基数）
- 管理端页面的"估算"与小程序的"预估"为同一实时计算的两种称呼，语义统一为：按当前规则对当月数据的实时计算（不落冻结库）
